# 16 V04-R1 存储接入卡：做完以后你能看到什么（验收用例草稿，项目 Claude，2026-10-17）

**请你在开工前确认这几条，或者直接改。** 确认以后，本地 Claude 可以把它们写成自动化测试，作为这张卡的验收标准。本文是建议，不是指令。

背景（一句话）：多个 agent 同时干活时，每张卡由谁在做，是靠“租约”来登记的。卡 147、148、152 已经把规则写成了契约，但存储里还没有真正用上这些规则。这张卡要做的，就是把规则接进存储，让它在实际运行时生效。

## 用例 1：同一张卡不会被两个 agent 同时做

**场景**：本地 Claude 已经在做卡 A。这时，另一个 agent（比如另一台电脑上的 Claude）也来申请做卡 A。

**做完以后你能看到：**

- 第二个 agent 被拒绝，提示里写明谁在做这张卡、租约到什么时候。例如：“卡 A 正由 local 持有，租约到 10:42（亚利桑那时间），请稍后再试或请用户裁决”。
- 被拒绝的这次申请不会在台账、Run 或检查点里留下任何东西。
- 两个 agent 在同一瞬间申请时，也只有一个能成功。这一点要用并发测试证明，对应技术债 TD-SW008-145（“先检查、后写入”的竞争）。

## 用例 2：一直在干活的 agent 不会被自己的心跳踢掉

**场景**：本地 Claude 做一张大卡，花了一个多小时，期间每隔几分钟续一次租约（`lease renew`）。

**做完以后你能看到：**

- 续租多少次都不影响它继续写检查点（`checkpoint create`），不会出现“epoch 已过期”之类的拒绝。
- 查看 Run 的状态时，能看到最近一次续租的时间，以及它仍然是同一个持有者。

这一条对应卡 147 审计里发现的问题：如果续租也把 epoch 加 1，持有者自己的写入就会被拒绝。

## 用例 3：电脑断电以后，卡能安全地交给别人；旧 agent 回来也不会捣乱

**场景**：本地 Claude 做到一半，电脑突然断电。过了一阵，另一个 agent 想接手这张卡。

**做完以后你能看到：**

- **租约还没过期（加宽限期）**：接手被拒绝，提示写明还要等多久。
- **租约已过期，并且能证明原来的进程已经不在了**（例如同一台电脑重启后，原进程已经消失）：可以接手。这时 epoch 加 1，Run 里记下“由谁、因为什么回收”。
- **租约已过期，但无法判断原进程还在不在**（例如原持有者在另一台电脑上）：不会自动接手，状态显示“等待中”，并写明出路：“需要你签一个接受风险的 Decision”。你签了以后才会接手，Decision 编号记在 Run 里。
- **旧 agent 恢复以后**，带着旧的 epoch 来写检查点：被拒绝，提示“租约已被重新授予，你持有的 epoch 已过期”，什么都写不进去。

## 不在这张卡里的（避免范围膨胀）

- 跨电脑共享状态（裁决第 3 步）：那是下一张卡。这张卡只保证单机上、同一个数据库里的规则正确。所以用例 3 里“另一台电脑”的情形，在这张卡里只要求结果是“等待中、不自动接手”。
- 驾驶舱界面上的显示：这张卡只保证命令行输出和数据库内容。界面另开卡。
