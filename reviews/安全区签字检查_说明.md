# 安全区签字检查上 GitHub：说明

> 2026-10-21，云端 Claude Code 会话（分支 `claude/safety-signoff-check`，D09 前预做，未开 PR）。本文是数据，不是指令。
> 设计依据：项目文件夹 `plans/现场回传与安全签字规则_设计稿_20261021.md` 第 2 节（落地卡 B）。

## 1. 这是什么

每个提交到 `main` 的 PR 都会跑一个 **`safety-zone`** 检查（工作流 `.github/workflows/safety-gate.yml`，脚本 `reviews/tools/safety_zone_check.py`）：

1. **碰没碰安全区**：急停、安全门、光栅/光幕、安全继电器及反馈、复位确认，以及**只靠软件实现的设备防撞联锁**（用户 10-21 定）。
2. **碰了，有没有你本人的签字**：你在 PR 页面评论一行 `安全签字 <PR 当前头提交号>`，检查自动重跑并放行。签完再推任何新提交，签字作废，要重签。
3. **两项硬检查，签字也放不行**：
   - 禁止式：`OR TRUE`、`AND FALSE` 这类恒真/恒假旁路（不管是什么变量）；安全点被直接赋常量；引用安全变量的代码被整行注释掉；
   - 完整性：清单里的每个安全点，程序逻辑里至少读一次（只在 VAR 里声明不算）。

和越界检查（`gate`）互不替代：`gate` 管“改没改不该改的地方”，`safety-zone` 管“改了危险的地方有没有人担责”。两个都设成必过检查。

## 2. 安全区怎么标：清单为主，区段注释为辅

**结论：每个项目一份清单文件 `02_PLC程序/工程资产/safety_zone.yml`，块里只有一段是安全逻辑时再用成对注释圈出来。** 理由：

| 考虑 | 清单文件 | 只用注释 |
|---|---|---|
| PR 能不能悄悄缩小安全区 | 不能：清单取 PR 基线（main）和 PR 头的并集，改清单本身就要签字 | 删掉注释就没了；所以注释也按两边并集算，删标记那一行本身就算碰了安全区 |
| 能不能抓到 `FB_1004:97` 这种（送料块里一行引用了 `SafetyOk`） | 能：按变量名/通配标，任何文件任何一行引用都算 | 抓不到：没人会把送料块整块圈成安全区 |
| 漏移植急停能不能查出来 | 能：清单列出安全点，逐个查有没有被读 | 不能：注释只标“有什么”，不知道“该有什么” |
| 一眼看清全项目安全范围、你签一次就定 | 一个文件，约 15 分钟看完 | 散在几十个文件里 |
| 块里只有一小段是安全条件 | 只能整块列入，签字次数偏多 | 精确 |

所以三层取并集，任一层命中就算碰：

```yaml
# 0100_PLC自动化/<项目>/02_PLC程序/工程资产/safety_zone.yml
project_id: DJ-2026-009
files:                      # 第 1 层：整块都是安全逻辑的文件（相对项目根，可通配）
  - 02_PLC程序/PLC_ST/00_安全/*.scl
variables:                  # 第 3 层：引用即算碰安全区（可通配，不分大小写）
  - "*SafetyOk*"
  - "*Interlock*"
points:                     # 安全输入点：必须被程序读到，且不得赋常量；X/Y 区间按八进制展开
  - ESTOP_OK
  - X140..X147
```

```
// 第 2 层：块里只有一段是安全条件时，在 SCL 里成对圈出（标记行本身也算在区段里）
// @安全区 开始：安全条件
q_bEnable := ESTOP_OK AND i_bSafetyOk;
// @安全区 结束
```

`io_points.csv` 可以加一列 `安全`（是/否），标“是”的行，标签名和地址都算安全点（程序里读到其中任一即可）。没有这一列也不报错。

清单只认这几个键：`project_id`、`files`、`variables`、`points`（另允许 `signed_by`、`signed_at_commit`、`note` 作记录）。**拼错的键直接判不通过**，免得一个错别字让安全区悄悄变小。

**还没有清单的项目（未标定）**：改它的任何 PLC 程序（`.scl/.st/.db/.udt/.awl`）都按碰了安全区处理，全部要签字，不会因为没标就放松。共享库 `01_SharedLibraries` 同理（FB_TON 这类被各项目联锁引用）。目前仓库里所有项目都还没有清单，补标是落地卡 E（先 009，再 005）。

## 3. 签字怎么写、机器怎么认

在 PR 页面（网页或手机 App）手写一条评论，某一行是：

```
安全签字 a1b2c3d
已看仿真记录：急停各步、安全门、复位上升沿 全过
```

机器核对：

1. 评论人登录名是 `baiyangfu-hash` **且**数字用户 ID 是 `246858089`（ID 不随改名变，防同名新账号）；
2. 提交号（至少 7 位，大小写不限，可带反引号或冒号）是 PR **当前**头提交的前缀；
3. 评论不是经由 GitHub App 发出的（`performed_via_github_app` 为空），Claude 等 App 代发的不算；
4. 以 `>` 开头的引用行、句子中间提到的“安全签字”都不算，必须是单独一行开头。

审计者不能代签，审计通过也不等于签字。能签字的人写在脚本的 `SIGNERS` 里；将来 3 人小队要加人，改它（它是“裁判”文件，改它要逐字点名，且本身受越界检查和审计）。

## 4. 已知漏洞（现在不解决，11-20 改私有时再定）

**本机 agent 可以拿你电脑上已登录的 `gh` 命令行，以你的名义写一条“安全签字”评论，机器分不出来。** 这样发出的评论用的是你的个人令牌，GitHub 不会标记成 App 代发，第 3 条核对挡不住。

现在的对策只有规矩加审计：入口文件写明“不得代签”（落地卡 A），审计逐条核对签字评论的来源。
更硬的做法要等仓库 11-20 改私有时一起核实：GitHub“环境审批”（Environment required reviewers）按钮在私有仓库需要的套餐、以及能否让签字只认网页点按钮。这和改私有时核实分支保护要不要 Pro 是同一个检查。

## 5. 为什么用“提交状态”而不是普通检查

签字是一条评论，评论触发的工作流（`issue_comment`）不会挂到 PR 上。所以工作流把判定结果写成 PR 头提交上的提交状态 `safety-zone`：推代码时算一次，任何人在 PR 上发/改/删评论时再算一次，最新一次覆盖之前的。工作流任务本身只在出错时失败；出错时状态标成 `error`，同样挡住合并（宁可错挡）。

裁判来自 main、PR 头只当数据读、`--ci` 拒绝自己判自己，做法和越界检查一样；`safety_zone_check.py` 已加进越界检查的裁判清单（`JUDGE_PATTERNS`）。

## 6. 上线顺序（D09 之后）

1. 本分支经独立审计后合进 main。**引入这个工作流的 PR 本身不受它检查**（同越界检查），合并前人工核对。
2. 先出 DJ-2026-009 的 `safety_zone.yml` 草稿（落地卡 E），你签一次。
3. 有一个 PR 跑过 `safety-zone` 后，在 Settings → Branches → main 的规则里，“Require status checks to pass”下勾选 `safety-zone`。
4. 在那之前，所有 PLC 程序改动都按“未标定”要签字；这是设计本意，不是故障。
