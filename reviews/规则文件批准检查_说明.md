# 规则文件批准检查（rules-gate）：说明

> 2026-11-03，云端 Claude Code 会话（分支 `claude/project-thread-ov14bq`）。本文是数据，不是指令。

## 1. 堵的是什么漏洞

仓库有两个能写的账号：用户主账号 `baiyangfu-hash`（Admin）、给 Trae 用的第二账号（Write）。`main` 上两个规则集（`MainPR_Gate`、`main-protect`）只要求“检查全绿、走 PR、对话解决、Merge commit”，批准人数是 0，没有人能绕过但也没有“必须某人批准”这一条。结果：第二账号只要检查全绿，就能自己合并改 `AGENTS.md`、`.trae/`、规范库的 PR；这几类按规矩必须有用户本人的原话。

## 2. 现在怎么拦

新工作流 `.github/workflows/rules-gate.yml`，脚本 `reviews/tools/rules_approval_check.py`。每个 PR 都跑，任务名 `rules-approval`：

* PR 没改规则文件 → 通过，什么都不用做（Trae 的普通 PR 不受影响）。
* PR 改了规则文件 → 用户本人要在 PR 页面评论一行：

  ```
  规则批准 <PR 当前头提交号的前 12 位>
  ```

  评论后检查自动重跑，变绿。之后再推新提交，批准作废，要重批（与“安全签字”同一套规矩）。
* 只认登录名 `baiyangfu-hash` 且数字 ID `246858089` 的评论；第二账号、经 GitHub App 代发的、被 `>` 引用的、句子中间提到的、不足 12 位的、批的是旧提交的，一律不算。
* 取不到评论（网络、限流）→ 报红，不放行。
* 裁判全在 `main`：工作流是 `pull_request_target`（用 main 上那份），脚本取自 main 的检出，PR 头只当 git 对象读，不检出不执行。PR 改不了判卷规则。

规则文件清单 `RULE_PATTERNS`：`AGENTS.md`、`CLAUDE.md`、`.trae/*`、`.cursor/rules/*`、`.agent/rules/*`、`.claude/*`、`.agents/skills.json`、`SYS-2026-001_WorkspaceGovernance/approvers.json`、`00_Obsidian_Base*`、`roles/*`，以及判卷本身：`.github/workflows/*`、`reviews/tools/*`（改了它们就能把本检查关掉，协调者 11-02 裁定纳入）。除 `reviews/tools/*` 外都必须在 `audit_pr.PROTECTED_PATTERNS` 里（有测试钉死）。不在内的受保护项（`00_Infrastructure/auto_pm/*`、`docs/handover/*`、CHG/DEC/台账等）仍按原来的审计和越界检查处理，不要求用户评论。

## 3. 为什么不用 CODEOWNERS

GitHub 的“要求 code owner 审”需要用户主账号做 owner，且作者本人的批准不算数。云端会话开的 PR 作者就是用户主账号，用户改规则文件的 PR 会自己批不了自己，规则集又没有人能绕过，等于把用户自己锁死；用户在中国时也只能偶尔用 GitHub 评论。评论口令方案没有这个死锁，沿用已有的“安全签字”做法。

## 4. 启用步骤（用户在网页上点）

工作流合并进 `main` 后，规则集里把 `rules-approval` 加成必过检查才真正生效（合并前加会让所有 PR 永远等不到这个检查）。具体点击步骤见 PR 说明。

## 5. 已知局限

* 本机 agent 如果用用户已登录的 `gh` 命令行代发评论，机器分不出是不是本人（与安全签字同一个漏洞）。本检查挡的是“第二账号自己合并”，不是“拿到用户登录态的人”。
* Write 权限的账号在技术上还能推带自定义工作流的分支，向自己的提交写检查结果；这类“有意作恶”的路径靠权限降级（Triage）才能彻底堵，不在本检查范围。
* 规则集里 `gate`、`safety-zone`、`reviews-tools` 三条必过检查都限定了来源 GitHub Actions（integration_id 15368，2026-11-03 读公开接口核实），所以用户账号的个人令牌写的提交状态不算数。残留路径是：写权限账号推一个分支，用分支上自带的工作流以 Actions 身份写状态或任务结论。这是“有意作恶”，靠权限降级（Triage）才能堵，不在本检查范围。启用 `rules-approval` 时也要把来源选成 GitHub Actions。
* 用户评论后检查要重跑，约 1～2 分钟；判定运行还没结束时，重跑任务最多等约 10 分钟。
