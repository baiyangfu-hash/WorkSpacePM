## 挡住合并的两处

### 1. “要你点头”那一类少了“删除或改名已入库的文件”

- 卡第 23、30 行列的“要你点头”只有：PLC 项目文件和 PLC 模板、安全回路、规则文件、本机合并命令和钩子、发版切换。
- 用户看过的减肥方案第三节 A（第 47 行）和 GitHub 按需方案第 39 行，都把“删除或改名业务文件”列在“要你点头”里。
- 现行 AGENTS.md FLOW-001 也把删除、改名已入库的文件归在全流程。

照卡改完，删除、改名已入库的业务文件就成了“直接做，事后告诉你”。这比用户看过的方案松。

建议：卡第 23、30 行补上“删除或改名已入库的业务文件”。本机合并命令的“要你点头”判定也照这个查。

### 2. “要你点头”那一类合并前，少了用户本人对这次改动点的那一下

- **方案写的**：GitHub 按需方案第三节第 3 条要求，账本里要有用户在看板点的“确认验收”记录，而且对应的就是这个分支的这次提交。
- **卡写的**：第 19 行只要求“提交说明里引用的变更单至少一张已被用户批准（状态是已批准或之后）”。
- **两个后果**：
  - 现在合规则文件要用户在 GitHub 点一次“规则批准”，照卡改完，用户在合并前就不用对这次改动的内容点任何东西了；
  - “至少一张已批准的变更单”没有绑到这张卡上。账本里有 218 张停在“已批准”的旧单（减肥方案第 23 行），引用任何一张都能过。

建议改成：“要你点头”那一类，合并前要满足两条：
- 引用的变更单就是这张卡的单（卡头或占位里登记的那张）；
- 账本里有用户本人对这个分支头提交的确认（看板“确认验收”记录，或用户在主对话里说的、带头提交号的那句话）。

如果作者认为这是有意收窄，也可以在卡里写明，并在本机主对话里点名问用户一句：“合规则文件、PLC 这类改动，合并前不再要你点一下，只看变更单批过，可以吗？”用户同意再保持现状。
