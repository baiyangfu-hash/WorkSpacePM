## 结论

**建议的核心原则：由唯一的“台账主机”（本地 Claude）分配编号、写台账；其他写入者只交建议文件和 PR，合并后由台账主机补登。** 这与项目记忆里用户 2026-10-16 的裁决一致：靠单一写入者的角色分工避免冲突，不做“先到先得、合并时拒绝”的自动合并。在这个原则下，大部分热点文件不需要改格式；真正需要动的只有 WBS（单文件太大）和地盘检查。

## 1. 变更单编号

### 方案一（推荐）：唯一取号者，格式不变

- 只有台账主机执行 `next_change_number`。云端 Claude、项目 Claude 和以后的协作者在 PR 描述和建议文件里写 `CHG-PENDING-<短主题>`，**不自己取号**；
- 合并时由台账主机取号，写变更单，并把号回填到 PR 评论里；
- 好处：现有 6 处以上按 `CHG-[A-Z]+-\d{4}-\d{3}` 写死的正则（`contracts/intake.py:89,92`、`contracts/decision_package.py:19`、`application/core/pm_resume_service.py:176`、`application/core/ai_handoff_service.py:1022` 等）一个都不用改，历史编号也不用动；
- 代价：外部写入者在合并前拿不到正式编号。对现在的协作规模来说可以接受。

### 方案二（以后多人时再用）：带写入者后缀

参照 Decision ID 的做法（`DEC-YYYYMMDD-` 加 8 位，`domain/change/decision_service.py:70` 用的是 uuid4 的前 8 位，`continuity_store.py:1465` 用的是内容哈希），格式改为 `CHG-<DOMAIN>-<YYYY>-<NNN>` 后面再加 `-<WRITER4>`，`WRITER4` 是写入者的 4 位登记码（例如 `LOC1`、`PRJ1`、`CLD1`）：

- 旧编号保留原样、不改写；新旧两种格式并存；
- 上面所有正则都要改成接受可选后缀 `(?:-[A-Z0-9]{4})?`，并新增测试：新旧格式都能匹配，且 `CHG-SCPT-2026-421` 与 `CHG-SCPT-2026-421-PRJ1` 被识别为两个不同的编号；
- 取号时只在“自己的后缀”范围内取下一个号，所以不同写入者之间不会撞号；
- 这是核心档改动（契约正则、意图解析），比方案一大得多。

### 跨项目同号（两种方案都要处理）

变更单编号本来就是按项目分配的，所以“编号全局唯一”从来不成立。凡是只凭编号查找变更单的地方（例如 `pm_resume_service.py:176` 从文本里抽取 `CHG-…`），都应当把项目编号一起作为键。建议先写一个只读检查，列出所有跨项目重号的编号，确认这些查找位置是否都限定在本项目目录内，再决定要不要改。

## 2. 台账：只追加 + `merge=union`

- 规则：两本版本变更台账和技术债台账**只在表尾追加新行**，不改历史行；更正写成新的一行“更正：……”；
- 在 `.gitattributes` 追加三行（现有文件只设置了换行符）：

```gitattributes
**/04_监控/01_变更管理/02_变更记录/01_版本变更台账.md merge=union
**/04_监控/02_整改项/活动技术债台账.md merge=union
```

  `union` 合并时会保留双方新增的行，两个分支各自追加的内容不再冲突。限制：如果两边都改了同一行，`union` 会把两个版本都保留下来，所以“只追加”这条规则是前提；
- 加一个只读检查（可以放进 `sw008-ci`）：对这些文件，`git diff base..HEAD` 里只允许出现 `+` 行，出现 `-` 行就失败。在过渡期，这个检查只对非台账主机的分支前缀生效；
- 不建议“一条一个文件”：现有工具（台账更新器 `<SW008>/auto_pm/domain/change/ledger_updater.py`）按单表读写，改成目录需要重写读写逻辑和所有引用；只追加加 `union` 用三行配置就能解决冲突。

## 3. WBS 按卡拆分

现在 1912 行、408 KB 的单个文件，每张卡收口都要改，是最大的冲突源，读起来也慢（每次加载要 40 万字节）。

- **新结构**：`SYS-2026-001_…/01_项目文档/wbs/` 下每张卡或每个任务行一个文件，例如 `wbs/M3/M3-COLLAB.md`，文件开头用 YAML 头写机读字段（`id`、`milestone`、`status`、`depends_on`、`card`、`chg`、`decision`），下面是正文；
- **投影**：脚本 `tools/wbs_project.py` 读取 `wbs/**`，生成 `39_…WBS_PM.md` 里的总表段落，并用 `<!-- BEGIN GENERATED --> … <!-- END GENERATED -->` 标出生成区；生成区以外的叙述段落（裁决记录、顺序说明）保持手写；
- **门禁**：CI 里运行 `wbs_project.py --verify`，按 AGENTS.md 第 8 条“验证与生成隔离”的要求，`--verify` 只读：先在内存里生成，再和已提交的文件逐字节比较，不写文件；
- **迁移**：分两步，第一步只把总表的行拆出去，并证明投影结果与现在的表逐字节一致（这一步就是验收标准）；第二步才让新卡只写 `wbs/` 下的文件。历史叙述段落不搬；
- 依赖关系（例如“D03 依赖 V04-R1”这类缺口）放在 `depends_on` 字段里，投影脚本可以顺便检查引用的任务是否存在、有没有环。

## 4. 外部 PR 的固定格式与合并后补登

### PR 描述模板（建议放仓库根目录的 `.github/pull_request_template.md`）

仓库根目录现在没有 PR 模板。`<SW008>/.github/pull_request_template.md` 在子目录里，GitHub 不会读取它。

```markdown
## 来源
写入者：<project|cloud|local> · 分支：<prefix>/<name> · 基点：<sha>

## 内容
<一段话>

## 建议的治理登记（由台账主机在合并后补登）
- 档次：<docs|product|core>
- 变更单：CHG-PENDING-<短主题>
- 涉及路径：<列表>
- 需要的 Decision：<无 | 说明>

## 自检
- [ ] 只改了本前缀允许的路径
- [ ] 本地检查结果：<命令和退出码>
```

### 最小补登流程（台账主机执行）

1. 读 PR，确认 `sw008-ci` 通过且地盘检查通过；
2. 取号：`main.py` 现有入口生成变更单（方案一）；
3. 在本机创建 Work、Decision，`approved_files` = PR 的文件集合，`git_head` = 合并后的提交；
4. 合并 PR（快进或合并提交，不用 squash，理由同 02）；
5. 追加台账行，在 PR 上评论回填变更单号和 Decision 编号；
6. 执行 `main.py ledger reconcile <PID>`。

由于 Decision 绑定的是合并后的提交，“先合并、后补登”不会让 Decision 指向一个不存在的提交。

## 5. 地盘划分与越界检查

### 建议写进 `AGENTS.md` 的表（经 AGENTS 修订卡落账）

| 分支前缀 | 写入者 | 允许的路径 | 禁止 |
|---|---|---|---|
| `codex/*` | 本地 Claude（台账主机） | 全部，受现有分档与 Decision 约束 | — |
| `project/*` | 项目 Claude | `reviews/**`，以及经 PR 明确提出的产品、测试路径 | `main`、`codex/*`；`AGENTS.md`、`00_Obsidian_Base…/**`、`00_Infrastructure/auto_pm/**`、`.auto-pm/**`、`.github/workflows/**`、`**/CHG-*`、`**/DEC-*`、WBS、台账 |
| `claude/*` | 云端 Claude | 同 `project/*` | 同上 |
| `main` | 只接受快进或 PR 合并 | — | 直接推送（开启分支保护以后） |

### 检查办法（两层）

1. **CI 层（推荐先做）**：在 `sw008-ci` 加一步，读取一份机读的地盘表（例如 `.github/territory.json`，内容与上表一致），对 `github.ref_name` 的前缀，检查 `git diff --name-only <base>..HEAD` 里的每个路径是否允许；基线取法与 01 的秘密扫描相同。注意：`sw008-ci` 有 `paths` 过滤，只改 `reviews/` 的推送不会触发它，所以这一步要放进一个**没有 paths 过滤**的独立小工作流，否则正好漏掉最常见的情形。这个小工作流也就是 01 里提到的“永远运行的汇总检查”，可以作为将来分支保护的必需检查；
2. **本地 Hook 层（可选）**：`pre-push` 钩子运行同一个脚本，提前拒绝越界推送。Hook 可以被跳过，所以只是方便，CI 才是门禁。
3. 地盘表本身属于核心档文件，只有台账主机能改。

## 建议的拆卡顺序

1. 地盘检查小工作流（最便宜，立刻减少越界风险）；
2. 台账的 `merge=union` 和只追加检查；
3. 变更单方案一（主要是写进 AGENTS.md 和 PR 模板，代码不改）；
4. WBS 拆分（工作量最大，第一步以逐字节一致为验收标准）。
