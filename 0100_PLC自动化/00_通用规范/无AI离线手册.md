# 无 AI 离线手册（电气 / PLC 人工路线）

> 2026-10-22 建。适用：没有 AI、没有网络，用户本人兼项目经理和电气工程师，要照常改 PLC 程序、做检查、留变更记录。
> 依据：用户 2026-10-22 硬要求“至少要保证电气 PLC 相关的离开 AI 我也能离线用”。
> 本文是操作说明，每一步按四要素写：**哪台电脑 / 哪个窗口 / 点什么或敲什么 / 做完看到什么**。

## 0. 一句话结论

改程序（InoProShop 或博图）→ 同步到仓库的 `.scl` → 跑 `plc check` → 在业务变更记录里记一行 → 本机 Git 提交 → 有网再推、开 PR。
这条路断网能走，**只有第 5 步“提交”今天会被提交检查挡住**，第 5 节写了原因、临时办法和修复计划。

## 1. 有网、有 AI 时先做好的准备（只做一次）

| # | 哪台电脑 | 哪个窗口 | 做什么 | 做完看到什么 |
|---|---|---|---|---|
| 1 | 用户笔记本 | 资源管理器打开 `C:\Users\fubai\Documents\My_Workspace`，地址栏输入 `cmd` 回车，弹出“命令提示符” | 敲 `.venv\Scripts\python.exe main.py plc check DJ-2026-009` | 第一行 `launcher: release verified …1.3.3-a4506c3`，最后一行 `Pass=… Warn=… Fail=…`。能出这一行就说明环境齐了，断网也能跑（依赖全在 `.venv` 里，不联网） |
| 2 | 同上 | 同一个命令提示符 | 敲 `git fetch origin`，再敲 `git worktree add -b manual/start .auto-pm\worktrees\manual origin/main` | 出现 `Preparing worktree`，文件夹 `.auto-pm\worktrees\manual` 出现。这是你自己的“人工工位”，跟 AI 的工位分开，不碰控制根的分支 |
| 3 | 同上 | VS Code | 确认已装 “Dynamic Siemens Language Support” 插件（可选） | 装了：`plc check` 会多一行 “Siemens 语言服务 check” 结果；没装：这一行是 WARN“未验证”，不影响其他检查 |

> 为什么要人工工位：控制根停在本机专用分支上，有几个故意不推的本地提交。在控制根里直接改、直接推，会把这些提交一起推上去。人工工位从 `origin/main` 起步，推上去只有你这次的改动。

## 2. 人工路线（断网可走）

以下全部在**用户笔记本**上做。“命令提示符”都指在 `C:\Users\fubai\Documents\My_Workspace` 里打开的那个（第 1 节第 1 步的方法）。下文 `<工位>` 一律写全路径 `C:\Users\fubai\Documents\My_Workspace\.auto-pm\worktrees\manual`（实测：旧版发布用相对路径会报“项目不存在”，写全路径两版都对）。

### 第 1 步：开一个本次改动的分支

| 窗口 | 敲什么 | 看到什么 |
|---|---|---|
| 命令提示符 | `cd /d <工位>`，再 `git switch -c manual/2026-11-10-feed-timeout origin/main`（日期和主题换成本次的；分支名只用英文、数字和短横线，命令提示符里不易出乱码） | `Switched to a new branch 'manual/…'` |

### 第 2 步：改程序

| 软件 | 做什么 | 看到什么 |
|---|---|---|
| InoProShop（汇川，009）或博图（西门子） | 照常在工程里改、编译 | 编译 0 错误。**编译是否通过只认 InoProShop / 博图本身**，仓库检查不替代编译 |
| VS Code 或记事本 | 把改过的那个 POU / FB 的 ST 文本同步到工位里对应的 `.scl` 文件（也可以反过来：先改 `.scl`，再粘进 InoProShop） | `git status` 里出现这个 `.scl`。**仓库里的 `.scl` 是真源**，两边必须一致 |

### 第 3 步：跑检查

| 窗口 | 敲什么 | 看到什么 |
|---|---|---|
| 命令提示符（先 `cd /d C:\Users\fubai\Documents\My_Workspace` 回控制根） | `.venv\Scripts\python.exe main.py -w <工位> plc check DJ-2026-009` | 最后一行 `Pass=… Warn=… Fail=0 -> …`。有 FAIL 时退出码 1，表里 FAIL 那一行写了哪个文件哪一行 |
| 同上 | `.venv\Scripts\python.exe main.py -w <工位> plc docs check DJ-2026-009` | 最后一行 `拦住项 0、警告 …、待确认 0`。拦住项不为 0，说明接口文档 / 变量定义文档和代码对不上，提交时会被挡 |

改了 FB 的引脚或注释时，可用 `plc docs sync DJ-2026-009`（同样带 `-w <工位>`）按代码补文档，补的行带“【待确认】”；核对后跑 `plc docs confirm DJ-2026-009` 去掉标记。

### 第 4 步：在业务变更记录里记一行

| 软件 | 打开哪个文件 | 写什么 |
|---|---|---|
| VS Code 或记事本 | `<工位>\0100_PLC自动化\DJ-2026-009_汇川换型改造\11_监控\01_变更管理\02_变更记录\02_业务变更记录.md` | 在表末加一行，规矩见下 |

- **编号**按提出时间：`BC-<项目号>-<年>_<月>_<序号>`，例如 `BC-DJ-2026-009-2026_10_000` 是 009 在 2026 年 10 月提出的第一条；序号每月从 000 起，项目内不重复。年月取对方**提出**的时间。2026-10-22 前的旧号（`BC-DJ-2026-009-001`～`004`）不改。
- **提出时间**写到分钟和渠道：`2026-11-10 09:30（电话）`。
- 状态：你自己当场批的写“已批”，改完、试过写“已实施”；“关联 CHG / 提交”栏等第 5 步出了提交号再填。
- 需求核对单 `REQ-<项目号>-<年>_<月>_<序号>` 是给 AI 用的确认单，断网人工路线可以不写；写的话和 BC 用同一个号。
- 抄一行示例：

```
| BC-DJ-2026-009-2026_11_000 | 2026-11-10 09:30（电话） | 张工（3Sun 设备科） | 参数 | 工位1 进料超时 10 s → 15 s（FB_1001 STEP_FEEDING） | 来料慢，10 s 误报 | FB_1001；不涉及安全区 | baiyang | 2026-11-10 | 已实施 | 待补 |
```

### 第 5 步：本机 Git 提交

| 窗口 | 敲什么 | 看到什么 |
|---|---|---|
| 命令提示符，`cd /d <工位>` | `git add -A`，再 `git status` | 绿色列出本次改的 `.scl` 和 `02_业务变更记录.md`，没有别的文件 |
| 同上 | 见下方“今天怎么提交” | 出现 `[manual/… 1a2b3c4] …`，这串字母数字就是提交号 |
| 同上 | `git log --oneline -3` | 最上面一行是刚才的提交 |

提交号填回第 4 步那一行的“关联 CHG / 提交”栏，再 `git add -A` 和 `git commit -m "docs(DJ-2026-009): BC-DJ-2026-009-2026_11_000 补提交号"`（纯文档提交，检查不挡）。

**今天怎么提交**：见第 5 节。修复卡合并之前，提交 `.scl` 用：

```
git commit --no-verify -m "[离线人工] DJ-2026-009 工位1进料超时10s改15s（BC-DJ-2026-009-2026_11_000）"
```

**`--no-verify` 只限用户本人在断网人工路线里用；任何 AI（Claude、Trae、Codex 等）都不得用，AI 提交被挡就停下来报告。**

### 第 6 步：有网之后

| 窗口 | 敲什么 | 看到什么 |
|---|---|---|
| 命令提示符，`cd /d <工位>` | `git push -u origin manual/2026-11-10-feed-timeout` | `branch 'manual/…' set up to track …`。断网时敲这句会报 `unable to access …` 一类的错，什么也不会坏，有网再敲 |
| 浏览器 GitHub 仓库页 | 顶部黄条 “Compare & pull request” → 点它 → “Create pull request” | 出现 PR 页面，CI 开始跑。AI 回来后补跑提交检查、审计，再合并 main |

## 3. 安全区：仍要你本人仿真和签字

急停、安全门、光栅、联锁（含只靠软件的防撞联锁）、安全继电器、双手启动的逻辑，断网时也可以改，但：

1. 必须先仿真：西门子用虚拟机里的 PLCSIM，汇川用 InoProShop 仿真。
2. 第 4 步那一行“影响”栏写“安全区，待签字”。
3. 有网后补开 CHG 变更单（安全相关照旧要 CHG），并在 PR 上写“安全签字 + 提交号”，签字前不合并 main。
4. 出现 `OR TRUE` 旁路、安全点漏接，直接判不合格。

## 4. 不要做的事

- 不在控制根 `C:\Users\fubai\Documents\My_Workspace` 本身的分支上改程序、提交、推送（会带出本地专用提交）。
- 不直接推 `main`（分支保护也会拒绝），一律推 `manual/` 分支再开 PR。
- 不删文件、不删分支；想撤销一个文件的改动用 `git restore <文件>`。
- 第二台电脑（虚拟机，`C:\WSPM`）跑的是旧版 1.3.3-d8f7c8b，没有文档一致性检查，**以笔记本的结果为准**。

## 5. 今天会挡住提交的两处（已实测）及修复计划

笔记本控制根装了提交检查（`.git\hooks\pre-commit`、`commit-msg`，2026-10-22 核对存在）。在断网沙箱里照原样装上钩子，提交一行 009 的 `.scl` 改动，结果：

| # | 哪一道 | 实测提示 | 原因 | 修复 |
|---|---|---|---|---|
| ① | `commit-msg` | `物理拦截：检测到暂存区包含生产代码变更，但 Commit Message 未绑定变更单！` | 任何 `.scl`/`.st`/`.py` 提交都要一张状态为已批或实施中的 CHG。和 10-19 瘦身定的“CHG 只在发版、安全相关时开，日常靠 BC”不一致 | 修复卡 A：提交说明里写一条本项目“已批”的 BC（新旧编号都认）也放行；发版、安全区仍要 CHG。D09 后合并 |
| ② | `pre-commit` | `物理阻断：PLC 项目 …DJ-2026-009_汇川换型改造 的文档与代码不一致（拦住项 56…）` | 009 的接口文档 / 变量定义文档和代码本来就有 56 处对不上，改一行也被挡；钩子还会顺手往工作区写补全的文档 | 修复卡 B：把 009 文档按代码对齐，`plc docs check DJ-2026-009` 拦住项归 0 |
| 附 | 绕行开 CHG | `change create` 在 009 上提示 `台帐更新失败: 未找到变更单索引表格`，再提交仍被拦“缺少或重复关联项目台账” | 009 的 `01_版本变更台账.md` 是旧格式，命令认不出 | 并入修复卡 A 的同类排查清单 |

两张卡合并之前：`.scl` 提交加 `--no-verify`，只提交到 `manual/` 分支，说明里写 `[离线人工]`。main 仍只走 PR + CI，有网后由 AI 补跑检查再合并，所以检查只是往后推，没有取消。合并之后：去掉 `--no-verify`，提交说明里写 BC 号即可。

**`--no-verify` 只限用户本人在断网人工路线里用；任何 AI（Claude、Trae、Codex 等）都不得用，AI 提交被挡就停下来报告。**

## 6. 断网演练：在 DJ-2026-009 上改一个小点（D09 后做）

- **前置**：修复卡 A、B 已合并并切换发布；人工工位已建好（第 1 节第 2 步）。
- **时长**：约 30 分钟，用户一人；演练是轻活，不受 17:00～21:00 MST 重载禁跑的限制。
- **改哪一点**：工位 1 进料超时 10 s → 15 s，`FB_1001_Station1.scl` 的 `STEP_FEEDING` 里 `s_tStepTimer.PT := 10000;`（不在安全区）。演练前如果这一行被别的卡改过，换同块里另一个超时常数。共享库计时器改真实毫秒的分支合并前，`PT` 写 15000 不一定是 15 s；演练只验证流程，最好排在计时器分支合并之后。

| 步 | 做什么 | 判过 |
|---|---|---|
| 1 | 笔记本拔网线、关 Wi-Fi；不开 Claude、Trae 或任何 AI | 浏览器打不开 github.com |
| 2 | 第 2 节第 1 步开分支 `manual/<日期>-drill-feed-timeout` | `git branch --show-current` 显示这个名字 |
| 3 | 第 2 步：在 InoProShop 里改、编译；同步到 `.scl` | InoProShop 0 错误；`git diff` 只有这一行 |
| 4 | 第 3 步：`plc check`、`plc docs check` | `Fail=0`；拦住项 0 |
| 5 | 第 4 步：记一行 BC（用当月编号，提出时间写到分钟，提出人写“演练”） | 编号格式对、状态“已实施” |
| 6 | 第 5 步：**不加** `--no-verify` 提交，说明里写 BC 号 | 两道检查都显示 ✅，出现提交号 |
| 7 | 故意做错一次：再改一行不记 BC、说明里不写 BC 号，提交 | 被 `commit-msg` 挡住（证明检查还在） → `git restore` 撤销 |
| 8 | 接回网络，第 6 步推分支、开 PR | PR 页面 CI 绿 |
| 9 | 演练分支不合并：PR 写“演练，关闭不合并”，关掉 PR | 删分支前按规矩先问用户 |

演练结果写进 `reviews/`，挡住 / 没挡住的地方按缺陷开卡。本演练和瘦身评估里“驾驶舱停用退回纯 Git + 文件夹”演练合并做。

## 7. 本文命令的实测记录

2026-10-22，云端 Linux 沙箱，用 `unshare -rn` 切断网络后执行（等同拔网线）；Python 依赖按 `requirements-lock-py312-win.txt` 预装。笔记本跑的发布 1.3.3-a4506c3 由 main `a4506c3` 的源码构建（2026-10-22 核对笔记本 `active_release.json`），沙箱直接跑同一份源码；钩子按笔记本 `.git\hooks\pre-commit` 的写法（工作区 = 工位，控制根 = 主克隆）装进沙箱。Windows 写法（`.venv\Scripts\python.exe`、`cd /d`）没有在 Windows 上实跑，留给第 6 节演练核对。

| 命令 | 断网结果 |
|---|---|
| `main.py plc check DJ-2026-009`（main 上的旧发布 1.3.3-d8f7c8b） | 通过：`Pass=45 Warn=0 Fail=0 -> ALL PASS`，退出码 0 |
| 同上，1.3.3-a4506c3 源码 | 能跑：`Pass=45 Warn=11 Fail=3 -> HAS FAIL`，退出码 1。3 个 FAIL 都是文档一致性（即第 5 节②）；“Siemens 语言服务”WARN 未验证（沙箱没装插件） |
| `main.py -w <工位绝对路径> plc check DJ-2026-009` | 能跑，检查的是工位里的文件（在工位里删一份文档，FAIL 从 3 变 4）。旧发布用相对路径报“项目不存在”，所以本文一律写全路径 |
| `plc docs check DJ-2026-009` | 能跑：`拦住项 56、警告 10、待确认 0`，退出码 1 |
| `git worktree add` / `git switch -c` / `git add` / `git status` / `git log` / `git diff` | 正常，不需要网络 |
| 带钩子 `git commit`（`.scl` 改动） | 被挡，提示见第 5 节①② |
| `git commit --no-verify` | 成功，生成提交 |
| 只改 `02_业务变更记录.md` 的 `git commit` | 成功，钩子放行（纯文档提交不要求 CHG） |
| `git push` | 失败，`unable to access …`，本地提交不受影响 |
