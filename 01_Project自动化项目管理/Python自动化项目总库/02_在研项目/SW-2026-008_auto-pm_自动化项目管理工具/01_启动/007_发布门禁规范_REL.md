# 发布门禁规范

> 本文件定义 auto-pm (SW-2026-008) 每次发布（内部试运行 / 候选版 / 正式版）前必须通过的质量门禁。
> 任何门禁项未通过，禁止升级版本号、禁止打 tag、禁止对外发布。

## 1. 门禁项定义

发布前必须全部通过以下 5 项门禁：

| 编号 | 门禁项 | 工具 | 通过标准 | 失败处理 |
|------|--------|------|----------|----------|
| G1 | 代码静态检查 | `ruff check .` | `All checks passed!`（0 errors） | 修复后重新提交 |
| G2 | 类型检查 | `mypy auto_pm` | `Success: no issues found`（0 errors） | 修复后重新提交 |
| G3 | 全量测试 | `pytest --no-cov --timeout=60` | 全部 passed（允许 6 skipped 可见演示模式） | 定位失败用例并修复 |
| G4 | 元测试 | `pytest tests/test_fixture_health.py` | 0 violations + FAIL 级别（非 WARN） | 修复 fixture 缺陷 |
| G5 | Dogfooding 闭环 | `auto-pm change list SW-2026-008` | 本里程碑有至少 1 条 CHG-*.md 走完 draft→closed 完整生命周期 | 补创建 CHG 并走完流程 |

## 2. 触发条件

### 2.1 必须执行门禁的场景

| 场景 | 触发时机 | 执行者 |
|------|----------|--------|
| 内部试运行版 | 每个里程碑（M0/M1/M2/M3/M4）完成时 | 项目负责人 |
| 候选发布版（RC） | pyproject.toml 版本号变更时 | 项目负责人 |
| 正式发布版 | 打 git tag 时 | 项目负责人 |
| CI 流水线 | push 到 main / PR 合并时（V2.5 启用） | CI 系统 |

### 2.2 不需要执行门禁的场景

- 本地开发提交（commit）
- 临时分支调试
- 文档-only 变更（仅 .md 文件，无 .py 文件改动）

## 3. 门禁执行流程

### 3.1 标准执行顺序

```powershell
# 0. 激活虚拟环境（必须）
& "<工作空间根>\.venv\Scripts\Activate.ps1"
cd "<项目根>"

# 1. G1 代码静态检查
ruff check .
# 期望: All checks passed!

# 2. G2 类型检查
mypy auto_pm
# 期望: Success: no issues found in <N> source files

# 3. G3 全量测试（不带 coverage，避免性能损耗）
python -m pytest --no-cov --timeout=60 -q
# 期望: <N> passed, 6 skipped

# 4. G4 元测试（G3 已包含，可单独验证）
python -m pytest tests/test_fixture_health.py -v
# 期望: 2 passed, 0 violations

# 5. G5 Dogfooding 闭环
python -m auto_pm -w "<工作空间根>" change list SW-2026-008
# 期望: 本里程碑至少 1 条 CHG-*.md 状态为 closed
```

### 3.2 门禁结果记录

每次门禁的原始结果与审查依据落在本次有效治理合同指定的 Checkpoint/验证证据及相关 CHG、Decision 记录中；`PM_SESSION` 已退役（用户 2026-10-10 裁决），不再承载门禁结果，也不替代原始证据或控制状态。发布、部署、切换与验收分别按各自有效授权判定。下面的记录格式仅作历史示例，可用于证据摘要：

```
- verified: G1 ruff 0 errors / G2 mypy 0 errors / G3 <N> passed / G4 0 violations / G5 CHG-XXX closed
- not_verified: 无
- method: ruff check . + mypy auto_pm + pytest --no-cov --timeout=60 + change list
- blocker: 无
```

## 4. 门禁失败处理

### 4.1 G1/G2 失败（静态检查/类型检查）

1. 修复所有 errors
2. 重新执行 G1/G2 直到通过
3. 不允许用 `# noqa` 或 `# type: ignore` 绕过（除非有明确合理的原因，需在代码注释中说明）

### 4.2 G3 失败（测试失败）

1. 用 `--tb=long` 获取完整 traceback
2. 按工作区根 `AGENTS.md` 与本次有效 Decision/Work 中的故障诊断步骤定位根因（不得调用或引用已退役的 `pm-workflow`）：
   - 先检查 fixture 是否完整
   - 再怀疑生产代码
   - 警惕"假通过"（条件断言跳过）
3. 修复后重新执行 G3

### 4.3 G4 失败（元测试 violation）

1. 元测试报告的 violation 都是 fixture 缺陷（缺项目标志文件/条件断言跳过）
2. 按 violation 描述修复 fixture
3. 不允许降级元测试为 WARN 级别（TD-T07 已升级为 FAIL）

### 4.4 G5 失败（无 Dogfooding 闭环）

1. 用 `auto-pm change create` 创建本里程碑的 CHG-*.md
2. 走完整 9 步状态流转：draft→submitted→under_review→approved→implementing→pending_acceptance→accepting→completed→closed
3. 每步用 `auto-pm change transition` 推进
4. 完成后重新执行 G5 验证

## 5. 版本号与门禁的关系

| 版本号变更类型 | 门禁要求 | 示例 |
|---------------|----------|------|
| PATCH（0.3.6→0.3.7） | G1-G5 全部通过 | Bug 修复、文档收口 |
| MINOR（0.3.7→0.4.0） | G1-G5 全部通过 + 新功能交付 | V2.2 规范中心整合 |
| MAJOR（0.x→1.0） | G1-G5 全部通过 + 全量文档同步 + 正式发布评审 | 1.0 正式发布 |

## 6. 例外与豁免

- **紧急修复（原条款范围保留）**：原版本仅允许申请 G5（Dogfooding）豁免，并在下一个版本补做；本条不授权其它门禁豁免。新发布是否允许该例外须按现行发布合同另行批准。对应治理记录和发布证据应明确记录“本次发布未走 Dogfooding 流程”、批准范围及责任人。
- **第三方库 warning**：G3 的 warnings 如果来自第三方库（如 jinja2 DeprecationWarning），不视为门禁失败，但应在技术债报告中记录。
