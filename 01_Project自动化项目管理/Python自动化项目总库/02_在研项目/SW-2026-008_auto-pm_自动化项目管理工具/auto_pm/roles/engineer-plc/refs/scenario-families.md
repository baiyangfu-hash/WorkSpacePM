# 设备 / 功能场景族与模板

## 设备 / 功能场景族

### 1. 双位置执行器

适用：

- 气缸
- 真空 / 破真空
- 夹具开闭
- 挡停 / 升降

默认维度：

- 动点 / 原点
- 得电动作 / 失电复位
- 极性映射
- 单传感器 / 缺失反馈
- 消抖 / 超时 / 冲突

### 2. 单动作执行器

适用：

- 点动输出
- 脉冲阀
- 单向机构

默认维度：

- 动作触发
- 动作保持
- 输出脉冲
- 完成判定
- 异常中止

### 3. 双向电机 / 变频器驱动

适用：

- 输送电机
- 双向滚筒
- 端子控制变频器
- 带方向输出和速度段修饰的电机执行器

默认维度：

- 正转 / 反转命令仲裁
- 慢速 / 高速修饰
- 运行输出与实际运行反馈区分
- VFD 故障输入与故障封锁
- 控制模式预留与未实现模式保护
- 停机默认态与方向互斥

### 4. 输送 / 节拍 / 上下游握手

适用：

- 来料 / 放料
- 到位 / 清空 / 占位
- 上下游允许 / 完成信号

默认维度：

- 上游请求
- 本位可接收 / 可放行
- 节拍同步
- 堵料 / 丢料 / 超时

### 5. 工艺步序 / 状态机

适用：

- 自动步序
- 多步骤工艺流程
- 子流程编排

默认维度：

- 步序定义
- 迁移条件
- 异常跳转
- 复位回零
- 手动介入

### 6. 报警 / 联锁 / 安全逻辑

适用：

- 设备互锁
- 故障锁存
- 报警聚合

默认维度：

- 触发条件
- 等级
- 锁存
- 复位
- 输出抑制

### 7. 服务型基础块

适用：

- 模式管理
- 报警管理
- 定时器封装
- 状态聚合

默认维度：

- 通用接口
- 跨项目稳定性
- 复用边界
- 配置驱动

## 双位置执行器场景模板（以 `FB_1011` 为基线）

当任务涉及气缸、真空阀、夹具或其他双位置执行器时，优先套用此模板。

### 1. 工艺抽象

- 动点命令
- 原点命令
- 动点到位
- 原点到位
- 得电动作
- 失电复位

禁止一开始就把语义锁死为“夹紧 / 松开”或“伸出 / 收回”。

### 2. FB 默认应覆盖

- 命令优先级
- 极性映射
- 传感器消抖
- 动作超时
- 反馈冲突
- 单传感器 / 缺失传感器
- 空闲态与安全态

### 3. 结构体默认应包含

1. 命令
2. 反馈
3. 参数
4. 输出 / 状态
5. 报警 / 故障

### 4. 审查输出要求

- 当前语义是专用气缸还是双位置执行器
- 结构体是否该共享
- 通用化是否损失现场可读性
- FB 是否覆盖关键工艺边界

## 双向电机 / VFD 场景模板（以 `FB_1012` 为基线）

当任务涉及输送电机、双向滚筒或端子控制 VFD 时，优先套用此模板。

### 1. 工艺抽象

- 正转命令
- 反转命令
- 速度修饰符
- 故障输入
- 运行请求输出
- 运行状态输出

### 2. FB 默认应覆盖

- 正反转互斥
- 命令优先级
- 慢速 / 高速修饰逻辑
- 故障最高优先级封锁
- 停机默认态
- 控制模式预留是否真正落地
- 预留参数是否会误导调用方

### 3. 结构体策略

对于简单输送电机执行器，优先先判断是否真的需要结构体：

- 若接口简单、字段少、场景稳定，可保持扁平接口
- 若多个电机 FB 共享稳定对象模型，再考虑抽象共享结构体
- 若控制模式、反馈、参数会快速演进，避免过早沉入全局 `types/`

### 4. 审查输出要求

- 当前是“简单执行器”还是“可扩展驱动器”
- `q_bRunning` 是命令派生状态还是实际反馈状态
- 预留模式 / 预留参数是否存在“接口声明了但逻辑没实现”的风险
- 文档是否明确职责边界：执行器只处理执行，不处理编排和安全互锁

## 工艺步序 / 状态机场景模板（按优先级基线）

当任务涉及 `CASE` 步序、自动/手动切换、子步骤、协议状态机或共享库级顺控时，优先按以下基线参考，而不是临时发明状态组织方式。

### 1. 优先级基线

- `A` 设备顺控母模板：`FB_1002_SingleLayerConveyor_BufferFraming`
- `A` 机构动作母模板：`FB_1003_PickPlace_BufferFraming`
- `A-` 共享库复杂顺控模板：`FB_1013_NinetyDegreeTransfer`
- `B+` 多模式输送站模板：`FB_1014_StationConveyor`
- `B` 协议状态机模板：`FB_1020_EquipmentHandshake`
- `C` 轻量交互模板：`FB_1004_GlueMachineFeeder_BufferFraming`

### 2. 状态机分类

先判断当前属于哪一种：

- 设备顺控状态机：单主 `CASE`、明确步号、`bStepEntry` 入口动作（参考 `FB_1002`）
- 机构动作状态机：步数不多，伴随轴控/气缸/超时/检测（参考 `FB_1003`）
- 共享库复杂顺控：多执行器聚合、报警分类更完整（参考 `FB_1013`）
- 主状态 + 子步骤：主 `CASE` + 子 `CASE`，模式差异大（参考 `FB_1014`）
- 协议状态机：通道独立、双 `CASE`、心跳/完成脉冲/通信故障（参考 `FB_1020`）
- 轻量交互状态机：少步数、设备协同明显（参考 `FB_1004`）

### 3. 设计骨架

设备步序状态机默认至少具备：

1. 状态变量
2. 步入口标志
3. 启动触发或启动锁存
4. 自动 / 手动分支
5. 停止 / 复位路径
6. 超时 / 故障路径
7. 最终回零或回空闲路径

### 4. 推荐写法

- 主状态机优先使用 `CASE iCurrentState OF`
- 有明显入口动作时优先使用 `bStepEntry`
- 步号常量优先集中在 `VAR CONSTANT`
- 自动与手动优先明确分支，不混写
- 子步骤只在确有必要时引入，避免每个小动作都独立成主状态
- 协议双通道场景优先分成两套独立状态机，而不是把上下游混成一个大 `CASE`

### 5. 验证清单

审查状态机时，至少检查：

- 是否存在非法状态回退到空闲的兜底
- 每一步是否有明确入口动作和迁移条件
- 停止 / 复位后是否清理输出、锁存、定时器
- 自动与手动切换是否会留下脏状态
- 报警后是冻结、回空闲还是允许继续
- 子步骤是否可能卡死
- 通信 / 协议状态机是否双通道对称
- 状态输出是否真实反映内部状态

### 6. 逻辑风险识别

状态机场景中优先识别以下风险：

- 启动信号只置位不复位，导致无法二次启动
- 定时器或锁存在异常回退后未清理
- 手动模式回到自动模式时残留状态
- 步迁移条件依赖多传感器同时满足，现场容错不足
- 协议状态机一侧复位后另一侧未同步收敛
- 子步骤缺少超时，导致卡死但不报警
