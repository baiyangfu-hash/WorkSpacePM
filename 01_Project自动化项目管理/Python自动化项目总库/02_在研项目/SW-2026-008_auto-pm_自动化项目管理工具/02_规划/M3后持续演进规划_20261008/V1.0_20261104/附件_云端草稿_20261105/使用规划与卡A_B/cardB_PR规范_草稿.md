# PR 与独立审计规范（卡 B 草稿，未入库）

> 本草稿以“汇总”为主（第 2A 节是用户 11-05 定的开 PR 口径，已写入使用规划 G-16）：把原来散在 `AGENTS.md`（AUD-001、FIX-001、WS-001）、`.github/pull_request_template.md`、`reviews/21_audit_checklist.md`、`reviews/tools/*.py`、`docs/handover/01` 里的 PR 规矩收成一份。**不新增任何规矩**。拿不准的条目标“未核实”，由 CHG-SPEC 评审时对源文件逐条核。
> 入库后：上面各文件改成“见 PR 与独立审计规范”一行指针，不再复述。

## 1. 角色
| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 用户 | 拍板、验收；安全签字、规则批准、删除/切换发布/规范库/`.trae/` 的同意 | — |
| 作者（一债一个会话） | 读代码、出计划、写代码和测试、开 PR | 不审自己的 PR，不合自己的 PR |
| 独立审计（另一个会话） | 跑 `audit_pr.py`，按审计清单逐项核，写报告，结论贴 PR 评论 | 不推被审分支，不删任何东西 |
| 合并（云端合并线程） | 审计过 + CI 全绿 + 评审对话全部解决，Merge commit | 不用 Squash/Rebase；安全区、`.trae/`、`AGENTS.md`、规范库的 PR 永远等用户 |
| 协调者 | 排期、盯线程、日报 | 不替用户拍板 |
做和审必须是不同会话。**合并者与作者不能是同一个会话**（协调者原为现行安排，2026-11-05 起升为规矩，随文档批次由用户最终拍板）。

## 2. 分支与工位
分支名 `<agent 前缀>/<主题>`，前缀与工位见 `AGENTS.md` WS-001 表；一个分支一件事；本机工位只从控制根 `git worktree` 派生，不另克隆。

## 2A. 怎么开 PR（统一走驾驶舱 PR 工作流；用户 2026-11-05 15:09Z 定：不加人工开 PR 入口）
1. **本地 agent**（Claude Code、Trae、Cursor、VS Code 里的 AI、将来的 Codex）一律在控制根执行 `main.py pr open <agent> <卡号> --task-card …`，不手工拼 PR，不另找入口。`<agent>` 必须是名册内名字（claude、trae、cursor、vscode、codex）。
2. **云端会话**（没有 `gh`、不占本机工位）用 GitHub 连接器开**草稿 PR**，正文照 `.github/pull_request_template.md` 的七栏写（署名、做了什么、可改范围、安全回路、证据、同类排查、关联 TD/WBS/建议回写），栏位名和顺序不改。
3. 不新增拦截：`gate`、`safety-zone`、`rules-approval` 对任何开法一视同仁，正文缺栏、越界、没有批准评论照样过不了；本节只约束“怎么开”，不改机器关。
4. 开 PR 之前按卡里的验收命令在驾驶舱跑完自检（PLC 卡先 `plc check`/`plc test`），证据写进“证据”栏。
5. 一条 PR 对应一张卡、一个分支；PR 开出后只改卡内可改范围，要加范围先在 PR 里写明再改。

## 3. PR 描述（字段以 `.github/pull_request_template.md` 为准）
署名；做了什么；可改范围（每行完整路径，锁定文件逐字写，目录前缀不算授权）；安全回路（`安全回路: 是|否` 单独一行）；证据（提交号/测试/门禁，拿不出写“未核实”）；同类排查（修缺陷的 PR 必填）；关联 TD；WBS；建议回写。
**PLC PR 另需**（必填，由脚本强制；用户要的“脚本强制”，随文档批次由用户最终拍板）：`驾驶舱记录: CHG-… / RUN-…`；`lsp_report` 摘要（plc check/plc test 退出码）。

## 4. 机器关（必过，不过不能合）
`gate`（越界）、`safety-zone`（碰安全区要用户本人对当前头提交的“安全签字”）、`rules-approval`（改规则文件要用户本人对当前头提交的“规则批准 <12 位>”）、`reviews-tools`（含严格 UTF-8 乱码扫描）、`plc-ci`（PLC）、`sw008-ci`（按路径）。新推送使旧的签字/批准失效。

## 5. 独立审计
`python reviews/tools/audit_pr.py <PR号>`：退出码 0 无 FAIL，1 至少一项 FAIL（不能合），2 用法/Git 出错；WARN 点名，UNVERIFIED 人工补查；再照 `reviews/21_audit_checklist.md` 人工逐项核；报告写 `reviews/`，推审计者自己的分支，结论贴 PR 评论，每段结论末尾一行 `放行判定: <头提交前8位> 过|有条件过|不过`。

## 6. 合并条件
审计通过、CI 全绿、评审对话全部解决，三条都满足；只用 Merge commit。

## 7. 做事硬要求（FIX-001）
1. 修缺陷先写根因，全库同类写法一次查全，清单写进 PR。
2. 样件联调查出的缺陷，本周活碰到就先修再用。
3. “完成”“可承诺”附证据，否则写“未核实”。
4. 提问前先查已定事项台账和用户给过的图纸手册。
5. 交给用户的操作写四要素：哪台电脑、哪个窗口、点什么或贴什么、完成后看到什么。

## 8. 回写
台账、WBS、治理库、发布指针只由账本主机上的主执行写；云端会话在 PR 里只写“建议回写”。
