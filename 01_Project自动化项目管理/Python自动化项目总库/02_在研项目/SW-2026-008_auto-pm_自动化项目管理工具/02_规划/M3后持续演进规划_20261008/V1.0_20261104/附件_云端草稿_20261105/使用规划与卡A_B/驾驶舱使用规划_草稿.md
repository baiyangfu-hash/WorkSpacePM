## 0. 一页结论

**为什么觉得散**：不是功能少，是有三套东西各自完整、互相不指路。

1. **入口有三层，但互不连通**：薄入口 `cockpit-entry`（进门定位）、`docs/handover/`（真正的“怎么干活”手册，16 份）、`AGENTS.md`（规则）。已核：`AGENTS.md`、`CLAUDE.md`、`.trae/`、`.cursor/`、`.agent/`、`roles/` 里**没有一处指向 `docs/handover/`**；`25_每天怎么走一遍与命令速查.md` 没有任何入口文件引用它。新 agent 进门读到的是定位，读不到流程。
2. **两条路线并存，没有一张图**：本地主执行走“任务→工单→租约→验收→收口”（`pm …`、`continuity …`），云端会话走“分支→PR→门禁→审计→合并→建议回写”（`pr …`、`reviews/tools`、CI）。`handover/90` 把它们的冲突列成待裁定，但没人画出“一件事从头到尾怎么走”。
3. **命令和文档里混着历史物**：195 条命令里 31 条是历史或别名（`handoff` 17、`workflow` 11、`pm-session` 3），还有几条能把人带进已挂起路径（见 §4）。

**建议的用法（一条脊柱，三个变体，用户只在“要你出手”页处理本人的事）**

- **脊柱**：进门 → 入箱 → 计划 → 批准 → 开工 → 写与自检 → 验证 → 提 PR → 审计与合并 → 验收与收口（§2）。每步只有一条“该用的命令”，本地路线和云端路线在第 4、8、10 步分叉并说清谁做。
- **三个变体**：PLC 任务、规范改动、发版，各自只写“和脊柱不一样的地方”（§3）。
- **用户只在驾驶舱“要你出手”页处理需要本人的事**：脊柱里标“要你出手”的步骤，以及三个变体里的亲口事，都集中在这一页处理；逐项清单（各场景、各自怎么完成、驾驶舱怎么提醒）见 GUI 方案（https://claude.ai/artifact/Q8YDVBWAo7XwMAZRfGNKS5）“需要你本人介入的场景”一节，本稿不重复。其余全是 agent 的事。

## 2. 脊柱：一个 agent 接一件事的完整流程

两条路线：**本地**＝用户笔记本上的主执行（写账本、跑插件、跑重门禁）；**云端**＝云端会话（作者、审计、合并，不写账本，只在 PR 里写“建议回写”，见 `handover/24`）。命令都在控制根跑，Trae 前面加 `pm-as-trae.ps1`。

| # | 步骤 | 命令 / 动作 | 谁 | 用户要做什么 |
|---|---|---|---|---|
| 1 | 进门定位（只读） | `git rev-parse --path-format=absolute --git-dir --git-common-dir`（两行相同）→ `project list` → `pm orient <PID> --json`（旧版报没有时用 `pm resume`）→ 中文报告焦点、Work/Run、`next_legal_action`、`conflicts` | 本地、云端 | 无 |
| 2 | 入箱 | `pm inbox add`（`--original-words` 照抄用户原话）→ 用户确认后 `pm inbox confirm` | 本地 | 说一句话需求；要你出手：确认入箱 |
| 3 | 出计划 | `pm plan` 带齐七栏（原话、范围、`--declared-dirty`、安全回路、验收标准加 `--check "命令 => 退出码"`、风险、回退）；先跑一次基线门禁 | 本地 | **要你出手：确认计划** |
| 4 | 批准 | `pm approve`（已启用口令时用户在终端输入口令） | 本地 | 要你出手：口令或点头 |
| 5 | 开工 | `pm confirm-start` → 开工位（`worktree open <agent> <卡号>`）→ `continuity run start … --worktree … --lease-wallet` → `continuity run transition --to RUNNING`；长命令用 `long-run start` 或 `continuity lease run-with-renewal` | 本地；云端直接开分支，跳过账本 | 无 |
| 6 | 写与自检 | 领域门禁：PLC `plc check <PID>`、`plc docs check`；规范 `spec check`/`lint`；Python `pytest`、`ruff`/`mypy`；文档 `doc check`；改动只落在可改范围 | 本地、云端（云端没有 LSP 插件） | 无 |
| 7 | 验证 | `continuity run transition --to VERIFYING` → `pm verify --mission-id <ID> --lease-wallet`；之后工作树不要再改 | 本地 | 无 |
| 8 | 提 PR | 提交（钩子 `git-hook` 自动跑）→ `pr open`（只开不合）；PR 描述照 `.github/pull_request_template.md` 写七栏；改受保护文件逐字列路径 | 本地、云端 | 无 |
| 9 | 审计与合并 | 另一个会话：`python reviews/tools/audit_pr.py <PR号>` + 清单；CI 必过项全绿；`pr ready` 放行检查；**Merge commit**；规则文件加“规则批准”、安全区加“安全签字” | 云端审计与合并线程 | **要你出手：评论“规则批准 / 安全签字 <头提交号>”**（只在碰规则或安全区时） |
| 10 | 验收与收口 | 用户在驾驶舱点“确认验收”（或口令下 `pm accept` 再 `pm close`）→ `change transition … --to completed --pid <PID>` → `ledger reconcile <PID>`（目标 0/0/0）→ 提交驾驶舱生成的变更单和台账；云端只写“建议回写” | 本地 | **要你出手：点确认验收** |

**“要你出手”**＝这一步必须用户本人动作，在驾驶舱“要你出手”页集中处理。第 2、3、4、10 步对应 GUI 方案（https://claude.ai/artifact/Q8YDVBWAo7XwMAZRfGNKS5）盘点表第 2、3 种（口令生效与否），第 9 步对应第 9 种；三个变体里的切换发布、删除、改规则、TIA 编译等亲口事同样在那张表里。清单只在 GUI 方案里维护，本稿不重复。

**中途出状况**：插急活 `pm park / switch / unpark`（用户原话才能切）；换 agent `pm handoff` 加 `pm takeover`；主控重启后 `pm recover`；租约过期按 `handover/22` §七；卡死先读 `handover/26`。
