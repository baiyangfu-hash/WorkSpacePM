## 5. 合同

### 5.1 登记与解析（A，`contracts/project_archive.py`）
文件 `SYS-2026-001_WorkspaceGovernance/project_archive.jsonl`，一行一个 JSON 事件，末尾换行。字段：`seq, project_id, action, project_root, at_utc, by, reason, evidence_ref, head_commit, tree_oid, tree_digest`；unarchive 另有 `seal_check ∈ {match, mismatch, missing}`。逐行解析规则，任一违反整份按**损坏**：`seq` 从 1 连续（**顺序以 `seq` 为准**）；`at_utc` 只要求能解析成 UTC，**不要求单调**（电脑时钟偏差不得造成损坏）；`action ∈ {archive, unarchive}`；该项目当前在用才能 archive、已封才能 unarchive（**已封再 archive 拒**）；`project_root` 相对、无 `..`、无反斜杠，**且等于该 `project_id` 在 `workspace_registry.json` 登记的路径**、在 `0100_PLC自动化/` 之下、不在禁区（`01_SharedLibraries`、`00_*`、`_archive`）；`evidence_ref` 通过 `user_evidence_problem`；`project_id` 不得为 `SW-2026-008`、`SYS-2026-001`。当前状态＝该项目最后一条事件的 action。
**损坏的范围与修复出口（防自锁）**：整份不可解析时，被拒写入＝登记里出现过的项目（逐行尽力提取 `project_id`）＋无法判定时一律拒写 `0100_PLC自动化/` 下各工程；控制面（SW-2026-008、SYS-2026-001、`reviews/`、`.github/`、`00_Infrastructure/`）不受影响。修复出口：钩子允许“只改登记文件”的提交；`archive-gate` 在基线登记损坏模式下只放行“只改登记文件且结果能完整解析”的 PR，需用户评论 `登记修复批准 <头前12位>`。**登记文件本身不算“已归档文件夹”**，只由纯追加规则管。`DJ-2026-009_汇川换型改造` 当前未登记于 `workspace_registry.json`，归档它须先 `project register`（前置，不在本卡）。
纯函数 `is_append_only(old_bytes, new_bytes)`：新字节以旧字节为前缀且新增行逐行合法（B、C 复用）。
**读取规则（取最严者）**：命令层、钩子读工作区、HEAD、`origin/main` 三处，任一说已归档即已归档；未提交的解封不放行；文件不存在＝无事件；存在但读不出/损坏＝按已归档拒；HEAD 或 origin/main 里有而工作区缺失＝篡改，拒。本地命令还读**尚未合并的本地分支 `archive/<PID>`**（`git show` 读登记），所以本地立即拒写；未合并的 unarchive 分支不放行，只有合并进 main 才解。写命令前先尝试 `git fetch origin main`（短超时）；失败或 `origin/main` 取不到时，用 HEAD＋工作区＋本地 archive 分支，并在输出里写明“未核对 origin/main”；**C 一律取基线分支，取不到则报红**。

### 5.2 命令（A，`project.py`）
- `project archive <PID> --reason … --approval-evidence-ref … [--dry-run]`：带 agent 标记拒；批准口令启用走 `_user_proof_or_exit`；前置条件任一不满足列原因退出 1：①无开着的 Mission/Work/Run（含“搁着”“等你”，复用 `open_work_blockers`）；②工程文件夹无未提交改动、无未跟踪文件（复用 `uncommitted_blockers`）；③`project_root` 在 HEAD 存在；④非 `SW-2026-008`/`SYS-2026-001`；⑤当前为在用；⑥读账本/Git 任一失败。输出明说“只核对了本机账本，未核对其它电脑上的卡，兜底靠 archive-gate”。通过后追加事件（`head_commit`、`tree_oid=git rev-parse HEAD:<root>`、`tree_digest=sha256(git ls-tree -r HEAD -- <root>)`），**落地方式**：命令**不碰控制根的 main 和工作区**：先短超时 `git fetch origin main`，在 `.auto-pm/worktrees/archive-<PID>` 用 `git worktree add` 从最新 `origin/main` 建分支 `archive/<PID>`，在那里写登记（临时文件＋改名＋回读）并**单独提交**（只含登记文件，走正常 pre-commit，不得 `--no-verify`）；写入或提交任一步失败则整个工位与分支一起清掉，控制根不变，退出 1。命令末尾打印推送命令与开 PR 命令（沿用现有 `pr open`），并明说：**“本地已封，未合并到 main，其它电脑与 CI 尚未生效”**。谁推、谁开 PR：用户本人（或用户让 agent 推并开 PR）；用户本人合并后才全局生效；合并后由 `worktree sweep` 清理。`--dry-run` 不写不提交不建分支。

### 5.5 服务器必过检查 `archive-gate`（C）
工作流 `archive-gate.yml` 含两个任务。
**任务一 `archive-gate`**：`pull_request_target`（opened/synchronize/reopened/edited）＋ `issue_comment`（重跑，同 rules-gate）＋ main 前进时对仍开着的 PR 重算；裁判与脚本取自 main，PR 头只拉成 git 对象当数据读，不检出不执行；评论经 `gh api` 取成 JSON 传入。**检查在合并引用 `refs/pull/N/merge` 上算**：基线登记取自合并引用的 main 一侧。脚本 `archive_gate_check.py --base <合并引用的 main 侧> --merge <合并引用> --head <PR头> --comments <json>`，只用标准库，不访问网络、不写仓库：
1. **从基线（main 侧）读登记**，不读 PR 头自带的登记；基线登记有而不可解析进入“修复模式”（见第 4 条）；
2. 取路径用 `git diff --name-only --no-renames -z <合并基点> <合并引用>`（改名拆两端），同时比对权限位、符号链接、子模块变化；对基线登记里每个已封文件夹做路径分量前缀匹配并大小写折叠，任一命中＝**不通过**（退出 1），无例外。**登记文件本身不算已归档文件夹**；
3. PR 对登记的修改必须是基线版本的纯追加且逐行合法，**含 archive 事件的 PR 只许改登记文件**；新增 `unarchive` 事件需要有效评论：用户本人（`baiyangfu-hash` + 数字 ID `246858089`）、未编辑、非 App 代发、非引用行、某一行为 `解封批准 <PR 当前头提交前 12 位>`；头变则作废；新增 `archive` 事件的 `tree_oid` 必须等于**合并引用里** `<root>` 的树哈希，且该 PR 内工程文件夹零改动；
4. 修复模式（基线登记损坏）：只放行“只改登记文件且结果能完整解析”的 PR，需用户评论 `登记修复批准 <头前12位>`，其余一律红；
