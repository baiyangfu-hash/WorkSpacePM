# SW-2026-008｜持续演进路线图 V0.3

2026-10-17（V0.2 为 2026-10-09）· 规划建议；具体实施未授权。版本变更见 [修订记录](05_修订记录与任务映射_PM.md)。

## 1. 路线结论

驾驶舱首先服务一名电气工程师管理真实项目：知道有哪些需求、正在做什么、哪些需要决定、哪里卡住、交付证据是否齐全。用户在熟悉的 IDE 中选择 Agent/模型；驾驶舱提供共同的项目事实与受控操作入口，不要求用户搬到新的 AI 开发环境。

Claude 可以作为当前主要执行工具，未来换到 VS Code、Cursor、Trae 或其他环境时，产品边界不应重新定义。某一组合能否执行，必须用其真实接口、合法身份和实际任务证明；本包不宣称已经兼容全部组合，也不要求继续使用 GPT。

默认流程：

1. 用户或外部 Agent 从薄入口读到项目级简报、未验证项与确切下一步。
2. Agent 根据真源分析需求和影响，生成可预览的建议。
3. 用户批准准确版本及范围；适用的治理记录、Work/Run、lease 和隔离边界生效。
4. 用户选择的工具执行，驾驶舱提供查询、核验与回传入口。
5. 机器检查证据，独立复核后由用户验收；合并、部署、发布各自保持独立条件。

“默认不由驾驶舱启动模型”不等于禁止 Agent 内部使用子代理，也不等于删除现有授权和调度合同。可选自动执行模块将来可以接在同一公共合同上，不能成为唯一可用入口。

## 2. 为什么调整

旧稿正确保留了证据治理和电气扩展，但把工具制造能力排得过早。执行端沿着卡工厂、分档器、适配器等局部可实施事项推进，容易让用户真正关心的概览、看板、需求确认后退。问题在于规划把“管理执行”过多等同于“由驾驶舱发起执行”，没有把默认主路径写清。

这是对规划优先级和边界的修正，不是认定此前成果无用。已完成的检查器、隔离、回执和恢复机制应复用；需要凭证据判断哪些是公共底座、哪些只服务自动进程。这里不估算所谓浪费时数，也不把当前全部状态归因于某个 Agent。

## 3. 分阶段成果与进入条件

| 阶段 | 用户得到什么 | 候选 | 退出依据 |
|---|---|---|---|
| A：校正事实与边界 | 明白本次改什么、复用什么、不会影响谁 | B01、B02 | 当前批准/候选/部署差异有出处；正式旧任务与新方向逐项映射 |
| B：能接手、能看清 | 一个新会话读懂整个项目；自己的驾驶舱能看五栏和验收区 | G01、O01、V01、X01 | 真实外部 Agent 完成一条合法小任务；只读简报/看板不写状态、不假报完成 |
| C：需求确认可追溯 | 看分析预览、批准准确版本、知道变更影响 | R01、R02、R03 | 需求、批准、任务与证据关联一致；漂移/越权/旧版本被拒 |
| D：计划与环境接续 | 知道预期成果及时间，换工具后还能接上 | L01、X02；必要时 S01 | 日期性质明确；第二环境真实演练；未实现操作明确标示 |
| E：已部署版本的日常验证 | 用于三次真实小交付 | A01 承接原 D08/D09 | D07 部署前提、原 AC 和人工验收均成立；候选彩排不能替代部署后证据 |
| 后续选择 | 针对真实电气项目与实际瓶颈增加能力 | 保留的 EV0 任务 | 每项有实际触发收益和最小范围，重新批准 |

表内为能力依赖，不是所有工作必须串行等到同一阶段结束。并行规则（V0.3，替换 V0.2“每次只激活一个正式切片”一句）：**独占**——改核心存储（`continuity_store.py` 等）、哈希链、Hook/门禁、共享夹具的卡，同一时刻全仓只能有一张在做，重门禁照旧串行；**可并行**——只读简报（O01）、只读看板（V01）、入口说明文档（G01 的纯说明切片）、规划与审阅文档，可与一张独占卡同时进行；**前提**——每张并行卡开工前写明自己的文件范围（owned paths），两张卡的范围不能重叠，重叠的那张等前一张合进 `main` 再开；**谁做谁审**——做的 agent 和审的 agent 不能是同一个。R01 的设计可在 B02 后进行，O01 基础简报无需等待新需求存储，R03 才负责合并。V01 先只读；S01 只补确实缺失的状态操作。

“挂起、废弃、归档”是用户看板语义，先定义其承载对象和与现有记录的对应关系。现有 schema 有单项目一个未终结 Mission 的约束；不能为画五栏就先造多个 Mission，或把 Run 的取消冒充业务废弃。无数据/无语义的列必须标注，不宣称已经有相应操作能力。

## 4. 既有 WBS 如何承接

| 原范围 | V0.2 建议 | 不得丢失的验收 |
|---|---|---|
| E01–E08 | B02 逐项识别公共合同及自动进程专属部分，给默认外部执行路径明确承接 | 身份、授权、租约、交接、状态与证据；原 C01/C09 对 E05/E08 的依赖不能悬空 |
| V03/V04/V04-R0 | 先复用已有证据、再核是否适用于新外部路径 | 接续与失效边界不因不用自动模型而消失 |
| V04-R1 | 租约续期/失效、新 owner/epoch、旧写拒绝属于公共部分；物理进程回收按实际功能另定 | 不能用 fencing 冒充杀进程；原文未把整项 R1 设为 V05 前置，不扩大既有门槛 |
| V07/V08/F01-b | 可提出后移，明确保留条件及影响，待正式修订批准 | 不静默删除原 AC；已在途有效授权不由本包中断 |
| 077 | 核已有提交和闭环，避免重做；规则只加不放宽的事实需分层确认 | 提交不自动等于治理验收或部署 |
| 078/分档器 | 非主路径必要前置；未启动可建议后移，已合法在途先核范围和期限 | 不擅自撤销或延长授权；不以提效削减核心门禁 |
| D07/D08/D09 | 继续按正式发布、真实使用和退出条件推进；新范围需映射到适用的正式任务 | D08 在批准部署之后做三次真实小交付；全部原 AC 由正式修订明确承接 |

上述是调整建议，未改原 WBS。已通过成果是否满足新范围，要由证据和适用性决定，而非要求全部重做，也非默认可以跨版本复用。表内 EV1 新依赖不自动成为原 D08/D09 的新增前置；M3 后批准的增量按同样方法另验，不重写原里程碑状态。

## 5. 对电气日常工作的持续迭代

先有一个真实项目的材料包，再沿最能减轻你重复劳动的一条链投入：

| 真实问题 | 保留候选 | 交付边界 |
|---|---|---|
| 图纸、IO、接口、变量来自哪里，彼此是否一致 | EV0-R02、EV0-I01–EV0-I06 | 保存原件与出处，关联变化；未知接线/极性/动作时序留待确认 |
| 厂商软件编译失败，AI 不知对应哪里 | EV0-C01–EV0-C03 | 导入真实反馈、定位源码、记录修订与人工复编；不冒充真实编译器 |
| FAT/SAT 资料与现场异常分散 | EV0-F01/EV0-F02 | 待执行检查包和可追溯证据；现场执行结果由真实操作产生 |
| 上下位机接口经常对不齐 | EV0-E01/EV0-E02 | 先一个协议映射、再真实本机回环；仿真/回环不等于设备联调 |
| 原型与实现不同，或 PLC 逻辑需仿真 | EV0-U01–EV0-U03 | 限定画面/块和真实工具输出；不生成假 PASS |

本包 EV0-C/E 与正式 WBS 的 C/E 编号不同，必须使用完整 ID。PLC 的正式静态交付边界保持；TIA Portal/InoProShop 编译、下载、现场联锁与安全判断由具备真实环境的人执行。不能因为有“驾驶舱”就扩大自动操作设备的权限。

## 6. 提效和架构债怎么选

EV0-T01–EV0-T05 先核是否已经偿还。EV0-T06/EV0-T07 以可复现负载问题触发。EV0-T08/EV0-T09 卡工厂、EV0-T10/EV0-T11 分档工具后移到重复劳动成本真实出现时；不让工具建设挡住首次使用。EV0-P02 仅在外部合法身份路径实际受阻时补缺；EV0-P03 能力试件后移；EV0-P05 自动启动扩展冻结，等用户另行选择。

EV0-A01/EV0-A02 按依赖方向、历史共同修改、测试隔离困难和变更成本证明耦合热点；每次只拆一个值得拆的边界。大文件或层数多本身不证明需要重构。EV0-Q01/EV0-Q02 涉及完整挂起/进程抢占与恢复，比只读看板和基本调度语义更重，保持独立。它们与新主线 EV1-A01 的部署后验证不同。

若要借鉴 GitHub，后续在确定具体问题后只选少量官方/原始仓库，核许可证、维护状态和适配成本，不凭相似界面复制架构。本次没有开展外部仓库调研，不能把未核方案写成已验证选型。

## 7. 先后顺序、记账卡配额与 main（V0.3 新增）

**先后顺序**：正式 WBS 的 M3 主线先走完下面几步，再开始本规划的首批（B01/B02/G01/O01）：（1）补丁 09、13（卡 147 的启动时间与 PENDING 出口）已由卡 152 落地，随 PR #2 合进 `main`（`46aead17`）；（2）补丁 10（`M3-ENVPORT`，新电脑一键可用，无启动器部分）已由卡 158 落地，PR #3 已合进 `main`（`b68bd03e`）；启动器依赖探测因提交钩子拒绝而未落地，另登技术债；（3）技术债：`lease_reclaim.py` 对超长纯数字启动时间抛 `ValueError`，契约应返回 UNKNOWN，排在 V04-R1 存储卡之前；（4）V04-R1 存储接入卡（核心档），再做真实进程演练卡；（5）跨机共享状态（`M3-COLLAB` B，S1～S5）。B01 的事实刷新以“开始做 B01 那一刻的 `main`”为基线，不再用 V0.2 里引用的 release `1.3.3-a808fa8`；077/078 的“待核”已有结果，B01 改为以卡 147 之后的事实重做差异表。

**记账卡配额**：TD 台账回写、WBS 修订写回、变更单补入库，并进实质卡的收尾步骤，不单独开卡；确需单独记账（例如一天内多张卡合并写回）时，每做一张实质卡最多附带一张记账卡；每个里程碑出一张“原始需求 vs 实际交付”对照表，代替逐卡的状态回写卡。（背景：10-09 之后约 70 张卡里约 42 张是记账卡，主线 B01/B02/G01/O01 一张没开工。）

**`main` 只走 PR**：必须 PR、禁止强推和删除、必须解决评审对话（规则集 `main-protect`，用户已在 GitHub 设置）；不要求审批人，因为是单人仓库；命令行快进只在应急时使用并事后补记；gate 检查做好后再加为必需检查。

## 8. 成本控制和何时停下

每批选择 3–5 个可独立评审的候选，实际继续拆成单成果正式卡；每次只激活一张。先确定收益，再确定文件和门禁。详细 WBS 的工程时数是低置信范围，不是 AI 墙钟或你的劳动时数，不能和重门禁机器时间混淆。

第一轮（排在上面几步之后）只取 B01+B02+G01+O01，工程占位为 24–48 h，另计正式门禁/审核/等待；已有能力满足的部分直接扣除，不为表格重复开发。任何一项勘测后过大都继续拆卡。这不是交付日期承诺。

达到“你能看清、批准、接手、验收一个真实项目”的获批范围后即可停下来使用并收集反馈。没有需求就不继续扩大候选池。剩余条目以真实收益触发，不作为使用税。
