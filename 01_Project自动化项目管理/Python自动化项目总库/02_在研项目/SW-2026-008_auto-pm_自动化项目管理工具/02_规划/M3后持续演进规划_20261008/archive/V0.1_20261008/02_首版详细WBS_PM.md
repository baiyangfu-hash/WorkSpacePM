## 1. 本表如何使用

每个 EV0-* 是一个候选最小成果，不是已创建的 Work/Run，也不保证一个候选只需一张正式卡。正式勘测发现超过约6个产品文件、涉及多个责任边界或未知迁移时，必须继续拆卡并重新估算。测试/文档/工具路径同样完整列入，不得为满足数量而隐藏。

依赖表达的是“所需能力已被证实”，不要求把已经实现且证据充足的能力重做一遍。R01 可用现有已验成果满足依赖，并记录证据引用；仅有候选、回执或聊天标签不能满足依赖。

所有任务默认继承：用户批准具体范围；合法身份和适用的 CHG/Decision/Work/Run/lease；独立候选与冻结字节；适用门禁及负向证据；独立会话复核；用户验收。报告性只读任务按适用文档治理办理，不为规划草案自行写库。

## 3. 估算口径与门禁预算

工程投入单位为有效人时（h），包括勘测、设计、实现、针对性开发验证与材料整理；不含正式门禁机器占用、审批/排队、现场窗口、独立审计或返工。它不是AI墙钟预测，更不是用户劳动时数。此版全部低置信、待首批实测校正。

| 门禁代号 | 规划预留机器占用/轮 | 必须遵守的适用边界 |
|---|---:|---|
| GD | 0.25–0.75 h | 非运行态文档的结构、引用、边界、哈希等静态检查；不凭扩展名判文档档 |
| GT | 0.5–3 h | 获批测试档的完整相关组、健康/静态/类型/变异及场景；范围无法证明时升级GC |
| GC | 2–6 h，异常时可能更长 | 按当时获批矩阵执行完整九组及必要场景/静态/类型/变异；本数值不是时限或可删检查的上限 |
| GX | 随实际试单档位；GD/GT/GC之一，另加真实模型和恢复场景时间 | 接续演练沿用试单实际风险档，不以“演练”降低范围 |
| GT/GC | 先预留GC，正式卡解释能否采用GT | 涉及全局负载/关键Hook边界时不得仅凭文件位于tests而裁剪 |

“两小时以上”来自Claude一线建议S11，本次没有复测。2–6h等区间是排期占位假设。基线、候选、恢复后若需多轮，每轮分别累计；保留失败并计返工，不用最后一次绿覆盖失败。

单批预算 = 工程投入 + Σ(每卡适用门禁×实际轮数) + 独立复核 + 明确的用户参与 + 排队/外部等待。缺少后几项时不得给总交付日期。卡数拆分、环境或范围变化后重估。

1. R01先刷新基线。P01/P04和T类工具可以按收益选择；P04不等待P02/P03/P05，但合法执行身份验证失败时必须停在不支持，不能绕开。

3. T09依赖冻结身份和工具，**不依赖T11**；T11也不依赖T09。负载诊断T06/T07不阻塞全部提效，但没有可靠证据前不得启用并行提速。
4. I01→I02与I01→C01→C02→C03可交错安排。用户编译窗口等待时可做只读规划，不能同时占用别人重门禁资源。
5. 新协议、新厂商、新图格式、新页面、新热点都是新的范围。不要把“可扩展”当成这一张卡顺便全做的理由。
6. 条件项已被原M3或后续修复满足时，记录映射后删除待实施工作；不要为了维持40个编号而制造重复任务。
7. 同一模块、同一治理对象、共享门禁工具或共享运行资源默认串行。子代理只读勘测可以分工；实现与独立复核须分离上下文。
8. 独立执行卡的冻结字节不可被后续规划更新追溯改写；范围有变重新批准并留下原失败/差异证据。

| 验证 | 正反例是否真正命中；命令/环境/退出码/用例集合是否可信；卡/Run/Checkpoint/提交/工具/报告字节能否互证 |
| 独立复核 | 非实现会话按冻结材料检查；同模型复核披露同源盲点；必要反例不能由用户签字替代 |
| 闭环 | 按适用治理完成Run/Work/CHG与台账；技术完成、用户验收、发布分别记录 |
| 发布使用 | 只有批准后更新部署；active/previous/manifest及CLI/GUI/Hook/SDK身份核对；新事件不能被旧DB回滚覆盖 |
| 文档 | 更新实际受影响的操作入口/合同说明与残余限制，不进行无界限的全部归档 |
| 后续 | 首次真实使用记录收益/失败，校正下一批估时，不能用自述成功代替证据 |

## 9. 任务池体量的正确解释

本表全部40项（含可跳过、可推迟、互不必需的方向）的工程区间机械相加为 **418–866 h**，尚未包含正式门禁、审核及外部等待。这个数字只说明“全部愿望都做”投入很大，**不是建议用户承诺的项目预算，也不是M3剩余时长**。

本初稿因此推荐每批3–5项、一个真实项目验效后再选下一批。已实现能力会减去重复工作，扩大范围或新发现迁移会增加成本。近期批次应在实际环境勘测后给较窄估算，远期区间不用于日期承诺。
