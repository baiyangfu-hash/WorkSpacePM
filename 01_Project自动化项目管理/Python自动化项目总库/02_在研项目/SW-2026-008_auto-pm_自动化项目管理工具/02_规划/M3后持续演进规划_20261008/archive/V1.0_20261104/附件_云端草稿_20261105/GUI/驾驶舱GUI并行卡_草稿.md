## 0. 先说结论

**像 PLC 和 HMI 并行：规划是“程序”，GUI 是“画面”，两边共用一张“点表”，各自写，再联调。**

1. 总控屏现状（已核）：今天、问题、全部项目、决定（九个按钮）、流程图（任务、工作项、运行、变更单四张状态图，数据在 `flow/graphs.json`）、工具（变更单、决策、变量表查重）、工程工位（`plc check`、BC 行）。**缺的正是规划脊柱里“一件事怎么走”的那一整条**：进门定位、入箱出计划、开工位、PR 与审计、发版、出状况。
2. 因此 GUI 卡不是“再做一套界面”，而是给规划的每个批次配一张“画面”，一张验“程序”对不对、一张验“画面”对不对。下面 §2 是点表，§3 是 10 张卡，§4 是联调规矩。
3. 所有卡守同一条原则（已核，设计稿和 `README`）：**界面是命令行的另一层皮**。按钮只拼一条 `main.py` 命令，命令和退出码原样进抽屉；门禁、租约、口令、受保护清单全由命令自己判，界面不放行。永不加的按钮（合并、删除、切换发布、代签、改规则、启动 agent）保持原样。

## 1. 为什么能并行验证（一句话讲清）

规划里每一步都写了“该用的命令”和“用户看到什么”。GUI 里每个视图也是“读一条只读命令 → 显示；点一个按钮 → 跑一条命令”。**两边说的是同一件事，所以能互相对账**：

- **正向（程序验画面）**：规划说第 N 步用命令 X，GUI 对应视图就必须读或跑命令 X，退出码含义一致。GUI 做不出来，说明命令缺 `--json` 或规划写得含糊。
- **反向（画面验程序）**：GUI 在某个状态下要显示“下一步”，规划就必须在这个状态写清谁做什么。画面上出现规划没讲的状态，说明规划漏了。
- **故障注入（两边一起）**：造一个坏状态（租约过期、规则批准缺、`orient` 自相矛盾），规划“出状况怎么办”和 GUI 横条必须给出同一个动作。
