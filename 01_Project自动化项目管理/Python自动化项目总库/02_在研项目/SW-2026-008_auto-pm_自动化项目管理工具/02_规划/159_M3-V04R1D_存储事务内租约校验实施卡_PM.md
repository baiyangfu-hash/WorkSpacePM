## 1. 背景与已核实事实（2026-10-16 夜）

1. **为什么**：（a）**TD-SW008-145 的先查后写竞态**：租约校验在服务层先读后判，再由存储层另开事务写入；存储层的 `create_checkpoint` 与 `transition_run` 在自己的写事务里完全不查租约。回收或移交落在“查完”与“写入”之间时，旧持有者的写入仍会成功。多个 agent 并行、跨电脑共享状态，都要求“谁持有租约”由存储层在写入的同一个事务里说了算（项目 Claude 审阅 03 的设计，我已在开发树上实现并核对）。（b）**契约里一个小缺陷**：评审机器人在 PR #2 指出，纯数字启动时间超过 4300 位时 `int()` 抛 `ValueError`，契约本该判 UNKNOWN；持续演进规划 V0.3 的先后顺序把它排在存储卡之前，所以并入本卡。用户 2026-10-17 转述咨询 Claude 的裁决：先补丁 09/13 与补丁 10，再做存储接入卡，最后跨电脑共享状态。
2. **做什么**（6 个文件；全部事实在构建时读自 git 并断言）：
   - **存储** `continuity_store.py`：`_grant_epoch` 从事件里取“当前 token 被授予时的 lease version”（创建 Run 为 1，移交为移交后的 version；续租只加 version、不改 epoch）；`get_grant_epoch` 只读；`_require_lease_in_tx` 在 `BEGIN IMMEDIATE` 事务内校验 owner、token、到期与（带了才校验的）epoch；`create_checkpoint` 与 `transition_run` 新增必填关键字参数 `owner_id`、`lease_token` 与可选 `expected_epoch`，校验放在精确重放之后（重放仍返回原结果），`transition_run` 里放在状态合法性检查之后；
   - **服务** `continuity_execution_service.py`：`checkpoint`、`transition_run` 把参数传下去并保留原来的快速检查，另加可选 `expected_epoch`；
   - **契约** `lease_reclaim.py`：纯数字启动时间超过 30 位判无法解析；
   - **测试**：新增 6 个存储/服务测试（续租不改 epoch；移交后旧持有者、旧 epoch、未来 epoch 被拒且什么都没写；移交落在服务检查与存储写入之间也无法竞速；到期在事务内判断；精确重放不受移交影响；不带 epoch 在兼容期被接受）与 1 个契约测试；适配 1 个假存储函数与 4 处直接调用。
   - 不带 `expected_epoch` 的写入在兼容期被接受、**不产生事件**；`record_run_started`、`create_handoff`、`renew_lease` 的 epoch 与回收接口、驾驶舱界面与真实进程演练另卡。
3. **不做什么**：不改表结构、不改事件哈希链、不改 `settle-expired` 的现有行为、不接入进程指纹与回收接口、不改 CLI 与监督服务的调用方式（它们经服务层，签名向后兼容）、不加 `INITIAL_EPOCH`；不推送由本卡完成（走 PR）。
4. **为什么是核心档**：分档器不认识这个路径，按“未知路径按核心档复核”的规则声明为核心档，跑九组回归并要求与上一张卡的受治理输出逐项相同。

基线、工具/卡/Decision 指纹、冻结文件字节、owner/scope、lease（含续租失败）或 hook 漂移；新增范围；任何门禁失败（§1 第 6 条那一条容忍规则之外）；Checkpoint 不能绑定当前字节；提交 Hook 拒绝；插件缺失或版本不符；需要改这 6 个文件以外的任何内容、或为让检查变绿而放宽判据：均停止，保留现场，不靠重跑、改字节或放宽判据变绿，不开第二轮。止损：同一问题最多修 2 轮，连续 2 张卡失败整体停下；同一问题两次未解就通知用户（用户切 Opus 诊断）；不做任何真实模型调用。
