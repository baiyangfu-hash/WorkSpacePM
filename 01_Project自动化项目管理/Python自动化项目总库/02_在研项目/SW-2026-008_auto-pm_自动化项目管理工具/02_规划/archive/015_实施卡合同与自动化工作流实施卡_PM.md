## 1. 原始目的

实施卡不是另一份 WBS，也不是聊天提示词。它把 WBS 已选定、且经用户批准进入实施的原子任务转换为机器可验证的有界执行合同：固定不可变基线、产品路径、提交治理证据、门禁、失败出口与独立授权边界，防止换 Agent 后重新解释任务。

实施卡本身不授予执行权。只有匹配的 CHG、用户批准、Decision、Mission、Work、Run 与有效 lease 同时成立，执行方才可修改声明范围。

## 3. 产品合同

### 3.1 最小字段与状态

`implementation_card.v1` 至少包含：

- `card_id`、`project_id`、`wbs_item_id`、`milestone_id`、`intent_type`；
- `source_refs`、用户故事或问题陈述、验收条件；
- `base_commit`、`candidate_policy`、`owned_paths`、`commit_evidence_paths`、`non_goals`；
- 门禁命令 cwd、参数、预期 Exit Code 和覆盖目标；
- `max_runs`、`max_healing_attempts`、时间与额度停止线；
- Decision、Work/Run、Checkpoint、最终提交的证据映射；
- 合并、推送、部署和 release 切换的独立授权边界。

状态为 `DRAFT → REVIEWED → APPROVED → DISPATCHED → VERIFYING → ACCEPTED → CLOSED`；`REJECTED` 与 `CANCELLED` 为终态。普通接口不得跳跃状态。

### 3.2 产品路径与提交治理证据分层

- `owned_paths`：真正接受产品门禁、允许执行代理修改的代码、模板和测试路径；
- `commit_evidence_paths`：Git Hook 要求与产品代码位于同一最终快照的 CHG 与项目台账；
- Decision、Work、Run、Checkpoint 和最终提交范围必须严格等于二者并集；
- Ruff、Mypy、Pytest 只覆盖适用的产品路径，不能把 Markdown 治理证据冒充产品门禁目标；
- `validate`、`dispatch`、`verify` 必须对两个集合分别校验并对并集 fail-closed。

## 4. 自动化工作流

目标根入口命令族：

```text
python main.py implementation-card create
python main.py implementation-card validate <CARD_ID>
python main.py implementation-card approve <CARD_ID>
python main.py implementation-card dispatch <CARD_ID>
python main.py implementation-card verify <CARD_ID>
```

`validate` 只读校验字段、canonical WBS、Git 基线、受管隔离候选与路径集合；`dispatch` 仅在 Decision/Work/Run、候选 HEAD 和十路径范围完全一致时输出执行包；`verify` 绑定最新当前字节 Checkpoint 和最终提交，不自动合并或部署。
