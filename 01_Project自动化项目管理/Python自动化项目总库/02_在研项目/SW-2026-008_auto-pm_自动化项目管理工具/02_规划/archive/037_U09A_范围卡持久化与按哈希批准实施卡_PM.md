## 1. 背景与已核实事实（2026-10-01，基线 `d40318d0`，均为命令或源码核验）

1. 用户已裁决的 4 个设计问题（2026-10-01）：① 范围卡由 PM 经 CLI/SDK 起草，驾驶舱只展示给用户审；② 驾驶舱用一个按钮“批准范围并开始”；③ 待批准范围卡存规范库（Continuity Store）**追加一张表**，在事件链内、可审计；④ 驾驶舱批准人身份来自配置项，未配置则拒绝批准。拆分：U09A（本卡：Store + Facade）、U09B（CLI）、U09C（驾驶舱界面与批准人配置）。
2. 现状缺口：`PmFacadeService.create_planning_scope_card` 只在内存里算出范围卡并返回，**没有任何地方保存批准前的范围卡**。规范库只有 `planning_drafts`（目标与验收）、`planning_draft_chg_bindings`、`planning_draft_spec_bindings`、`planning_draft_decision_bindings`（批准后）4 张规划表；没有范围卡表，也没有“列出草稿”的读取接口。CLI `pm approve` 现在靠调用方把范围、风险、非目标、执行授权**原样再传一遍**来重建卡。驾驶舱因此无处读取待批准的卡。
3. 驾驶舱保存的草稿：`pm_cockpit_bridge.py` 用 `REQ-COCKPIT-<uuid>` 作为 `request_id` 调 `create_planning_draft`，该编号对用户不可见；PM 要为它起草范围卡，必须先能从规范库列出草稿。
4. 追加表的先例：U06 的 `closure_items / closure_steps / closure_outbox` 就是在 `continuity-store.v7` 上**只追加表、不升版本号**（`tests/core/test_pm_closure_service.py::test_initialize_adds_closure_tables_to_an_existing_current_store` 断言建表后版本仍是 v7）。不升版本号意味着已部署的旧运行时仍能读写同一个库，回退安全。

## 2. 单一目标（用户故事与完成定义）

作为起草范围卡的 PM，以及之后要展示并批准它的驾驶舱：

1. PM 能列出某项目的全部规划草稿（含驾驶舱保存的草稿），看到目标、验收条件、是否已有范围卡、是否已批准；
2. PM 能为一个已存在的草稿提交范围卡，范围卡被**持久化**在规范库的追加表里，并在事件链留下 1 条事件；可以提交新修订取代旧修订；
3. 任何调用方能列出某项目“待批准”的范围卡（每个请求只列最新修订），读出的卡与提交时逐字段相等，被改动过的记录一律拒绝而不是悄悄跳过；
4. 批准只需要 `request_id + plan_hash + 批准人 + 批准证据`，不再需要调用方重传范围内容；一次调用完成“CHG 批准 → Decision → Mission → Work”，重放幂等；
5. 不改变任何既有方法、既有表、版本号与既有测试。

三个模型均为 `ConfigDict(extra="forbid", frozen=True)`：

3. `PlanningApprovalResult`：`schema_version: Literal["planning-approval-result.v1"]`、`request_id`、`subject_project_id`、`change_id`、`plan_hash`、`decision_id`、`mission_id`、`work_id`，全部为非空字符串。

### 5.2 `continuity_store.py`（只追加）

1. 新表（语句放在一个模块级常量里，`_DDL` 引用同一常量，写入方法也用同一常量保证表存在；逐字如下）：

   ```sql
   CREATE TABLE IF NOT EXISTS planning_scope_cards (
       request_id TEXT NOT NULL REFERENCES planning_drafts(request_id),
       revision INTEGER NOT NULL CHECK (revision >= 1),
       plan_hash TEXT NOT NULL,
       change_id TEXT NOT NULL,
       card_json TEXT NOT NULL,
       submitted_by TEXT NOT NULL,
       created_at TEXT NOT NULL,
       PRIMARY KEY (request_id, revision),
       UNIQUE (request_id, plan_hash)
   );
   ```

2. **版本与迁移不变**：不新增版本常量，不改 `_CURRENT_SCHEMA_VERSION`、`_KNOWN_SCHEMA_VERSIONS`、`initialize` 的任何迁移分支，不向 `schema_migrations` 写行。任何新逻辑不得读取或比较 schema 版本，只能用 `sqlite_master` 判断新表是否存在。
3. **只追加**：对 `planning_scope_cards` 只允许 `INSERT` 与 `SELECT`；本卡新增代码不得对它 `UPDATE`/`DELETE`，也不得对其它任何既有表新增写入（事件表经既有 `_append_event` 追加除外）。
4. `submit_planning_scope_card(card: PlanningScopeCard, submitted_by: str) -> int`（返回修订号），单个 `_transaction` 内按序：
   - 用 `conn.execute`（不得用 `executescript`）执行上面的建表语句；
   - `submitted_by` 必须等于其去空白结果、非空、不超过 80 字符、全部可打印，否则拒绝；
   - 草稿必须存在；`planning_draft_chg_bindings` 的 `change_id` 必须等于 `card.change_id`；`planning_draft_spec_bindings`（按 `spec_id` 排序）必须等于 `card.spec_sources`；
   - 用 `PlanningScopeCard.from_draft(草稿, change_id=…, scope_paths=…, risks=…, non_goals=…, spec_sources=…, execution_grant=…)` 以卡内字段重建，重建结果必须与传入的卡**相等**（由此保证 `plan_hash` 与内容一致），否则拒绝；
   - 该请求已存在 Decision 绑定则拒绝（已批准的请求不再接受新修订）；
   - 规范序列化：`card_json = json.dumps(card.model_dump(mode="json"), ensure_ascii=False, separators=(",", ":"), sort_keys=True)`；
   - 同一 `(request_id, plan_hash)` 已存在：`card_json` 相同则直接返回其修订号（不新增行、不新增事件），不同则拒绝；
   - 否则修订号 = 该请求当前最大修订号 + 1，插入一行，并经 `_append_event` 追加 1 条事件：`aggregate_type="planning_draft"`、聚合 ID 为 `request_id`、事件类型 `PLANNING_SCOPE_CARD_SUBMITTED`、幂等键 `planning-scope-card-submit:{request_id}:{plan_hash}`、载荷恰为 `request_id / revision / plan_hash / change_id / submitted_by / card_sha256`（`card_sha256` 为 `card_json` 的 UTF-8 SHA-256）。
   - 所有拒绝均抛 `ContinuityStoreError`，且事务回滚后行数与事件数不变。
5. 三个读取方法全部走 `_read_connection`（严格只读快照），新表不存在时**不建表**：
   - `list_pending_planning_scope_cards(subject_project_id: str) -> tuple[SubmittedPlanningScopeCard, ...]`：该项目下、每个请求的最新修订、且该请求没有 Decision 绑定；按 `created_at`、`request_id` 排序；新表不存在返回空元组。
   - `get_submitted_planning_scope_card(request_id: str, plan_hash: str) -> SubmittedPlanningScopeCard`：按精确 `(request_id, plan_hash)` 取一条（不论是否已批准）；不存在或新表不存在抛 `ContinuityStoreError`。
   - `list_planning_drafts(subject_project_id: str) -> tuple[PlanningDraftOverview, ...]`：该项目全部草稿，按 `created_at`、`request_id` 排序；新表不存在时 `card_revision` 为 0。
6. **读出即校验（不得悄悄跳过）**：每条范围卡记录读出时，`PlanningScopeCard.model_validate(json.loads(card_json))` 后必须满足：卡的 `request_id`、`plan_hash`、`change_id` 分别等于该行的列值；卡的 `subject_project_id`、`acceptance_criteria` 等于草稿；用 `from_draft` 以卡内字段重建后与读出的卡相等。任一不满足抛 `ContinuityStoreError`（整次读取失败），不得返回其余记录。
7. 不改任何既有方法体、既有表定义、既有索引；`from auto_pm.contracts.pm_facade import …` 这一行可扩充导入名。

### 5.3 `pm_facade_service.py`（只追加）

1. `list_planning_drafts(subject_project_id)` 与 `list_pending_planning_scope_cards(subject_project_id)`：直接转调 Store，同名同返回；`ContinuityStoreError` 转 `PmFacadeError`。
2. `submit_planning_scope_card(request_id: str, *, scope_paths, risks, non_goals, execution_grant: PlanningExecutionGrant, submitted_by: str) -> SubmittedPlanningScopeCard`：
   - 草稿必须已存在（`get_planning_draft`）；由**持久化的草稿**重建 `PmIntent`，调用既有 `create_planning_scope_card`（不得复制其逻辑），再调 Store 的 `submit_planning_scope_card`，最后以 `get_submitted_planning_scope_card` 的结果返回；
   - `execution_grant` 为必填（不接受 `None`）；
   - `ContinuityStoreError`、`ValueError` 转 `PmFacadeError`。
3. `approve_pending_planning_scope_card(request_id: str, *, expected_plan_hash: str, approver: str, approval_evidence_ref: str) -> PlanningApprovalResult`，按序：
   - 先调 `DecisionService.validate_planning_approval(approver, expected_plan_hash, approval_evidence_ref)`——不合格的批准在**任何写入之前**被拒绝；
   - `get_submitted_planning_scope_card(request_id, expected_plan_hash)`；`superseded` 为真则拒绝（固定文案含“已被新修订取代”）；
   - 把卡绑定的 CHG 推进到 `approved`：状态为 `draft / submitted / under_review` 时依次补走到 `approved`（`transition_status(change_id, state, approver=approver, comment=f"user approved planning scope {plan_hash}", project_id=…)`），已处于 `approved / implementing / pending_acceptance / accepting / completed` 则不动，其它状态拒绝；
   - 依次调用既有的 `approve_planning_scope_card`、`materialize_planning_mission(card, created_by="PM Facade")`、`create_planning_work(card)`（不得复制其逻辑、不得改其方法体）；
   - 返回 `PlanningApprovalResult`。
   - 相同参数重放返回相等结果，且 Decision/Mission/Work 数量不增加；批准人或证据与首次不同则拒绝（由既有 Store 绑定保证），不产生新对象。
   - `ContinuityStoreError`、`DecisionError`、`MissionServiceError`、`WorkRegistryError`、`TransitionGuardError`、`ValueError` 转 `PmFacadeError`。
4. 本卡**不**启动执行、不创建 Run、不生成或保存租约口令；不改 `pm.py`、`api.py`、驾驶舱服务/Bridge/QML。
