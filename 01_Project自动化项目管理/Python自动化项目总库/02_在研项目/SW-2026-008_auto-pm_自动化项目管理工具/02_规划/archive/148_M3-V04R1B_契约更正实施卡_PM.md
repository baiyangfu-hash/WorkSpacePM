## 1. 背景与已核实事实（2026-10-16）

1. **为什么**：项目 Claude 对 V04-R1 设计的云端只读评审（2026-10-16 傍晚）指出，卡 147 的模块说明与卡文写“epoch 等于 lease version，续租时增加”。我核对了代码：`renew_lease` 每次续租都会 `version = version + 1`；若写入要求 `epoch == version`，持有者自己每心跳一次，它在途的写入就被当成旧 epoch 拒掉，心跳越勤自伤越多。这是我设计里的错，卡 147 已收口并推送，本卡更正。我另核实：租约校验在服务层（`_require_active_lease`），先读后判再调存储层另开事务写入，存储层的 `create_checkpoint` 本身不查 owner、token、过期（先查后写竞态）——这是第 2 张存储卡的任务，本卡只在契约说明里写明。
2. **做什么**（2 个已有文件改，不新增文件；见 §4）：
   - **epoch 的语义**：epoch 是 Run 租约的“所有权编号”，**不是** lease version；只在所有权变化（授予、移交、回收）时增加，续租不增加；`version` 只做续租的比较并发控制；
   - 新增 `LeaseEvent`（GRANT、TRANSFER、RECLAIM、RENEW）与 `epoch_after(current, event)`；`next_epoch` 保留，说明更正为“所有权变化之后的 epoch”；
   - `ReclaimResult` 新增 `exit_path`：PENDING 的出口是“用户签 Decision 强制收回，并承担抢占一个无人能识别的进程的风险”；其他结果为空；
   - 模块说明补一句：写入检查必须在同一个写事务里（先查后写会被回收超过）——存储卡的任务；
   - 新增 4 个测试。
3. **开发期实测**（开发工作树，非治理）：22 个用例全过；`ruff`、`mypy` 干净。
4. **不做什么**：不改存储、不改任何其他文件、不读或返回 lease token、不改 `expires_at`、不推送（夜间推送由我在收口后另行完成并读 CI）、不合并 main。
5. **容忍规则**：沿用 M3-RACE 的同一条具名规则（事先声明）：rest 组里若恰有 r09 一个失败且同字节隔离重跑 3/3 通过则放行并记偏差；此前所有受治理卡均严格全绿（未使用）。
6. **演练事实（非治理，草稿工作树，不是正式证据）**：2026-10-16 在基线（卡 147 的提交）的临时工作树里跑了一遍本卡的快速门禁与判卷（原始输出在 `.auto-pm/reports/m3-v04r1b/gates_rehearsal/`）：22 个契约用例全过、模块导入不加载存储、静态检查、13 个真实变异全部被抓住并按字节还原、真实 pre-commit 钩子退出 0；九组回归用合成输出（卡 147 的受治理输出按期望增量调整）判卷，G1–G9 全 PASS，4 个反例变体判卷结果符合预期。演练不是正式证据，正式 Run 完整重跑。
