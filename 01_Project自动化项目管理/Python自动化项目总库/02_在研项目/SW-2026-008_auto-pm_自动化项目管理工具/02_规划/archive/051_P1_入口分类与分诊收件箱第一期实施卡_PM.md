## 2. 单一目标（用户故事与完成定义）

作为用户，我希望新事项有一个正规的“前台”：

1. **一条命令入箱，不打乱当前任务**：`pm inbox add` 把新需求、bug、想法、技术债连同分诊单记下，状态 `PROPOSED`；正在执行的 Mission、Work、Run、租约、检查点的字节不变；
2. **分诊单由机器把关**：缺取证、缺备选方案、紧急无客观判据、非紧急却要求打断、安全类紧急没有 `SAFE` 影响范围、取证文件不存在、同名未处理条目、建议驳回的条目被确认——全部被拒绝且不留痕；
3. **我确认的是精确内容**：`pm inbox confirm|reject` 必须给出条目的 `ticket_hash`、真实人类审批人与 `user-confirmation` 证据，模型或 Agent 自签被拒；
4. **确认后的条目转成按类归档的计划**：`pm plan --inbox-id` 把已确认条目建成范围卡，变更单的性质、领域、影响范围、紧急程度来自条目的分类；`pm plan` 与 `pm approve` 的完整形式不再写死 `DEF/SCPT/MODULE`，没有分类（`--kind` 或 `--inbox-id`）就拒绝；
5. **`pm resume` 同时显示收件箱**：待确认数、已确认待排数与最多 5 条队列（已确认在前，其次按建议处置的紧急程度），并且**不改变**当前任务的任何字段。

### 5.2 行为合同

**5.2.1 分类（`IntakeClassification`）**

| 分类 `--kind` | 含义 | 变更单性质 | 变更单紧急程度 |
|---|---|---|---|
| `iteration` | 正常迭代 | `OPT` | normal |
| `bug` | 缺陷修复 | `DEF` | normal |
| `change` | 功能变更：增加、修改、减少、冻结、移除 | `REQ` | normal |
| `urgent` | 紧急 | `EMRG` | urgent |
| `debt` | 技术债 | `OPT` | normal |

- `change` 必须带 `--change-action add|modify|reduce|freeze|remove`，其他分类不得带；
- 领域 `--domain` 必须是变更单规范的 8 个领域之一；缺省时按项目技术栈推断（`plc`→`PLC`，`python`→`SCPT`），推断不出就拒绝并要求显式给出；
- 影响范围 `--impact-scope` 可重复，必须是规范的 5 个范围之一；缺省 `MODULE`（以我的默认裁决：缺省值是显式写进合同的，不是隐藏写死）。

**5.2.2 分诊单（`TriageTicket`）与入箱规则**——全部由机器校验，任何一条不满足即拒绝，且不留任何行与事件：

1. 必填：用户原话、影响了什么、查重结论、取证、建议处置、理由、至少一个备选方案、成本与风险；可选：重复条目编号、需要用户决定的点；
2. **取证至少一条**，写法 `file:<相对路径>`、`cmd:<命令>`、`ledger:TD-…`、`chg:CHG-…`、`commit:<十六进制>`；`file:` 必须是安全的工作空间相对路径且**文件必须存在**；其余类型只校验写法（登记为 `TD-SW008-072`）；
3. 紧急：`urgent` 类必须给出客观判据 `--urgent-criterion safety|data_loss|blocks_all|wrong_output`（设备或人身安全、数据损坏或丢失、阻塞全部后续工作、已造成错误产出），其他类不得给；判据为 `safety` 时影响范围必须含 `SAFE`；
4. 建议处置 `--disposition interrupt_now|after_current|inbox_wait|reject`：只有 `urgent` 类可以 `interrupt_now`（“只有紧急能打断”）；`urgent` 类不得 `inbox_wait`；
5. **建议驳回的条目只能被驳回**：处置为 `reject` 的条目不能被确认（同意请用 `reject`，不同意请重新分诊）；
6. 项目必须存在；同一项目内**同名的未处理条目**（忽略大小写与空白差异）被拒绝，条目被驳回后可以重新提出；
7. 同一 `--request-id` 重放同一内容返回既有条目（`created=false`），内容不同则拒绝；并发入箱的编号不重不漏（`INBOX-<项目编号>-<4 位序号>`，每项目独立递增）。

**5.2.3 状态与确认**：`PROPOSED`（入箱）→ `CONFIRMED` 或 `REJECTED`（用户决定）；`CONFIRMED` → `PLANNED`（由 `pm plan --inbox-id` 转计划时原子完成）。`pm inbox confirm|reject <编号>` 必须给出 `--ticket-hash`（条目内容哈希，`add` 与 `show` 都会输出）、`--approver`（真实人类审批人，模型或 Agent 名字被拒）、`--approval-evidence-ref`（`user-confirmation:…` 外部证据）；哈希不符、状态不对均拒绝；同一决定重放是空操作。

**5.2.4 命令**：`pm inbox add|list|show|confirm|reject`；`pm inbox list` 缺省列出未处理的（`proposed`、`confirmed`），`--status` 可重复；输出为 JSON（`pm-inbox-item.v1`、`pm-inbox.v1`）。

**5.2.5 计划按类归档**：
- `pm plan` 与 `pm approve` 的**完整形式**必须有分类：`--kind`（与 `--change-action`、`--domain`、`--impact-scope`）或 `--inbox-id`；同一请求已绑定分类时（例如重放）可省略；已绑定不同分类则拒绝；
- `--inbox-id`：条目必须已确认、同项目；命令行给出的分类必须与条目一致；转计划时条目原子地变为 `PLANNED` 并记下计划的请求编号；一个条目只能供一个计划；
- 变更单：性质、领域、影响范围、紧急程度来自分类；参考信息追加 `intake_kind=…`、`change_action=…`（仅功能变更）、`intake_item=…`（仅来自条目）；
- 不变的部分：`--mission-id` 兼容路径不接受分类参数；按哈希批准已保存范围卡的短形式不接受分类参数（分类在 `plan` 时已绑定）；范围卡的 `plan_hash` 不含分类，既有草稿不受影响；
- **服务层的旧调用方**（驾驶舱桥、`api.py`）不带分类时，门面仍按旧默认建单——这是有意保留的兼容回落，登记为 `TD-SW008-070`，不在本卡改。

**5.2.6 `pm resume`**：`continuity-resume.v2` 增加 `intake` 字段（`intake-summary.v1`：`awaiting_confirmation`、`confirmed_waiting`、最多 5 条 `queue`，已确认在前，其次按建议处置紧急程度、再按编号）；文本输出在有条目时追加“收件箱”行；**其余所有字段不变**；`evidence_id` 仅在收件箱非空时才把摘要纳入，因此空收件箱的既有输出字节不变。

**5.2.7 存储**：两张新表 `intake_items`、`planning_draft_intake_bindings` 在首次写入时惰性创建，不进 `_DDL`、不改 schema 版本；**在从未初始化的库上拒绝写入且不创建任何表**（避免让后续初始化拒绝该库）；读取从不创建表；每次变化追加事件（`INTAKE_ITEM_RECORDED`、`INTAKE_ITEM_CONFIRMED|REJECTED`、`INTAKE_ITEM_PLANNED`、`PLANNING_DRAFT_INTAKE_BOUND`）。**任何收件箱操作不得改动 Mission、Work、Run、租约、检查点、交接表的任何一行。**

**5.2.8 既有测试的两处最小改动**：`tests/cli/test_pm_facade.py` 的 `_planning_args()` 与 `tests/cli/test_pm_pending_cards.py` 的 `SCOPE` 各在末尾追加 `--kind bug --domain SCPT`，使它们仍按旧语义（缺陷、SCPT）建单；其余既有测试字节不变。
