## 1. 背景与已核实事实（2026-10-21）

1. **为什么**：D08 三道交付后，用户要求把 IO 点表查重接成 `io-check` 命令。`pm plan --project-id SW-2026-010` 报“候选 CHG 已绑定其他 PlanningDraft”：项目下一个号 `CHG-SCPT-2026-004` 已被 SW-2026-009 的规划草稿绑定（本机账本：SW-2026-009 占 004、005、008～012）。规划草稿的号码绑定表 `planning_draft_chg_bindings.change_id` 全工作区唯一，而变更单号只要求项目内唯一；空跑测试线程曾预报（缺陷⑤）。
2. **做什么**：`ContinuityStore.reserve_planning_draft_change` 在候选号已被别的草稿绑定时，在同一事务里顺延到同一序列第一个未绑定的号（保留补零位宽），再绑定并返回；同一草稿重放仍返回原号；编号格式非法时拒绝。候选号由 `next_change_number` 取项目内最大号加一，更大的号在本项目也必然空闲。不改表结构、不迁移账本，旧版本可照常回退。新增 5 个测试。台账登记并偿还 TD-SW008-169，§3 追加卡 179 与 D07d 的变更单；WBS 写回（D08 已完成）。
3. **同类排查清单**（根因：变更单号按项目编号，但有几处仍按全工作区判断；逐条交审计核对）：
   1. 账本 `planning_draft_chg_bindings.change_id` 全工作区 UNIQUE（本次挡路）：**本卡修**，做法是预留时顺延到同序列第一个空号，不改表结构。为什么安全：候选号取自项目内最大号加一，顺延后的号仍大于项目内所有已用号，所以项目内必然唯一；全工作区唯一比需要的更严，只会让号码出现空档，不会撞号；不改约束就不需要账本迁移，旧版本（`1.3.3-a4506c3` 及更早）读同一个库照常工作，切换失败可直接回退。代价：号码可能有空档（如 SW-2026-010 跳过 004、005 直接用 006），已在台账写明。彻底改为“项目+号”的复合唯一要迁移账本、影响回退，留到 D09 后评估。账本里其余按单号的列（决策绑定的 change_id 等）没有唯一约束，不挡。
   2. 决策服务只在 `04_监控` 找变更单，模板项目用 `11_监控`（缺陷④）：**本卡不修**，D09 要合并的 `claude/d09-onboarding-blockers`（N2 `15a481dd`、N3）已修并经空跑线程端到端验证，避免两处改同一段代码；随 D09 合并关闭。
   3. 带 `--pid` 查变更单，项目内没有或项目定位失败时回退全工作区（`ChangeFileLocator.find_change_file`），会把别的项目的同号单当成本项目的读写：**本卡修**，带 `--pid` 时只在本项目找，找不到就返回不存在；原有一条测试按旧行为写的，同步改为新行为。
   4. 不带 `--pid` 时遇到多个项目的同号单不拒绝、取第一个（缺陷⑦）：**本卡不修**。现在几乎每个号在多个项目里都有（例如 CHG-SCPT-2026-002 全工作区 254 份），一旦改成拒绝，所有不带 `--pid` 的变更单命令都会报错，影响用户和各 agent 的日常用法，属于要用户定的行为变化；D08 提示词已要求所有变更单命令带 `--pid`。登记为 D09 后的待办卡（建议做法：不带 `--pid` 且有多个同号时拒绝并列出候选项目）。
   5. 收口写证据与实施回填按全工作区找变更单：卡 177 已修（按项目）。
4. **已验证**：开发工作树里新测试 5 条、账本规划测试与 PM 门面、待批范围卡相关测试共 147 条通过；变更单相关测试 263 条通过；G3 三个测试文件 53 条通过；ruff、mypy 干净。
