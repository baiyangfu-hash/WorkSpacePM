### 2.3 迭代规则（V1.0 第 5 节，接手的 agent 照这个做）


1. **先定位**：从控制根执行 `main.py pm orient <PID> --json`（读 `cockpit-entry`）。没有匹配的 Work／Run／Decision，不得修改。
2. **按“设计→计划→实现→合并”走**：设计与计划只读、可并行；实现要授权的 Work 和带 lease 的 Run；合并只走 PR，用 Merge commit。
3. **选之前先核现状**：用 EV1-B01 的办法，先看 `main` 上有没有、`009_CLI命令参考.md` 里有没有、技术债台账里是不是已有；已落地的不重做，部署版没有的先标“未部署”。
4. **做的与审的分开**：写 PR 的不审它；审计用 `reviews/tools/audit_pr.py` 和 `reviews/21_audit_checklist.md`（AUD-001）。
5. **“完成”要附证据**：提交号、对账结果或门禁结果，至少一样；拿不出就写“未核实”（FIX-001）。
6. **一个 PR 一类事**：只改文字的 PR 不碰 `auto_pm/`、`templates/`、`scripts/`、`tests/`，保证门禁载荷等价；受保护文件要用户原话，规则文件的 PR 还要用户本人评论“规则批准 <头提交号>”。
7. **不得越过用户**：删除、切换、reset、`--force`、`worktree remove`、`rm` 只认用户原话；agent 不索要、不代填批准口令。
8. **发现新问题**：先记进遗留表或技术债台账，附证据；不要在不相干的 PR 里顺手改。
9. **卡验收合并后随收尾归档**：一张实施卡验收并合并后，在收尾时把卡文件移入 `02_规划/archive/`，同一个 PR 修引用并更新 `00_实施卡索引.md`，不再让已完成的卡堆在 `02_规划/` 里。卡文件在受保护路径时，该 PR 要用户的规则批准。
