## 4. 登记（唯一真源）

文件 `SYS-2026-001_WorkspaceGovernance/project_archive.jsonl`，**JSON Lines：一行一个事件，末尾换行**。原稿用“一个 JSON 对象里放 events 数组”，追加会改动结尾的 `]}`，“旧内容是新内容前缀”的检查成立不了（审计 582 §四.1），改为本格式。

```
{"seq":1,"project_id":"DJ-2026-005","action":"archive","project_root":"0100_PLC自动化/DJ-2026-005","at_utc":"…Z","by":"user","reason":"…","evidence_ref":"user-confirmation:…","head_commit":"<sha>","tree_oid":"<sha1>","tree_digest":"<sha256 of git ls-tree -r>"}
{"seq":2,"project_id":"DJ-2026-005","action":"unarchive", …, "seal_check":"match|mismatch|missing"}
```

- 逐行解析：`seq` 全文件连续（**顺序以 `seq` 为准**）、`at_utc` 只要求能解析成 UTC，**不要求不倒退**（两台电脑时钟偏差造成的合法追加不能判成损坏，否则触发下面的死锁）、`action` 合法（**在用时才能 archive，已封时才能 unarchive**——已封状态再追加 archive＝换封条，拒）。当前状态＝该项目最后一条事件的 action。
- **`project_root` 校验（防自锁，复审 583 P1-a）**：必须**等于该 `project_id` 在 `workspace_registry.json` 里登记的路径**，且在允许前缀 `0100_PLC自动化/` 之下，且不在禁区（`0100_PLC自动化/01_SharedLibraries`——其它工程依赖、`00_*` 通用目录、`_archive`）。因此 `""`、`.`、`SYS-2026-001_WorkspaceGovernance`、`.github`、`reviews/tools`、`00_Infrastructure/auto_pm` 之类的 archive 事件一律是损坏。注意：`DJ-2026-009_汇川换型改造` 目前**没有**登记在 `workspace_registry.json`，要归档它必须先 `project register`，这是前置，不在本卡。封存本身不需要 PR 批准（协调者裁决），所以这条校验是唯一防“任意追加一条事件把目录封死”的机械门。
- **损坏时的范围与出口（复审 583 P1-a）**：整份无法解析时，被拒写入的范围＝登记里**出现过**的项目（逐行尽力提取 `project_id`）加上无法判定时一律拒写 `0100_PLC自动化/` 下各工程；控制面（SW-2026-008、SYS-2026-001、`reviews/`、`.github/`、`00_Infrastructure/`）不受影响。**修复出口**：①提交钩子允许“只改登记文件”的提交；②`archive-gate` 在“基线登记损坏”模式下，只放行“只改登记文件且结果能完整解析”的 PR，并要求用户本人评论 `登记修复批准 <PR 当前头提交前 12 位>`。登记文件本身**不算“已归档文件夹”**（它在 `SYS-2026-001_WorkspaceGovernance/` 里，永远只由下面第 3 条规则管），解封 PR 与修复 archive-gate 的 PR 因此不会被自己锁住。
- **只追加**检查：新文件字节以旧文件字节为前缀，且新增的行逐行通过解析。跨电脑并发追加会合并冲突，人工解决。
- **读取取最严者**：命令层、钩子、CI 同一规则——工作区、HEAD、`origin/main` 任一说“已归档”就拒；**未提交的解封不放行**。文件不存在＝没有事件（正常）；文件存在但读不出/损坏＝按已归档拒；文件在 HEAD 里有而被删除＝篡改，拒。
- 登记进受保护清单（`PROTECTED_PATTERNS`，并保持 `audit_pr` / `pr_scope_check` / `rules_approval_check` 三份清单同步测试 `test_protected_lists_in_sync` 通过）。
- **禁止归档**：控制面项目 `SW-2026-008`（会把所有“项目无关”写命令锁死）和 `SYS-2026-001`（登记本身在它的文件夹里）。命令和解析器两处都拒。
- 显示用的阶段以登记为准；工程自写的 `phase: archived` 但登记里没有，**不算归档**，`project show` 提示“未生效”。

## 5. 命令（控制根执行）

| 命令 | 谁 | 作用 |
|---|---|---|
| `project archive <PID> --reason … --approval-evidence-ref … [--dry-run]` | 用户本人（agent 标记拒、口令启用则终端输口令） | 封存；**落到新分支并自动单独提交**（见下“分支与 PR”）；输出明说“只核对了本机账本，未核对其它电脑上的卡” |
| `project unarchive <PID> --reason … --approval-evidence-ref …` | 同上 | 开封（同样落新分支；**合并到 main 并有“解封批准”评论后才全局生效**） |
| `project archive-status [PID] [--json]` | 只读 | 列已归档；单个项目复核封条（第 8 节） |

agent 想归档：只能 `pm inbox add` 记用户原话，把完整命令交给用户。

**分支与 PR 的落地方式（复审 583 P2-c）**：控制根停在 main，本地 main 受保护、不能直接推，自动提交若落在 main 会让控制根 main 与 origin/main 分叉。所以命令**不碰控制根的 main 和工作区**：在 `.auto-pm/worktrees/archive-<PID>` 用 `git worktree add` 从最新 `origin/main`（先短超时 `git fetch origin main`）建分支 `archive/<PID>`，在那里追加登记并**单独提交**（只含登记文件，走正常 pre-commit，不得 `--no-verify`），任一步失败则整个工位和分支一起清掉、控制根不变。命令末尾打印：推送命令、开 PR 的命令（沿用现有 `pr open`），并明说：**“本地已封，未合并到 main，其它电脑与 CI 尚未生效”**。谁推、谁开 PR：用户本人（或用户让 agent 推并开 PR）；用户本人合并后才算全局生效；合并后 `worktree sweep` 清理。
本地命令读“已归档”时除工作区、HEAD、`origin/main` 外，还读**尚未合并的本地分支 `archive/<PID>`**（`git show` 读登记），所以本地立刻拒写；**未合并的 unarchive 分支不放行**，只有合并进 main 才解。

## 8. 封条复核与解除归档

**封条复核（`archive-status`，审计 582 §二）**：
1. `git rev-parse HEAD:<project_root>` 与 `origin/main:<project_root>` **都算**，都与登记的 `tree_oid` 比；只算当前签出分支会在旧分支上误报“一致”。
2. **同时跑** `git status --porcelain --untracked-files=all -- <文件夹>`：树哈希只覆盖 HEAD 里已提交的跟踪文件，未提交改动、未跟踪文件要靠它报出；输出明说“被忽略的文件不受保护”。
3. 文件夹缺失或被改名＝“封条文件夹不见了”，**不能**因 `rev-parse` 失败当成“没动过”。
4. `tree_oid` 与登记在同一份可编辑文件里，改文件再顺手改 `tree_oid` 本地检测不到；防它靠“只追加”＋ `archive-gate` ＋ archive 事件的 `tree_oid` 必须等于其提交之后的 `HEAD:<project_root>`（CI 里为合并引用）且该提交/PR 工程文件夹零改动。再存一份 `tree_digest`（`git ls-tree -r` 输出的 sha256），不单靠 SHA-1。

**解除归档**：用户本人运行 `project unarchive` → 追加 `unarchive` 事件（含封条复核结果）→ 单独提交 → 推送开 PR → 用户在 PR 评论 `解封批准 <头前12位>` → `archive-gate` 变绿 → 用户本人合并 → 之后才能开卡改工程。无 AI、断网时：本地手工追加并提交，**本地可用，但推送后 CI 才认**；本地无法区分是人还是 agent，所以离线手册里**不写成“只有用户”**（该手册是否受 rules-gate 管，开工前查 `rules_approval_check.RULE_PATTERNS` 再定）。
