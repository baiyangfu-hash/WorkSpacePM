## 1. 背景与已核实事实（2026-10-16）

1. **为什么**：WBS 的 V04-R1（受控租约撤销与 fencing 真实进程演练）在 M3 内承诺保留，按接力文档第 28 节拆为 3 张核心卡：契约 → 存储接入 → 真实进程演练。设计草稿 `.auto-pm/reports/V04R1_DESIGN_20261016.md`（本卡是第 1 张）。
2. **读代码得到的事实**（`continuity_store.py`）：lease 已有 `version`，续租、移交、过期结算、终态围栏都带期望版本做比较并发控制，所以“epoch”不需要新增字段或 schema 迁移；旧持有者的写入已被 owner、token 与过期检查挡住一大半；真正缺的是：已启动 Run 的进程指纹证明、并非所有写入都带期望版本、没有真实进程的演练证据。
3. **做什么**（新增 2 个文件，不改任何已有文件；见 §4）：纯契约模块 `lease_reclaim.py` 与它的 18 个测试：
   - **epoch = lease version**，按 Run 隔离、严格递增，只在授予、续租、移交时由授予方增加（`next_epoch`）；
   - **进程判定**（`judge_process`）：记录的指纹（主机、pid、启动时间、可执行文件与命令行哈希）对照现场观察——pid 不存在或 pid 被别的进程复用（启动时间不同）= 已证明不在；启动时间、可执行文件与命令行哈希都相同 = 仍在运行；跨主机、没有记录指纹、读不到进程表、同启动时间但哈希缺失或不同 = **无法判断**；
   - **回收判定**（`decide_reclaim`）：持有者进程仍在运行 → 拒绝；无法判断 → **PENDING**，绝不抢占未知进程；已证明不在 → 租约已过期（加 2 分钟宽限）才允许，租约未过期时只有用户 Decision 强制才允许；Decision 永远不能强制回收仍在运行或无法判断的持有者；
   - **写入 epoch 检查**（`check_write_epoch`）：旧 epoch 拒绝、超前 epoch 拒绝、非正整数拒绝、缺 epoch 仅在兼容期内接受并警告；
   - 契约与存储位置无关：以后 lease 改由 Git 引用仲裁（M3-COLLAB）时，Git 引用里的 version 就是这里的 epoch。
4. **开发期实测**（开发工作树，非治理）：18 个用例全过；`tests/contracts` 整个目录 234 个通过、1 个跳过；`ruff` 与 `mypy` 对新模块干净；模块不导入 `continuity_store`。
5. **不做什么**：不改存储（第 2 张卡，核心档）、不改任何已有文件、不读或返回 lease token、不改 `expires_at`、不跑真实进程探测（第 3 张卡）、不推送、不合并 main。
6. **容忍规则**：沿用 M3-RACE 的同一条具名规则（事先声明）：rest 组里若恰有 r09 一个失败且同字节隔离重跑 3/3 通过则放行并记偏差；此前所有受治理卡均严格全绿（未使用）。
7. **演练事实（非治理，草稿工作树，不是正式证据）**：2026-10-16 在基线（卡 146 的提交）的临时工作树里跑了一遍本卡的快速门禁与判卷（原始输出在 `.auto-pm/reports/m3-v04r1a/gates_rehearsal/`）：18 个契约用例全过、模块导入不加载存储、静态检查、10 个真实变异全部被抓住并按字节还原、真实 pre-commit 钩子退出 0；九组回归用合成输出（卡 144 的受治理输出按期望增量调整）判卷，G1–G9 全 PASS，4 个反例变体判卷结果符合预期。**演练中第一次有一个变异（可执行文件哈希缺失被当作仍在运行）没被杀死，说明测试漏了“两边哈希都缺失”的情形（None 等于 None）；已补一个用例后重新演练，全部杀死。**演练不是正式证据，正式 Run 完整重跑。
