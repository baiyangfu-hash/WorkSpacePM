# 需求草案：入口分类与分诊队列、一键换 Agent、薄 /pm 入口

> 状态：`DRAFT v0.3`（2026-10-05；用户已裁决 5 个问题，见 §7；§7.5 记录“功能变更”的口径修订；§7 的修订优先于 §3 的对应条文；定稿后提升为 `02_规划` 下的需求说明，并在 WBS 修订里登记任务）
> 对应台账：`TD-SW008-066`（入口分类与分诊队列）、`063`（一键换 Agent）、`067`（可安装的薄入口）；关联 `064`、`065`（口令传法与明文存库）
> 起因：用户 2026-10-04 说明——推进 WBS 或实施卡时不断插入新需求、新 bug 并新开任务，任务累积后“当前该做哪个、下一步是什么”说不清，这是重构 PM-Flow 的根因。

## 1. 目标（一句话）

任何时刻，任何一个 Agent 在任何一个 IDE 里敲一条命令，都能得到同一个答案：**这个项目现在在做哪一件事、下一步是什么、还有哪些挂着的和等着排的**；冒出新的需求或 bug 时，一条命令入箱，不打乱当前这件事；要换 Agent 时，一条命令交接，不需要人搬口令。

## 2. 我读到的现状（代码事实，基线 `edeeead9`）

| 已有的零件 | 缺的 |
|---|---|
| Work 有种类：`WBS`、`BUG`、`DEBT`、`TEST`、`GOVERNANCE`；变更单有性质：`REQ`（需求）、`DEF`（缺陷）、`OPT`（优化）、`CFG`（配置）、`EMRG`（紧急）与 8 个技术领域 | 入口 `pm plan` 建单时把领域写死为 `SCPT`、性质写死为 `DEF`、范围写死为 `MODULE`，不能表达“正常迭代、bug 修复、功能增加” |
| Mission（面向用户的需求）与它的根 Work、Run、检查点、租约、状态（含 `BLOCKED`） | 没有优先级字段（全库搜不到）；没有“当前焦点”“挂起”“待分诊”的概念 |
| `pm resume` 在多个活跃 Mission 或 Work 时返回 `MULTIPLE_ACTIVE_MISSIONS` / `MULTIPLE_ACTIVE_WORKS` 并按编号排序，要求你显式指定 | 只会“拒绝猜”，不会“建议先做哪个”；也不告诉你还有多少挂着、多少等着排 |
| 台账（`TD-SW008-NNN`）已是新问题的人工登记处，规则是“新问题先登记，不得只留在聊天里” | 登记在文档里，机器侧没有对应的收件箱记录 |
| 检查点绑定交接（`handoff.v2`）、租约围栏、受控撤销都已验收 | 项目管理层没有换 Agent 入口；底层命令要把旧口令写在命令行里；口令明文存库 |
| `AGENTS.md` 与各 IDE 规则文件是统一的知识入口 | 没有可安装的 `/pm`；旧 `pm-workflow` 已按你的要求卸载，新入口不得复活它 |

## 3. 三条需求

### N1 入口分类与分诊队列（根因，优先级最高）

**N1.1 一个项目、一个当前焦点。** 任何时刻每个项目至多一个“当前焦点”（一个进行中的 Mission）。`pm resume` 永远先回答它；没有焦点时回答“建议下一个做什么”。

**N1.2 收件箱：任何新东西先入箱，不直接成任务，也不改当前卡。** 把我们现在靠纪律做的事产品化。一条命令入箱，必须选类：

| 你的说法 | 入箱类别 | 对应变更单性质 | 对应 Work 种类 |
|---|---|---|---|
| 正常迭代（按计划往下做） | `iteration` | `OPT` | `WBS` |
| bug 修复 | `bug` | `DEF` | `BUG` |
| 功能变更（增加、修改、减少、冻结或移除某项功能；见 §7.5） | `change` | `REQ` | `WBS` |
| 紧急 | `urgent` | `EMRG` | 按内容 |
| 技术债（发现的问题） | `debt` | `OPT` | `DEBT`（同时在台账登记，保持台账为人工正本） |

领域（PLC、脚本、文档……）不再写死，从项目登记里取；影响范围由入箱人选，缺省按文件范围推算。

**N1.3 分诊：系统提议、你一键确认，系统不擅自改焦点。** 默认排序规则（可改）：`urgent` ＞ 阻塞当前焦点的 `bug` ＞ 其他 `bug` ＞ `iteration`（按 WBS 顺序）＞ `change`（须你批准排期，不自动进队）；同级先到先得。分诊给出“建议顺序 + 理由”，你确认后才生效。

**N1.4 插队与挂起：只有 `urgent` 能打断当前焦点，且须你确认。** 打断时先对当前 Run 做一次检查点，再把当前 Mission 标为“挂起”（复用现有 `BLOCKED` 并写明原因 `PARKED`，不新增状态机分支），紧急事项成为新的焦点；它收口后 `pm resume` 提示“恢复被挂起的那件事”，从检查点续做。每个项目最多 3 个挂起，超出强制先收口一个。

**N1.5 `pm resume` 的输出统一为：** 当前焦点与下一步合法动作；挂起列表（最近的在前）；收件箱按类的数量与最急的一条；冲突（有就列出，并给出建议的处置，不再只丢一个错误码）。

**N1.6 命令草图（不是最终名字）：** `pm inbox add --kind bug|iteration|change|urgent|debt --title …`、`pm inbox`（看箱）、`pm triage`（提议并确认顺序）、`pm focus`（看或设焦点）、`pm park`（挂起当前焦点）、`pm resume`（接着做什么）；`pm plan` 增加 `--kind`，不再写死 `DEF`/`SCPT`/`MODULE`。

**典型场景：** 推进实施卡时冒出新 bug → Agent 执行 `pm inbox add --kind bug`（当前卡的范围、Run、租约一字不动）→ 卡收口后你敲 `pm triage` 看建议顺序并确认 → 下一件事自动成为焦点。若是线上紧急 → `pm park`（先留检查点）→ 紧急事项做完 → `pm resume` 回到原来那张卡。

### N2 一键换 Agent（`TD-SW008-063`）

**N2.1 一条命令：** `pm handoff --to <codex|trae|cursor|manual>`。系统在当前 Run 上做检查点、生成 `handoff.v2`，并生成一份给接收方的“接手包”。

**N2.2 口令不上命令行、不明文存库、不由人搬运整份 JSON：** 旧口令由项目管理这一侧的进程在内存里使用（不落命令行与 shell 历史）；接收方拿到的是一个**一次性接手码**（短时有效、用后作废、库里只存哈希）；接收方在自己的 IDE 里执行 `pm resume --claim <接手码>`，系统校验后自动给它新租约、让旧 owner 之后的写入被围栏拒绝（这一步 V03 已经用真实进程证明过）。

**N2.3 旧进程怎么办：** 旧 Agent 的写入立即被拒；如果旧进程还在跑，系统记录“待回收”并提示，不假装已停（沿用 V04-R0 的“无法证明回收就 PENDING”原则）。

**N2.4 接手包的内容：** 接手码、一行 `pm resume` 命令、检查点编号与摘要、当前焦点的范围与下一步；不含口令明文。

**N2.5 关联修补：** 所有带口令的命令改为从环境变量读取（`TD-SW008-064`）；口令改存哈希（`065`）——这两条是 N2 的前置，不是可选项。

**N2.6 诚实边界：** “另一个模型读了交接能不能接着干”只能靠真实切换演练验证，建议部署后用一次真实的 GPT 或 Cursor 切换作为验收证据；`pm execute` 目前只会自己启动 `codex exec`，其他 IDE 里的 Agent 由你自己打开，系统不假装能替你启动。

### N3 薄 `/pm` 入口（`TD-SW008-067`）

**N3.1 形态：** 每个 IDE 一个很薄的入口文件（Trae 的技能、Cursor 的命令、Codex 的提示），内容只有三件事：先运行 `pm resume`；按它的输出做；冒出新事就 `pm inbox add`。**不含业务逻辑、不让 Agent 手填表单、不绕过 `pm` 命令**；不复活 `pm-workflow`。

**N3.2 单一真源与防漂移：** 入口文件由一个脚本从同一份模板生成并校验（死链、命令名是否存在），各 IDE 一份，改动只改模板；这样不会再出现“好几份技能各说各话”。

**N3.3 安装由你授权：** `.trae/` 属 Trae 生态，生成和安装每个 IDE 的入口都需要你逐个授权；技能 README（`TD-SW008-069`）同时改写，不再推荐旧技能。

## 4. 验收标准（草案，可机器验证）

1. 冒出新 bug 时一条命令入箱；当前焦点的 owned paths、Run、租约字节不变；
2. `pm plan --kind bug|iteration|feature` 建出的变更单性质分别为 `DEF`、`OPT`、`REQ`，领域取自项目登记，不再恒为 `SCPT`/`DEF`；
3. `pm triage` 的建议顺序符合规则，且未经你确认不改变焦点；
4. 紧急插队后原任务可从检查点续做、不丢文件与证据；每个项目超过 3 个挂起被拒绝；
5. 任一时刻 `pm resume` 要么给出唯一当前焦点，要么明确要求选择并给出建议，不会猜；
6. 换 Agent：整个过程命令行与 shell 历史里没有口令；旧 owner 之后的写入被拒；接手码一次有效、过期无效；
7. 在一个新的 IDE 里装薄入口后，一句 `/pm` 得到当前焦点与下一步；入口文件无死链、命令名都存在。

### 7.2 N1 修订：分诊台模型（PM 接诊）

**角色：** 用户只对接“产品型项目经理”——即主 Agent 的 PM 治理角色（不是执行 Agent）。用户用自然语言说需求、问题、想法；PM 接诊并出**分诊单**；执行 Agent 只接批准后的实施卡。PM 不写代码，需要核实时下到项目侧（只读勘测，必要时派只读子代理），这与 AGENTS.md 的阶段 0 一致。

**接诊流程：**
1. 复述与澄清：只问代码库里查不到的（先查再问）；
2. 只读取证：查代码、台账、WBS、收件箱——是不是重复？影响哪里？能不能复现？牵涉哪些文件与下游？
3. 分类：正常迭代 / bug 修复 / 功能增加 / 紧急 / 技术债，并判断紧急度；
4. 出分诊单（下表）；
5. 用户一键确认或修改；
6. 系统据此入箱、排期或插队。

**分诊单字段（缺“取证摘要”不得入单，由机器校验）：** 用户原话；分类；紧急度与理由（紧急的客观判据：设备或人身安全、数据损坏或丢失、阻塞全部后续工作、已造成错误产出）；影响（项目、WBS 行、文件、依赖）；重复检查结论；取证摘要（命令、文件、数字）；建议处置（立即插队 / 排在某张卡之后 / 进收件箱待排 / 拒绝并说明）；理由与备选方案；成本与风险估计；需要用户决定的点。

**用户主动分类时：** PM 必须复核，有异议如实提出，不盲从也不抬杠；用户有最终决定权。

**系统侧职责（机器强制，不靠提示词）：** 记录分诊单；每个项目一个当前焦点；未经确认不改焦点；紧急插队须用户确认；挂起上限 3；`pm resume` 展示当前、挂起、待分诊与建议。

### 7.3 N2 修订：定位与两种接手顺序

新增只读命令（名字待定，暂称 `pm orient`）：输出接收方需要的**定位信息**——控制根路径、主线分支与尖端提交、当前焦点的隔离工作树路径、哪些目录不能动（例如控制根里的脏改动）、当前所处的 WBS 位置与卡、挂起与收件箱概况。
- **顺序 A（推荐）先看后领：** 接收方先 `pm orient` 了解全貌（不需要口令），你再把接手码贴给它，它执行 `pm resume --claim <接手码>`；
- **顺序 B 先领后看：** 你先贴接手码，领取成功后自动回显定位信息；
- 接手码绑定具体的 Run 与工作树，防止领错；一次有效、短时有效、库里只存哈希。

### 7.5 “功能增加”改称“功能变更”（用户 2026-10-05 重申）

用户指出：功能增加也可能是减少或者冻结，总之属于功能变更。因此分类名由 `feature` 改为 `change`（功能变更），并必须写明动作：`add` 增加、`modify` 修改、`reduce` 减少、`freeze` 冻结、`remove` 移除（后三者是我补全的常见动作，可再增减）。五种动作都归档为变更单性质 `REQ`（需求变更：客户新增功能、工艺调整或范围扩展）；动作写入变更单的参考信息，便于事后检索。动作只用于 `change`，其他分类不得带动作。
