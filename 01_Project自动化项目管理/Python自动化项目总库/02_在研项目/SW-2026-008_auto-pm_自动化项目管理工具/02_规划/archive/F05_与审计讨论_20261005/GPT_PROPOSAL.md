**推荐方案 B：保留 Mission 的业务生命周期，增加结构化调度状态、唯一当前焦点与持久化切换事务。挂起对象是 Mission；分诊条目负责保存尚未进入执行授权链的需求。**

## 2. 两个方案共同遵守的不变量

1. 当前焦点、业务生命周期、是否允许执行必须分别表达。唯一焦点是调度权，不是新的业务授权。
2. 普通 BLOCKED 不自动释放当前槽；旧 BLOCKED 不按标题、原因字符串或聊天内容自动迁移成挂起。
3. 每项目只有一个未完成的焦点切换操作。确认绑定项目、原/目标事项、分诊单指纹、当前版本与操作标识；两个 Agent 并发确认不能各自生效。
4. 被挂起对象的原 Mission、Work、Run、Checkpoint、授权与文件证据均保留。Run 终态不重开；恢复后若需要新的执行，创建新 Run 和新租约。单纯回到待验收界面不制造空 Run。
5. Checkpoint、lease 到期、handoff 和 Run 行政结算都不能证明操作系统进程已停止。有效围栏阻止受治理接口写入，不能撤销仍存活进程的文件写权限。
6. 安全停止未证实，切换保持 PENDING，旧焦点仍可定位但禁止正常执行；新 urgent 可继续分诊、规划和报批，不能先启动执行或靠“另一个工作树”忽略旧进程。
7. 授权过期不阻止安全停止，但不得因此延长或恢复执行授权。恢复必须重新核验当前卡、CHG/Decision、范围、候选与证据。
8. 查看、建议、分诊确认、调度确认、实施授权和最终验收保持分离。一个用户确认可以在明确合同中授权整个受控切换，无须每个内部步骤再问一次。

三槽针对已经建立的 Mission；尚未建立 Mission 的分诊条目/PlanningDraft 留在待排区，不占槽。DRAFT/AWAITING_APPROVAL 的 Mission 若需挂起，保留其规划阶段与原 root Work 要求；没有 Run 就不制造 Checkpoint。方案 A 的 SUSPENDED 校验须按 suspended_from_state 判断 root Work 是否必需，不能一律强塞 root Work；方案 B 保留原业务状态即可表达。验收后与终止对象不列为挂起。

## 3. 方案 A：新增 Mission 生命周期状态 SUSPENDED

| 用户要求 | 方案 A |
|---|---|
| ① 挂起什么 | 挂起 Mission，新增 SUSPENDED。保存 suspended_from_state 与业务阻挡信息；紧急事项使用自己的 Mission/授权。分诊条目仍是来源记录。 |
| ② 存储、迁移、旧运行时 | 升级 Mission 合同与存储 schema；唯一索引显式排除 SUSPENDED，同时修改列表、状态机、聚合和 Resume。增加项目焦点、三个槽位及切换日志。旧枚举不能解析新状态，旧写入口也并非全局检查 schema；必须执行 §6 的升级隔离，不能与 1.3.3-a808fa8 同库混写。 |
| ③ Work/Run/lease | 采用 §5 的停止与围栏协议。SUSPENDED 只是业务对象的暂停标记，不直接杀进程或释放租约。Work 使用结构化调度 hold；旧 Run 按事实合法终态，终态与 lease 围栏原子提交。 |
| ④ 上限、恢复 | 三槽限额含尚未提交的预留。恢复时校验原状态、现存业务阻挡、授权和 Checkpoint；不能简单 SUSPENDED→ACTIVE。先前待验收则恢复待验收，先前业务 BLOCKED 且问题仍在则仍受阻。 |
| ⑤ resume / orient | 显示“挂起前状态 + 挂起原因 + 是否可恢复 + 缺少条件”。必须升级 schema/枚举消费者；显式选中挂起 Mission 只查看，不隐式切回焦点。 |
| ⑥ V05 前接口与风险 | Mission v1 的状态集合、生命周期迁移、过期授权下的安全停止例外、Work→Mission 聚合、事件和 UI 均受影响。必须保护 SUSPENDED 不被异步聚合覆盖。实现概念直观，但生命周期开始同时承担调度和业务进度。 |

**可行性：**能够完整实现需求，适合明确把“暂停”定义为 Mission 生命周期的一等阶段的产品。

**主要代价：**ACTIVE、业务 BLOCKED、ACCEPTANCE_PENDING 三种状态均可能挂起，恢复仍需保存另一份原状态；未来加入其他调度状态时容易扩大状态组合。它同样需要切换事务与旧运行时隔离，并不只是多加一个枚举值。

## 4. 方案 B：业务生命周期与调度状态分开（推荐）

| 用户要求 | 方案 B |
|---|---|
| ① 挂起什么 | 挂起 Mission 的调度资格。业务状态仍表示该目标所处阶段；调度维度区分 RESIDENT（占当前处理槽）与 PARKED。ACTIVE + PARKED 表示“目标仍待履行，执行调度权已收回”，界面不能将其显示为正在执行。 |
| ② 存储、迁移、旧运行时 | 在 Mission 增加结构化调度字段，并增加 project_focus、park_slots、switch_operations 等受同一 Store 事务管理的记录；必要的 Work hold 是结构化记录，不是自由文本。新索引只允许一个 RESIDENT 且业务未释放名额的 Mission。已有对象迁移为 RESIDENT，绝不自动识别 PARKED。按 §6 升级，禁止旧版本同库混写。 |
| ③ Work/Run/lease | 采用 §5。调度 hold 阻止创建/启动/重试/正常回写，也由底层服务检查。Work 只走现有合法状态迁移；不能强行让 VERIFYING→BLOCKED。若沿用 Work BLOCKED 承载暂停，必须标明纯调度原因，保存其他业务阻挡；聚合不能把纯调度 hold 当成业务失败。 |
| ④ 上限、恢复 | 三槽事务限制；恢复只清除本次调度 hold，不消除原业务阻挡或恢复过期授权。保留原 Mission/Work，执行需要时用新 Run。待验收 Mission 在执行已安全退出、证据冻结且无收尾写入时可挂起，恢复后先校验验收证据。 |
| ⑤ resume / orient | 共用一个带版本的项目视图：当前焦点、切换中操作、三个挂起槽、业务状态、可执行性、恢复条件、收件箱、其他冲突。业务 BLOCKED 与人为挂起分别解释。 |
| ⑥ V05 前接口与风险 | Mission 的业务状态不再承担队列含义，但增加了新的调度合同。创建 Mission、派发、恢复、显式 Work/Run 命令及自动聚合必须共同遵守；仅改 GUI 或查询过滤不够。主要风险是遗漏绕过调度守卫的底层写入口，以及冗余投影不一致。 |

### 4.1 建议固定的数据职责

以下名称是设计名称，尚非已有 API 或已批准 schema。

| 数据 | 唯一职责与约束 |
|---|---|
| Mission 调度字段 | 标识 RESIDENT/PARKED；不得只靠 reason="PARKED" 判定。生命周期终态/验收后对象不占执行槽，也不计入三个挂起。 |
| project_focus | 每项目一行，保存当前 Mission、单调 version、未完成 switch_operation；焦点必须指向本项目 RESIDENT，或在无当前对象时为空。 |
| park_slots | 主键为 project_id + slot，slot 只能是1、2、3；同一 Mission 不能占两槽。占用与预留在同一槽记录，不能分别统计成两个各三条的集合。 |
| switch_operations | 保存确认引用、原/目标对象、预期版本、槽位计划、阶段、停止与 Checkpoint 证据、幂等键及结果；阶段包含准备、等待安全停止、待人工处置、提交、终止。恢复操作进程不等于恢复业务执行。 |
| Work 调度 hold / 停放回执 | 绑定 Mission、operation 与确切 Work/Run 集合，区分调度阻挡和业务阻挡；保存必要的前态、Checkpoint、候选快照与工作树定位。不得存租约明文。 |

索引的目标语义是：同项目中，“调度为 RESIDENT”且“生命周期不在 ACCEPTED/CLOSED/CANCELLED”的 Mission 至多一个。新索引必须通过显式迁移替换；修改 CREATE INDEX IF NOT EXISTS 的文本不会替换旧定义。

该索引只保证数量，不保证安全停止、授权或焦点一致。创建 Mission 必须与占槽/焦点记录协调；root Work、子 Work 和调度 hold 的归属必须可证明。历史 Work 归属不明时报告冲突，不能把同项目的所有 Work 都认作当前 Mission 的子项。

**序列化与过期授权：**业务 Mission 字段和调度快照分层读取，Store 显式映射字段，不能继续把新增列的 SELECT * 原样交给严格的 mission.v1 DTO。业务 version/updated_at 与调度 version/updated_at 分开维护，切换同时核对两组版本。纯调度安全停止不伪造业务更新时间、不延长 AuthorityEnvelope；它记录自己的真实操作时间。现有 Mission 合同只允许 BLOCKED 的业务更新时间超过授权有效期，因此方案 A 必须增加受限的 SUSPENDED 安全停止例外，方案 B 则用独立调度记录完成收权。两者均须在动作入口按当前时间验证重新执行的授权，不能从旧 DTO 可读推导“仍有权执行”。

### 4.2 三个槽与恢复规则

- 新 urgent 替换当前焦点：先预留一个空槽，再做任何不可逆的停止动作；满三槽即拒绝本次新增挂起。不能先制造第四个再补救。
- 恢复已有挂起 Mission：通常要求当前事项已完成必要收尾，或当前无焦点；建议最近挂起且满足条件的事项，恢复仍经明确确认。
- 若当前事项仍未收口，恢复目标也必须满足“urgent + 用户确认”的打断规则。槽位交换本身不授予插队权。
- 合法交换可让当前事项占用目标释放的同一个槽；准备阶段锁定交换计划，最终事务交换，不要求额外第四槽，也不暂时放松上限。
- BLOCKED 但没有有效停放回执的 Mission 仍占当前槽。授权失效、文件漂移、未回收进程、缺依赖等均显示具体不可恢复原因；只清除已解决的阻挡。
- 取消或收口一个挂起事项应走自己的治理路径并释放槽。不能仅删除列表项来满足上限。

## 5. 两方案共用的安全切换协议

**原子性只覆盖数据库提交，不能把操作系统停止进程和数据库回滚描述成同一个原子动作。**

1. **准备目标。** 分诊 urgent 并取得用户对切换的确认；准备独立 PlanningDraft、CHG/Decision 和明确范围。旧 Mission 占槽期间，不提前创建另一个 DRAFT Mission。分诊单确认本身不能替代 urgent 的实施授权。
2. **登记切换。** 一个短事务锁定 project_focus 的预期版本，登记 operation、预留槽和调度 hold；当前焦点仍指向旧 Mission。冻结创建新业务 Work/Run、派发、重试及收尾的竞争入口。派发的持久启动声明也必须绑定焦点版本；无法证明未启动的旧声明不能忽略。
3. **停止与留证。** 对所有确属该 Mission 的执行资源处理，包含子进程、启动控制方和收集器；防止控制方稍后再启动一个 child。合作式停止时，允许原有效 owner 在受限排空阶段留最后的稳定 Checkpoint，取得实际停止证明后复核候选字节。未启动 Run 不应为了“总要先做检查点”而制造与无启动证明冲突的新证据。
4. **依法结束执行。** 自然完成保留 SUCCEEDED/FAILED 的真实结果；受控中止按获批能力转 CANCELLED，不能把中止记为成功。Run 终态与 lease 释放/epoch 提升同事务完成；拒绝旧 owner、旧 token、旧 epoch 的后续写入。已过期或失联 owner 走独立 Recovery 授权链；不能直改 expires_at，也不能倒填原 Run 的 Checkpoint。
5. **判断是否可交出焦点。** 仅有 Run 终态/lease 到期/行政结算不够，还须有确切 PID/job/启动身份的停止或无启动证明、无未决启动声明、候选与回执匹配。缺一则 operation=PENDING，保留旧焦点和执行 hold。新的查询可以解释阻断；新的业务派发不能继续。
6. **一次事务提交调度结果。** 重核确认、授权、Mission/Work/Run/lease 版本与证据，原对象进入 PARKED/占槽；以批准的规划创建 urgent Mission，或选取合法恢复目标；更新焦点 version、相关来源绑定与事件，operation=COMMITTED。持久化创建/绑定能力必须接受同一个 Unit of Work，不能串联数个各自提交的现有方法后宣称原子。实际启动 urgent 是此后另一个受派发门禁约束的动作。
7. **恢复与失败处理。** urgent 收口后由 resume 提议恢复；授权仍有效、依赖满足、候选/Checkpoint一致才恢复调度资格。原 Work 只走合法迁移，例如 BLOCKED→READY；新执行创建新 Run。需要新授权时，现有 authorize 只接受 PLANNED，不能硬给 BLOCKED Work重授权：须另定保留旧授权历史的受控 reauthorization 合同；该合同尚未具备时保持挂起并返回 REAUTHORIZE_REQUIRED。若另行批准创建带原链引用的新 Work，那是重新规划，不能计作 WBS 的“同 Work 续跑”验收。中途放弃切换不能复活已终态 Run、恢复旧租约或抹掉停止事件；继续旧任务也须按新的合法尝试执行。

**待验收与收尾例外：**ACCEPTANCE_PENDING 可以在执行均已安全退出、验证证据已固定、没有不可中断收尾操作时挂起；业务状态保留。恢复后若只是接受已有成果，不创建空执行 Run。ACCEPTED 不用作暂停态；其尚未完成的行政收尾应单列。紧急事项通常以 CLOSED 后提示恢复原事项；紧急事项发生失败或业务阻塞，不能自动假装收口后恢复旧任务。

**文件与 Checkpoint：**保留原工作树及脏改动，不因挂起 reset/clean/合并。若最终停止后的字节已经超出原 Checkpoint，保存明确的停止后快照/Recovery证据与原Checkpoint关系，不能宣称旧Checkpoint自动覆盖新字节；恢复后的验证依此重做。Checkpoint证明进度与证据，停放回执证明调度切换，两者不互相代替。

## 6. 存储升级、旧运行时兼容与回退

### 6.1 已部署版本的真实限制

1.3.3-a808fa8 的 Store 当前 schema 为 v7。initialize 与 list_missions 检查未知版本，但通用 _transaction/_read_connection 没有全局版本守卫。旧 PM 创建 PlanningDraft 的路径可不经 initialize；Mission show 也可直接读取。**仅把版本号升高，或新增 min_reader_version/min_writer_version，并不能阻止旧代码继续写旧表。**

旧 Mission DTO 使用 extra="forbid"，读取整行；新列或 SUSPENDED 状态可能使旧 Mission 解析失败，但这同样不能封住其他表的写入口。旧初始化还可能先配置 WAL/开启写事务再拒绝版本，因此也不能承诺“旧版本拒绝时库字节完全不变”。

### 6.2 两方案的升级步骤

1. **先准备兼容阻断能力，再开放新状态。** 新 Store 的所有读写通路统一校验存储/协议版本；根入口核验运行时能力，不满足则拒绝，不能 fallback 到不认识挂起的旧 release。只改新 Store 无法修复旧代码，必须另有旧入口写阻断。
2. **建立可验证的旧写屏障。** 部署迁移期间停止旧进程、启动者和续租器，明确唯一管理者。对迁移后的库，建议再加数据库层协议写屏障：受保护表的写触发器要求连接提供新协议能力，旧 SQLite 连接不提供则拒绝 DML；覆盖 Mission、Work、Run、lease、Checkpoint、intent、planning、intake及事件等治理写表。具体实现须由兼容卡验证旧二进制的真实入口，包括“不初始化就写”的路径。它是防误用的协议围栏，不是防御有权直接改数据库的恶意管理员；DDL、旧初始化、迁移连接与异常回滚也必须纳入验证。屏障未经验证，不得解除原单 Mission 约束。
3. **在授权的静止维护窗口迁移。** 取得一致备份，核验实际版本集合、旧索引定义、Mission/Work归属及未决资源；不能把历史混合 schema_meta 或多活动对象自动清掉。一个事务迁移版本、数据、索引、约束与能力标记；既有 Mission 默认 RESIDENT，不按 BLOCKED 推测挂起。焦点仅在唯一、可解释时建立，有歧义则拒绝或形成待裁决冲突。
4. **启动新运行时后核验整个入口面。** CLI、GUI、Facade、派发、显式 Work/Run、受控恢复以及投影必须共用新调度约束；先核验单焦点普通流程，再启用挂起能力。并发切换必须验证幂等、版本冲突与进程中断后的操作恢复。
5. **保留旧 release 文件，禁止对新库做软件版本单独回退。** 尚未写入新模型数据且维护窗口内，可按一致备份和已验证的反向迁移回退。产生挂起、切换或 urgent 新事实后，优先向前修复；不得恢复旧备份丢掉新事实。若确需降级，须由新管理器先合法处置所有挂起/切换，证明能重建旧唯一条件及旧合同并保留历史，再经独立迁移验收。否则只能维护性停写，不能强切 previous_release。

| 组合 | 本方案承诺 |
|---|---|
| 旧运行时 + 原库 | 继续现有能力；不提供真实多 Mission 挂起。 |
| 新候选 + 原库 | 显式只读/兼容模式可查看；迁移前不得启用挂起。不能自动在普通命令里迁移。 |

停车、口令哈希及接手码迁移可以统一发布，但不能为了“只迁移一次”强制捆绑不同成熟度或风险级别的功能，更不能延迟必要的安全修复。迁移版本在实施时按真实基线确定，不预占 v8。迁移后发布回退不等于数据回退；旧备份也不能覆盖迁移后已发生的新历史。

### 11.5 “授权模型”与“大模型选择”必须拆开

本讨论中描述权限结构时，建议使用“任务授权规则”或“执行授权边界”，避免含糊的“授权模型”。它回答允许做什么、改哪些文件、有效到何时、哪些操作需另行确认、谁当前持有执行资格。模型推荐回答用哪个大模型完成任务。两者不应混成一个品牌许可。

作为 WBS 设计方，我确认建议原则：**DeepSeek、GLM、Gemini 等都应能成为候选执行模型；默认推荐不应自动升级为硬性品牌约束。** 固定 WBS `57e14c194fdcc9c69fa601223240d68589472747` 第296行已写明，未启动任务原有 A/T/G/L 仅保留历史建议，不再构成模型授权。实际使用的模型、适配器、复核者应记录以便追溯。

当前实现尚未完全达到该原则，不能只做术语解释就说不存在耦合：

| 当前事实（固定候选 edeeead9） | 含义 |
|---|---|
| `contracts/mission.py:76～99` 的 `approved_model` 是普通字符串 | 没有只允许某几家模型厂商的枚举白名单。 |
| `execution_adapter_service.py:178～180` 强制 `executor_id == approved_model`；`pm_facade_service.py:375～380` 用批准模型充当 executor_id | 模型选择和执行者身份存在硬耦合，模型字段目前不是单纯推荐。 |
| `contracts/execution_adapter.py:24～29` 为 codex/trae/manual；同服务第63～110行均用本地准备回执适配器 | 有适配器名字不等于各家的真实启动链已经实现。 |
| `local_execution_orchestrator.py:61～68` 默认 LocalCodexExecutor；`local_executor.py:464～475` 组装 `codex exec -m ...`，第305～320行消费 Codex 会话事件 | 当前已核查的自动执行链依赖 Codex CLI 协议；填入 DeepSeek/GLM/Gemini 字符串不能证明能运行。 |

后续合同应分别记录：

- **任务权限**：目标、路径、允许动作、期限、并发和验收边界。
- **模型路由**：推荐模型、实际 provider/model、适用的能力要求；只有用户明确设置模型限制时，才有相应硬约束。记录实际模型不等于每换一个品牌都重批需求。
- **执行身份**：独立的执行器实例标识、Run owner 和 lease，不再用模型名称代替实例身份。
- **执行适配器**：统一启动、会话识别、停止、回收和证据回执合同，各家工具或 API 由适配器实现。缺失能力时明确不支持，不能只靠改枚举放行。

更换执行方仍须完成交接和租约围栏，这是防止两个执行方同时写入的要求，与品牌无关。对于已经把模型写成硬约束的活动授权，不能在本次讨论中静默移除或改写；后续以明确的契约升级处理，不干扰 Claude 当前正在执行的任务。

### 11.6 最终意见

采用双方已收敛的独立调度维度；M2 交付最小真实查询接口并如实标明能力，完整挂起可在明确分期后进入 M3；运行中插队以 V04-R1 为前提。物理存储与旧写屏障选择满足证据要求的最小实现。模型推荐保持可替换，执行授权与模型品牌解耦，真实适配器支持另行验证。
