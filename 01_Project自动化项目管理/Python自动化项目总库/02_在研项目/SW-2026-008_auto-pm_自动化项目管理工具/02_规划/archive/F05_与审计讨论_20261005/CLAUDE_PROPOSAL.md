# F05：“挂起后插入紧急事项”与唯一索引冲突 —— Claude 的独立方案

> 日期：2026-10-05。性质：方案草案，供用户在 GPT 的独立方案与本方案之间对比拍板；**写本文件时没有看 GPT 的方案**。
> 状态：不改任何代码、治理库、WBS 或需求草案；不含授权。
> 事实来源均为代码实读（基线 `4e165cf4`），行号可复核。

## 1. 冲突的事实

1. 唯一索引（`auto_pm/infrastructure/continuity_store.py:330-332`）：`UNIQUE ON mission_items(subject_project_id) WHERE state NOT IN ('ACCEPTED','CLOSED','CANCELLED')`。所以 `DRAFT`、`AWAITING_APPROVAL`、`ACTIVE`、`BLOCKED`、`ACCEPTANCE_PENDING` **都占着**项目唯一名额；只有 `ACCEPTED`（哪怕还没 `CLOSED`）起就释放名额。
2. 需求草案 N1.4 写的“挂起 = 复用 `BLOCKED` 并写明原因 `PARKED`，紧急事项成为新焦点”，在这个索引下**建不出第二个 Mission**，所以不能按字面实现。
3. 状态流转（`mission_service.py:33-36`）：`BLOCKED` 只能去 `ACTIVE` 或 `CANCELLED`；`resume` 把 `BLOCKED` 映射为“解决阻塞”（`continuity_resume_service.py:251`）。
4. Mission 带一个授权窗口（AuthorityEnvelope）：`contracts/mission.py:222-229` 允许 `BLOCKED` 的 Mission 在授权过期后仍可更新，**但不允许过期后处于 ACTIVE**。所以“挂很久再恢复”必然碰到授权过期。
5. 存储有 schema 版本门（`continuity_store.py:350-363`，当前 v7，`_KNOWN_SCHEMA_VERSIONS`）：旧运行时遇到不认识的新版本会拒绝打开（这是保护，也是兼容性的约束）。改索引谓词 = 必须升 schema 版本并写迁移。
6. 不能简单把 `BLOCKED` 整体移出索引：真实的故障阻塞（例如缺证据、被外部卡住）也会失去“一个项目同时只有一个未收口 Mission”的并发保护。

## 2. 三个可行方案

### 方案 A（我推荐）：给 `BLOCKED` 加一个“挂起”标记，索引只豁免“被挂起的 BLOCKED”

- **做法**：`mission_items` 加一列 `parked_at`（可空）；索引谓词改为 `WHERE state NOT IN ('ACCEPTED','CLOSED','CANCELLED') AND parked_at IS NULL`。挂起 = 在**一个写事务里**：对当前 Run 做检查点 → Run 置 `BLOCKED`（原因 `PARKED`）并释放租约（epoch 提升，旧 owner 写入立即被拒；注意这依赖“受控租约撤销与围栏”的能力，V04 只证明了到期后的前向结算，受控撤销是 V04-R1 要证明的，所以挂起功能必须排在 V04-R1 之后）→ Mission 置 `BLOCKED` 且写 `parked_at` → 同一事务里数一下该项目已挂起的数量，超过 3 个就整体回滚。
- **挂起的对象**：Mission（连同它的根 Work）。收件箱条目不动（它们是另一回事）。
- **恢复**：`parked → ACTIVE` 要求当前项目没有未收口且未挂起的 Mission（索引天然保证）；Work 用**新 Run** 从检查点续做（这就是 V03/V04 已证明的“同 Work 新 Run”路径）；授权已过期则必须先重新批准（用户确认一次），这是个有意的闸门而不是缺陷。
- **存储与迁移**：schema v8 = 加列 + 重建索引，放在**一个迁移事务**里；迁移前自动备份库文件。旧运行时（1.3.3-a808fa8）遇到 v8 会因版本门拒绝，这是想要的行为，**代价是回滚发布版本不能再打开已迁移的库**，所以部署清单必须写明“先备份、不支持降级”。
- **优点**：状态机几乎不变（只在 `BLOCKED` 上多一个标记）；并发保护不丢（真阻塞仍占名额）；恢复复用 V03 已证明的“同 Work 新 Run”；符合需求草案原意。
- **缺点**：要升 schema；要改 Mission 契约和 `pm resume`、驾驶舱的输出（多一个挂起列表）；迁移要有真实库的测试；回滚受限。

### 方案 B：不挂起，紧急事项排到“当前卡的下一个检查点之后”，由用户决定取消还是等

- **做法**：保持“一个项目同时一个未收口 Mission”。`urgent` 入箱后永远排第一，但不打断：用户可以选择让当前卡先收口，或**取消**当前 Mission（`CANCELLED`，Work 保留检查点），再为紧急事项开新 Mission；之后新开一个 Mission“从检查点续做”原来的 Work。
- **优点**：零 schema 变化、零旧运行时兼容问题；今天就能用。
- **缺点**：取消再重开会让一件事分裂成两个 Mission，验收标准与授权要重新批准，历史被拆开；“`CANCELLED` 但 Work 还要继续”会污染 `CANCELLED` 的语义（目前它表示放弃）；没有“最多 3 个挂起”这种可见的队列。

### 方案 C：挂起放到收件箱一侧，Mission 本身不动

- **做法**：挂起 = 把当前焦点的“意图 + 检查点编号 + 范围”存成一条收件箱条目（状态 `PARKED_FOCUS`），然后 Mission 走 `CANCELLED`；恢复时从这条条目新建 Mission，带 `resumed_from` 引用。
- **优点**：用第 1 期已有的收件箱表（延迟建表，不碰 schema 版本）；最多 3 条的限制在收件箱一侧做。
- **缺点**：和方案 B 一样把一件事拆成两个 Mission；挂起的 Work 仍在，但它的 Mission 已 `CANCELLED`，需要新增“孤儿 Work 归属”的规则；恢复就是新建一个 Mission，授权每次重批。

### 对比

| 维度 | A 标记挂起 | B 不挂起 | C 收件箱挂起 |
|---|---|---|---|
| 是否改 schema | 是（v8 迁移） | 否 | 否 |
| 旧运行时兼容 | 旧运行时拒绝新库，不支持降级 | 无影响 | 无影响 |
| 一件事是否保持一个 Mission | 是 | 否 | 否 |
| 并发保护 | 保持（真阻塞仍占名额） | 保持 | 保持 |
| 最多 3 个挂起 | 事务内计数强制 | 无 | 收件箱一侧强制 |
| 复用已证明的机制 | 同 Work 新 Run（V03 已证）；受控撤销与围栏（V04-R1 待证） | 无 | 部分 |
| 实现量 | 大 | 几乎没有 | 中 |

## 3. 我的推荐与理由

1. **设计选 A，但不放在 M2 里做。** 理由：需求已经裁决“最多 3 个挂起”，B 满足不了；C 把一件事拆成两个 Mission，会留下语义债；A 的代价是一次 schema 迁移，值得，但迁移的部署成本只该付一次。
2. **和另一个必然要改 schema 的任务一起做。** `TD-SW008-065`（口令改存哈希）与“一次性接手码”（`TD-SW008-063`）同样要改存储与契约；把它们并成**一次 schema v8**，一次备份、一次迁移测试、一次“不支持降级”的部署说明。
3. **M2 里只做一件事：不要让 V05（图形界面）和其他接口假设“已有挂起”。** V05 只需要在 `pm resume` 的数据结构里**留出一个空的挂起列表位置的约定**（不改契约，只在文档里写明），避免将来改接口。
4. **M2 期间的紧急事项按方案 B 的做法处理**（用户选择让当前卡收口或取消），这是今天就成立的现实。

## 4. 方案 A 的验收要点（给将来的卡用）

- 真实旧库（v7）迁移到 v8 的测试；迁移失败或中断后库不损坏；迁移前备份存在。
- 旧运行时遇到 v8 被拒绝且不写库。
- 两个进程同时“挂起并开新 Mission”只有一个成功；第 4 个挂起被拒。
- 真阻塞（不是挂起）的 `BLOCKED` 仍占名额，第二个 Mission 创建仍被拒。
- 挂起后旧 owner 的任何写入被拒；恢复用新 Run 从检查点续做，旧 Run 历史保留；授权过期的恢复必须先重新批准。
- 用真实进程做端到端，沿用 V04 的做法。

## 5. 需要你（用户）裁决的点

1. 挂起功能放 M2 还是 M3？（我建议 M3，和 `063/064/065` 一起做一次 schema v8。）
2. 挂起太久、授权已过期时，恢复是否必须重新批准？（我建议必须。）
3. “最多 3 个”按项目算还是按领域算？（我建议按项目。）
4. 紧急事项能否打断处于 `ACCEPTANCE_PENDING`（等你验收）的 Mission？（我建议不能：那时没有可打断的执行。）
5. 回滚发布版本不再能打开已迁移的库，这个代价是否接受？（我建议接受，并在部署清单里强制备份。）

## 6. 读完 GPT 方案后的更正与吸收（2026-10-05，写于第 5 节之后；第 1～5 节保持原样，作为独立方案的记录）

1. **更正一个事实错误**：第 1 节第 5 点和方案 A 里“旧运行时遇到新 schema 版本会拒绝打开”不成立。代码核实：`_KNOWN_SCHEMA_VERSIONS` 只在 `initialize`（`continuity_store.py:839`）和 `list_missions`（`:6250`）两处检查，已部署的 1.3.3-a808fa8 同样只有两处；通用的 `_transaction` 与 `_read_connection` 没有版本门，旧的 `pm plan` 路径（`create_planning_draft`）可不经 `initialize` 直接写库。所以“靠版本号挡住旧运行时”是我把一处检查外推到了全局，GPT 的判断（需要另外的旧写入口屏障）是对的。
2. **放弃我的“给 BLOCKED 加挂起标记”**：它表示不了“从待验收、草稿等状态挂起再原样回来”（`BLOCKED` 只能回 `ACTIVE`），也把真阻塞和人为挂起混在一个状态里。GPT 的方案 B（业务状态与调度状态分开）更干净，我认同它作为方向。
3. **吸收 GPT 的一个更好的做法**：三个挂起槽用 `(project_id, slot ∈ {1,2,3})` 的主键约束表达，由存储强制，比我设想的“事务里数数”更不容易被并发绕过。
4. **仍保留的分歧（供你裁决）**：
   - **规模与时机**：GPT 的 B 要新增焦点表、槽位表、切换操作表、Work 调度 hold、统一的 `ProjectSituation` 视图，以及可选的数据库层写入屏障，建议在 V05 之前冻结并实现“已安全停止的边界挂起”。我认为这在 M2 里太重：M2 还剩 V04-R1、V05、V06、V07/V08、总审计和部署。我主张分两段：**第一段**（M3）只做调度字段 + 槽位约束 + 边界挂起/恢复 + 共用的 resume/orient 视图；**第二段**（V04-R1 证明进程回收之后）再做运行中插队的切换操作与停止证明。M2 里只把合同写成文档冻结，并保证 V05 不预设“已有挂起”。
   - **旧写入口屏障的强度**：这是单人单机的环境，所有日常入口都经过启动器。最便宜的有效屏障是“启动器发现库的协议标记高于所选发布版本的能力就拒绝运行 + 迁移只在停止全部进程的维护步骤里做 + 迁移前强制备份”；GPT 提的数据库触发器写屏障更强，但要验证旧二进制的每个真实入口，成本高。强度由你选。
   - **待验收的 Mission 能否挂起**：GPT 允许（执行已安全退出、证据已固定时），我原先说不能。在方案 B 里它自然成立，我接受 GPT 的规则：仅在安全边界，且不由紧急插队自动触发。

## 7. 读完 GPT 第 11 节后的进一步更正（2026-10-05；均已回到代码核实）

1. **“Run 置 BLOCKED 并释放租约，恢复时用新 Run”不成立。** 创建 Run 时，Work 若已有非终态 Run 会被拒绝（`continuity_store.py:3843`、`:3958`，“Work 已有非终态 Run”），`BLOCKED` 的 Run 仍是非终态。所以挂起前必须先证明旧执行已停止，再把旧 Run 按事实合法结算为终态并围栏；之后确实要执行时才创建新 Run。我第 2 节方案 A 的“Run 置 BLOCKED”要撤回。
2. **“M2 期间紧急事项取消当前 Mission、再让新 Mission 从检查点续做原 Work”没有现成接口。** 取消再续做会改变 Mission 身份与 Work 授权关系，而 `WorkRegistryService.authorize` 只接受 `PLANNED` 的 Work（`work_registry_service.py:107`）。M2 期间真实可行的只有：让当前事项先收口，或取消后重新规划（新 Work），两者都不是“挂起”。我第 3 节第 4 点要改成这个说法。
3. **“授权过期则重新批准一次”不够具体。** 对已有 Work 的续授权、期限与范围的重新验证、审计记录与新的执行凭据都需要专门的接口设计；今天没有。
4. **撤回“必须把挂起和口令哈希、接手码捆绑成一次迁移”。** 它们成熟度与风险不同，可以统一发布，但不应为了“只迁一次”强行捆绑，更不能延迟必要的安全修复。迁移版本号按届时真实基线定，不预占 v8。备份必须是一致备份（SQLite 的 WAL 模式下直接复制主文件不是完整备份）。
5. **“所有日常入口都经过启动器”是待证明的部署前提，不是事实。** 若还支持旧脚本直接导入 Store、绕过启动器的命令行或旧进程并存，启动器检查就盖不住它们；迁移卡必须核实这些旁路入口，并按结果决定是停用它们还是加底层屏障。
6. **采纳 GPT 对 M2 的做法**：V05 前冻结一个带版本的 `resume`/`orient` 共用查询合同，带真实的生产者与消费者，并显式标明能力（建议 `parking_supported=false`、`preemption_supported=false`，相关动作返回 `UNSUPPORTED`，空的挂起列表必须配能力标志一起解释）。这比我第 3 节第 3 点“只在文档里留一个空列表”更能保证 V05 兼容。完整挂起放 M3，运行中插队以 V04-R1 为前提。
7. **双方此时的收敛**：业务状态与调度状态分离；每项目一个当前槽、最多三个挂起槽（存储约束）；安全边界下的挂起（含待验收）；运行中插队依赖进程回收证明；恢复不自动消除阻塞、不延长授权、不复活旧租约；M2 只交最小真实查询合同。剩下只需要用户确认分期、旧入口屏障的做法、回滚代价这三点。
