## 0. 演练要证明什么

一句话：**同一个项目开着两张卡，插急活、干完、再拿回原来那张，全程账本不乱、钥匙不重、用户说了算。**

| 编号 | 要证明的事 | 怎么判过 |
|---|---|---|
| P1 | 能开第二张卡；撞车时会拦、用户一句话能放行 | 第 2 步先被拒、放行后批准成功；`pm missions` 两张都在“等你” |
| P2 | 同一时刻只有一张“在干” | 第 4 步 B 开工被拒，提示 A 正在干 |
| P3 | 没有用户原话切不了 | 第 5 步 switch 被拒，账本无变化 |
| P4 | 切换一步到位，断点记得住 | 第 6 步后 A 在“搁着”，断点摘要和用户说的一致 |
| P5 | 搁着的卡谁也写不进 | 第 7 步用 A 的旧钥匙续租被拒 |
| P6 | 急活能正常干完、收口 | 第 8 步 B 进“已关”，对账 0/0/0 |
| P7 | 拿回时提醒落后 main、提醒撞车卡 | 第 9 步输出里有 `sync_note`、`overlap_note`（提到 B） |
| P8 | 原来那张能接着干完 | 第 10 步 A 进“已关”，对账 0/0/0 |
| P9 | 驾驶舱四栏和命令行一致，界面上没有切换按钮 | 用户在第 6、8、10 步各看一眼驾驶舱（只看不点） |

## 1. 角色和位置

- **用户**：只做三件事——说“开工 / 先做 B / 拿回 A / 放行”、看驾驶舱、最后验收。
- **M3 主执行**（用户笔记本上的 Remote Control 会话）：照本脚本敲命令，把每一步的输出原样记进演练记录。
- 电脑：用户笔记本；目录：控制根 `C:\Users\fubai\Documents\My_Workspace`（下面写作 `$ws`）。
- 命令前缀统一写作 `pm …`，实际是：`& "$ws\.venv\Scripts\python.exe" -B "$ws\main.py" pm …`

## 2. 开演前检查（任一条不满足就不开演）

1. TD-071 卡 1～4 已合进 `main` 并部署：`main.py --version` 显示的发布号包含卡 4 的合并提交。
2. `pm orient DJ-2026-009` 文字输出有“挂起: 支持 | 插队: 不支持”。
3. `pm missions --pid DJ-2026-009`：记下当前四栏（演练前基线）。“在干”必须为空；不为空先问用户怎么处理，不擅自搁着。
4. `ledger reconcile DJ-2026-009`：0/0/0。
5. 账本热备份（X02 一键热备份命令，参数以 `--help` 为准），记下备份文件名和 SHA-256。
6. 本机没有别的 agent 在写账本（D09 前后规矩：同一时刻只开一个写账本的 agent）。
7. 选好两张演练卡，**都不碰安全区**（急停、安全门、光栅、联锁、安全继电器、双手启动相关的文件一律不选）：
   - 卡 A“报警汇总文字整理”：只改 1 个非安全的说明文档，例如 `DJ-2026-009…/01_项目文档/<报警说明>.md`；
   - 卡 B“客户急改 IO 表注释”：改 1 个 IO 点表说明文件，**另外故意把 A 的那个文档也列进范围**，用来验证撞车检查。
   - 具体路径开演当天由主执行从仓库里选，先给用户看一眼再开始。

## 3. 演练步骤

每一步：敲命令 → 把输出原样贴进演练记录 → 对照“应看到” → 不对就**停下**，报告原文，不换办法绕过。

### 第 1 步：开卡 A（用户说“开工 A”）

```powershell
pm plan --project-id DJ-2026-009 --request-id DRILL-A-20261108 --kind iteration `
  --objective "报警汇总文字整理（演练卡 A）" --acceptance "<机器可判的验收条件>" --scope <A 的文件>
pm approve --request-id DRILL-A-20261108 --plan-hash <上一步输出的 plan_hash> `
  --approver fubai --approval-evidence-ref "user-confirmation:<用户说开工 A 的消息时间>"
```

应看到：批准成功。`pm missions --pid DJ-2026-009`：A 在“等你”。

### 第 2 步：开卡 B，先撞车被拦，用户放行（P1）

```powershell
pm plan --project-id DJ-2026-009 --request-id DRILL-B-20261108 --kind urgent `
  --objective "客户急改 IO 表注释（演练卡 B）" --acceptance "<…>" --scope <B 的文件> --scope <A 的文件>
pm approve --request-id DRILL-B-20261108 --plan-hash <…> --approver fubai `
  --approval-evidence-ref "user-confirmation:<用户说开 B 的消息时间>"
```

应看到：**拒绝**，原因含“和开着的卡‘报警汇总文字整理（演练卡 A）’……要改同一批文件：<A 的文件>，要你一句话放行”。把这句念给用户，用户说“放行”后：

```powershell
pm approve … （同上） --admission-release-ref "user-confirmation:<用户说放行的消息时间>"
```

应看到：批准成功。`pm missions`：A、B 都在“等你”，`open_count` = 基线 + 2。

### 第 3 步：A 开工并干一半

```powershell
pm confirm-start --mission-id <A>
git worktree add --detach .auto-pm/worktrees/drill-a
main.py continuity run start … --worktree <$ws\.auto-pm\worktrees\drill-a> --lease-wallet --owned <A 的文件> --declared-dirty <A 的文件>
main.py continuity run transition --to RUNNING …
```

在 `drill-a` 工作树里把 A 的文件改一半（例如加一行“演练：改到一半”），然后：

```powershell
main.py continuity checkpoint create …   # 摘要写“改到一半，差最后两条报警文字”
```

应看到：`pm missions`：A 在“在干”。

### 第 4 步：B 想开工被拒（P2）

```powershell
pm confirm-start --mission-id <B>
```

应看到：**拒绝**，提示含“项目里‘报警汇总文字整理（演练卡 A）’……正在干；请先搁着它（pm park），或用 pm switch 一步切换”。账本无变化（`pm missions` 同第 3 步）。

### 第 5 步：没有用户原话切不了（P3）

```powershell
pm switch --pid DJ-2026-009 --to <B> --reason "客户急改 IO 表" --summary "改到一半，差最后两条报警文字" --as claude:local
```

应看到：**拒绝**，提示要 `--approval-evidence-ref`。`pm missions` 不变。

### 第 6 步：用户说“先做 B”，一步切换（P4、P9）

```powershell
pm switch --pid DJ-2026-009 --to <B> --reason "客户急改 IO 表" `
  --summary "改到一半，差最后两条报警文字" --as claude:local `
  --approval-evidence-ref "user-confirmation:<用户说先做 B 的消息时间>"
```

应看到：输出 `parked` 有 A 的 park_id；因为 B 还没开工，`next_command` 是 `pm confirm-start --mission-id <B>`。`pm missions`：A 在“搁着”，`checkpoint_summary` = “改到一半，差最后两条报警文字”，`stale=false`；B 在“等你”。

**请用户看驾驶舱**（只看不点）：A 在“搁着”栏，写着为什么放下和断点；界面上没有切换按钮。

### 第 7 步：搁着的卡写不进（P5）

```powershell
main.py continuity lease renew --run-id <A 的 Run> --lease-wallet …
```

应看到：**拒绝**，提示“搁着呢，请 pm unpark”。

### 第 8 步：B 开工、干完、收口（P6）

```powershell
pm confirm-start --mission-id <B>
git worktree add --detach .auto-pm/worktrees/drill-b
main.py continuity run start … --worktree <$ws\.auto-pm\worktrees\drill-b> --lease-wallet --owned <B 的文件…> --declared-dirty <B 的文件…>
main.py continuity run transition --to RUNNING …
```

改 B 的文件（只改 B 自己的那个 IO 点表说明；A 的文档这次不动），自检验收条件，`checkpoint create`，然后按**当天 `main` 上现行的收口路线**收口：缺口⑧的正式命令（`pm verify` / `pm close` 一类，已合并的话）或驾驶舱“确认验收”按钮（由用户亲手点）。收口后：

```powershell
change transition <B 的变更单> --to <下一状态> --pid DJ-2026-009   # 逐步推到 completed
ledger reconcile DJ-2026-009
```

应看到：对账 0/0/0；`pm missions`：B 在“已关”，A 仍在“搁着”。**请用户看驾驶舱一眼。**

### 第 9 步：用户说“拿回 A”（P7）

```powershell
pm unpark --mission-id <A> --as claude:local --approval-evidence-ref "user-confirmation:<用户说拿回 A 的消息时间>"
```

应看到：`state` = ACTIVE；`checkpoint_summary` = 第 3 步的断点；`sync_note` 说明落后 main 几个提交（B 若已合并进 main 应 ≥1；B 只在控制根没进 main 时可能是 0，照实记录）；`overlap_note` 提到 B 和 A 的那个文档。口令不出现在屏幕上。

然后在 `drill-a` 工作树里同步 `main`、跑 A 的验收检查；**有冲突就停下交给用户，不自动变基**。

### 第 10 步：A 干完、收口（P8、P9）

把 A 的文件改完 → 自检 → `checkpoint create` → 按第 8 步同样的收口路线收口 → 变更单推到 completed → `ledger reconcile DJ-2026-009`。

应看到：对账 0/0/0；`pm missions`：A、B 都在“已关”，“在干”“搁着”为空，`open_count` 回到基线。**请用户看驾驶舱最后一眼。**

1. 两个演练工作树：分支已推送、没有未提交改动后 `git worktree remove`（删除前按规矩问用户）。
2. 演练改动是否保留进 `main`：问用户；不保留就不开 PR，只在演练记录里留输出。
3. 写演练记录（建议路径 `reviews/TD-071_插急活实地演练记录_20261108.md`）：每步命令、输出原文、P1～P9 逐条“过 / 不过 / 未测”，不过的附原因。

## 4. 出问题怎么办

- 任何一步输出和“应看到”不一致：**停下**，把原文发给用户，不重跑碰运气、不换命令绕、不手改数据库。
- 切换第二步失败（`pm switch` 报“A 已搁着，B 没起来”）：这是设计内的情况，A 稳稳在“搁着”；查清原因后**原命令重跑**，只补没做完的那步。
- 账本坏了或对账不为 0：先停，报告；恢复热备份要用户在 [M3 主执行] 亲口同意。
- 用户中途要真的插一件急活：演练暂停，A、B 按第 6 步的办法搁着，干完真活再继续或改天。
