## 1. 背景与已核实事实（2026-10-01，基线 `8b7f199a`，均为命令或源码核验）

1. WBS U07 原文：单一交付“薄 Cockpit SDK”；验收“SDK 经统一运行身份/Facade 从新目标到批准、真实 execute、验收落账完整实演；生产初始化不落到 editable/母体；不只验 import/查询”。
2. **执行与验收之间缺一环（本卡要补）**：前台执行成功后 Run 停在 `VERIFYING`；验收门（`PmFacadeService.accept`）要求 Mission 为 `ACCEPTANCE_PENDING`，且最新 Run 有一份内容绑定的自动质量 Checkpoint。但全仓库**没有任何生产代码**去创建这份 Checkpoint（`ContinuityExecutionService.append_verified_checkpoint` 没有任何调用方，只有定义）或把 Mission 推到 `ACCEPTANCE_PENDING`——此前只有人工脚本做过。结果是：驾驶舱用户无论如何点不到“确认最终验收”，U06 的自动收尾也永远到不了。
3. **执行入口依赖进程当前目录（本卡要补）**：`ExecutionDispatchService._project_stack` 用 `WorkspaceContextService.resolve(project_id=…)` 且不传 `start_path`，实际用进程当前目录做“是否位于工作区内”的校验；调用方（SDK、GUI 线程、测试）只要当前目录在工作区外就报“调用目录位于工作区外，拒绝解析”。演练中已复现。
4. 可行性演练（临时工作区、真实 Git、真实隔离工作树、一个会真实写文件的假 codex 辅助进程、真实 pytest/ruff/mypy 质量门）已证明下列链路在基线代码上可行：创建范围卡 → CHG 批准 → Decision → Mission/Work → `plan`、`approve(mission, work)`、`execute`（Work 变 `IN_PROGRESS`）→ `execute_planning_foreground`（Run `VERIFYING`，投影成功）→ `append_verified_checkpoint(profile="generic", project_root=候选工作树根)`（通过）→ Mission `ACCEPTANCE_PENDING` → `acceptance_gate_reason` 为空 → `accept` → `ACCEPTED`。演练也证明：`project_root` 取候选工作树根即可（无需项目子目录）。

## 5. 合同（全部定稿，执行者不得改写含义）

### 5.1 DTO（`contracts/pm_facade.py`，只新增）

`PmRunOutcome`（冻结，`schema_version: Literal["pm-run-outcome.v1"]`）：

- `mission_id: str`（非空）、`run_id: str`（非空）
- `receipt_status: str`（前台执行回执的状态原文，如 `VERIFYING`、`FAILED`、`PENDING`）
- `verified: bool`
- `checkpoint_id: str = ""`（`verified` 为真时非空）
- `mission_state: MissionState`
- `message: str`（≤200 字符，固定句，见 §5.2.4，不含路径、异常文本、令牌、标识符）

### 5.2 Facade（`pm_facade_service.py`）

1. **`verify_for_acceptance(self, mission_id: str, *, lease_token: str) -> PmRunOutcome`**，顺序固定：
   1. 读取 Mission；状态不在 `{ACTIVE, ACCEPTANCE_PENDING}` → 抛 `PmFacadeError("当前 Mission 不在可验证状态")`，不写任何数据；无根 Work → 抛 `PmFacadeError("Mission 缺少根 Work，不能验证")`；
   2. 取根 Work 的最新 Run（`list_runs(..., include_terminal=True)` 的第一项）；其状态不是 `VERIFYING` → 抛 `PmFacadeError("最新 Run 未处于 VERIFYING，不能验证")`；
   3. 租约属主取自 `store.get_lease(run_id).owner_id`；Checkpoint 标识固定为 `"CP-" + run_id + "-VERIFY"`；
   4. 调用 `ContinuityExecutionService(self._workspace_root, store=self._store).append_verified_checkpoint(checkpoint_id=…, run_id=…, owner_id=…, lease_token=lease_token, project_root=Path(run.worktree_path), profile="generic")`；`ContinuityExecutionError` → **不抛出**，记日志（含异常），返回 `verified=False`、`checkpoint_id=""`、`mission_state` 为当前状态、`message` 为 §5.2.4 的“验证未通过”句，且**不改变任何状态**；
   5. 成功后：Mission 为 `ACTIVE` → 用既有私有 `_transition(mission, ACCEPTANCE_PENDING, root_work_id=mission.root_work_id, action="verify")` 推进；已是 `ACCEPTANCE_PENDING` → 不再流转（重放）；返回 `verified=True`、`checkpoint_id`、`mission_state=ACCEPTANCE_PENDING`、“验证通过”句。
   6. 同一参数重复调用必须幂等：不新增 Checkpoint、不新增事件、返回等价结果。
2. **`run_approved_planning(self, card: PlanningScopeCard, *, expected_plan_hash: str, lease_token: str, lease_token_environment: str) -> PmRunOutcome`**，顺序固定：
   1. 校验 `card` 的哈希与 `expected_plan_hash`（与既有 `prepare_planning_execution` 相同的检查与异常文本）；
   2. `mission = self.materialize_planning_mission(card)`；`work = self.create_planning_work(card)`（均幂等）；
   3. Mission 为 `ACCEPTANCE_PENDING` → 直接返回 `self.verify_for_acceptance(mission_id, lease_token=lease_token)`（重放）；Mission 已是 `ACCEPTED/CLOSED/CANCELLED/BLOCKED` → 抛 `PmFacadeError("该需求已验收、已结束或被阻塞，不能重复执行")`；
   4. Mission 为 `DRAFT` → `self.plan(mission_id)`；然后 `self.approve(mission_id, work.work_id)` 与 `self.execute(mission_id)`（使根 Work 进入 `IN_PROGRESS`，收尾要求它）；以上对已处于相应状态的 Mission 须幂等；
   5. `receipt = self.execute_planning_foreground(card, expected_plan_hash=…, lease_token=…, lease_token_environment=…)`；
   6. `receipt.status != "VERIFYING"` → 返回 `verified=False`、`receipt_status=receipt.status`、`mission_state` 为当前状态、`message` 为“执行未完成”句，**不**调用验证；
   7. 否则返回 `self.verify_for_acceptance(mission_id, lease_token=lease_token)`（其结果的 `receipt_status` 填为 `receipt.status`）。
3. 令牌只在调用栈内使用：本卡的代码不得把它写入日志、返回值、异常文本、任何持久化对象，也不得新增任何口令落点；唯一例外是 `ContinuityStore` 在启动 Run 时既有写入的 `execution_leases.lease_token`（租约能力本身，本卡不触碰）。
4. 固定句（逐字）：验证通过“已执行并通过质量验证，等待您的最终验收。”；验证未通过“质量验证未通过，已保留现场；未进入验收。”；执行未完成“执行未完成，未进行质量验证；已保留现场。”。
5. 既有方法（`plan/approve/execute/accept/start_approved_mission_foreground/acceptance_gate_reason` 等）的行为、签名、测试一律不变。`start_approved_mission_foreground` 与驾驶舱开工流程**不改**（§5.6）。

测试不得通过 Mock 业务结果、硬编码预期字段或跳过来变绿；单元层可对“外部副作用点”注入故障（如让 `append_verified_checkpoint` 抛 `ContinuityExecutionError`），但至少场景 1、3、4、5 使用真实子进程与真实质量门。
