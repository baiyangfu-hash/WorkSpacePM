# M2 门禁分档与单卡规模规则

> 版本：V1.0（2026-10-06，随卡 055 / M2-GOV-TD2 批准生效；用户 2026-10-05 同意分档方向、2026-10-06 同意拆卡与规模上限）
> 适用：SW-2026-008 的各实施卡。批准前的现行做法不变；批准后各卡的门禁矩阵引用本文。
> 现状：**没有机器分档器**，也没有版本化的核心清单；本文只是文字规则。在机器实现获批并交付之前，每张正式卡仍须显式写出完整门禁矩阵，由范围与字节核验确保没有降档。本文不豁免现行对核心卡与产品卡的全量门禁。

0. **单卡规模**：产品文件一般不超过约 6 个，围绕一组关键反例。超出就拆卡，每张独立范围、门禁与验收；产品文件数、测试文件数、文档与工具文件数分别列明，不能只报产品数而隐藏总影响面。不得为压数合并无关模块，也不得借“一组反例”删减旧测试或必需的九组回归。文档卡按业务项目与基线拆分，SW-2026-008 侧与 SYS-2026-001 侧分开。
1. **分档取实际改动与验证工具变动的最高风险档，不由执行者自选。** 正式卡列出精确的 owned paths、基线状态与核心清单；由人与机器核对实际差异，未知路径或无法归类就拒绝定档并按核心档评审。文件后缀只是提示，影响行为的配置、模板、SQL 或脚本不能当普通文档。
2. **文档档**：仅非运行态的文档、台账、卡片与明确批准的 WBS 文字。门禁为文档结构与链接、台账完整性、旧内容保全、范围与字节指纹，以及这些检查的轻量负向对照；无需 pytest 全量。若文档会被运行时读取并决定行为，应升级。
3. **测试档**：仅测试与辅助文档；产品字节必须不变。跑相关的完整测试组、测试健康检查、类型与静态检查，并对新增断言做变异检查。`conftest`、全局夹具、收集或运行配置等跨组影响无法证实边界时，扩大到九组；不得减少既有断言、增加 skip 或抑制失败。
4. **产品档与核心档**：产品档是非核心的产品实现、生成模板、钩子与行为脚本；核心档是存储、contracts、schema 与迁移、执行授权与租约等核心清单。两档都跑全量九组、相关静态与场景门禁和变异检查；核心档必须覆盖真实进程、并发或对应的核心状态边界，不能以替身替代。
5. **变异判据统一**：同输入下先基线为绿，变异后被点名的测试因真实的目标断言失败而失败，恢复后再为绿。导入或收集错误、RuntimeError、超时、崩溃、没有测试与环境错误都不算“抓住”；分类不清写 UNVERIFIED。基线例外必须逐项绑定原始 nodeid、失败性质与批准范围，不能只比较数量。
6. **证据**：每档都保留命令、cwd、解释器与工具身份、时间、原始退出码、报告映射与 SHA。针对性的快速回路也保留这些证据，但标明它是开发回路，不能冒充或替代完整门禁。产品与核心的字节冻结后，由总协调方独占机器跑重门禁，其他参与者不并发跑负载；之后由非实现方只读审计。
7. **失败与重冻**：正式受治理执行中的失败按批准的卡停止并保留现场；演练只在明确授权的临时副本、次数与时间上限内修复。字节一变，关联结果即失效，须重冻并重跑受影响的矩阵；不能修改失败日志或旧身份。Checkpoint 在提交前绑定当前字节，提交里的 blob 与 Checkpoint 一致，技术完成与用户验收分开。
8. **不采纳跨 Run 复用**：本期不采纳演练证据的跨 Run 复用，受治理执行里完整重跑适用的门禁。以后实际演练前后用 `m2-tools/seal_inputs.py` 封存输入，但封存不是复用授权；要采纳复用，需要卡里一次性的明确条款、用户批准与独立审阅过的采纳校验工具。

**机器落地缺口**：分档器、版本化核心清单、判卷对复用回执的校验都属于代码工作，不能夹带在文档档卡里，需要另立实现卡。
