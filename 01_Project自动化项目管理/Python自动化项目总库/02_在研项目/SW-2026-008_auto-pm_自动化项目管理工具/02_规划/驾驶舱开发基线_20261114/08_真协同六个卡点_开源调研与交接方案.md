## 0. 先说结论

1. **直接拿来装就能用的开源方案没有。** 这六个卡点里，没有一个开源工具能原样装进驾驶舱就解决问题。能借的是“设计”，而且最好的那几个设计，驾驶舱其实已经做了一半。
2. **最值钱的一条不是开源软件，是给 agent 换一个 GitHub 账号。** 现在所有 PR 都是用户本人账号 `baiyangfu-hash` 开的【读到，最近 8 个 PR】，所以 GitHub 也分不出“人”和“AI”。只要 agent 改用第二账号，GitHub 自带的“作者不能批自己的 PR”“环境审核”就变成了真门，而且对哪家 agent 都一样。仓库里已经有一个给 Trae 用的第二账号，`rules-gate` 也已经认“环境审核”【读到 `reviews/tools/rules_approval_check.py`】，缺的是把所有 agent 都换过去，并且让 agent 摸不到用户本人的登录态。
3. **账本不改成多机同写。** 多机同写的方案都有（cr-sqlite、Dolt），但账本里是“谁拿着钥匙”“批准了没有”这种不能自动合并的事，自动合并反而危险。正确的做法是：账本留在一台电脑上，别的电脑和云端只往 git 里写“交接记录”，账本主机拉下来再入账。
4. **交接包能重新用起来，而且不用写大东西。** 现在的占位（`claims/<卡号>` 分支）本身就是一条存在 GitHub 上、谁都看得见的记录，提交说明里是一段 JSON【读到】。在同一条分支上每交一次棒就追加一个提交，就是一条谁都能读、改不了旧记录的交接链。旧 handoff.v1 的“交卷字段”和 handoff.v2 的“谁交给谁、交时的提交号”直接当这条记录的格式。要新写的只有两条小命令（记一笔、读整条），其余是串联已有命令。

## 第一部分：六个卡点的调研

### 卡点 1：账本只在一台电脑上，多机同写会冲突，没有常开的服务器

| 方案 | 链接 | 怎么做的 | 成熟度（实查） | 判定 |
|---|---|---|---|---|
| Litestream | https://github.com/benbjohnson/litestream | 后台进程把一个 SQLite 持续复制到文件或 S3，用于灾备 | 14.6k 星，Apache-2.0【读到主页】；页面没写最近发布日期 | **不适用于同写**。它是“一台写、备份到别处”，正好可以借来做账本备份【推断】 |
| cr-sqlite | https://github.com/vlcn-io/cr-sqlite | 给 SQLite 加 CRDT（自动合并的数据结构），多台都能写，事后自动合并 | 3.8k 星，MIT【读到】；原文“main 可能不是 100% 稳定，要用发布标签” | **不适用**。自动合并对“计数器、备注”可以，对“这张卡现在归谁”“批准了没有”会合出两个都成立的结果，等于两个人同时拿到操作钥匙【推断】 |
| Dolt（Beads 现在用的存储） | 经 Beads 主页得知【读到】 | 带版本的 SQL 数据库，像 git 一样分支、合并、推拉；多人同时写要另起 `dolt sql-server` | Beads 主页说默认是单写、多写要服务器【读到】；Dolt 自己的星数和许可证没去查 | **能借鉴设计，不建议换**。换库等于重写账本层，而且合并冲突还是要人判【推断】 |
| git-bug | https://github.com/MichaelMure/git-bug | 把每条事项的每次修改存成 git 对象，用普通 `git push/pull` 同步，离线可用，不需要服务器 | 10.9k 星，GPL-3.0【读到】；页面没写最近发布日期 | **能借鉴设计**：“只追加的操作记录放在 git 里”正是交接链要的；GPL-3.0 对公开仓库没问题，但驾驶舱不需要装它【推断】 |

**驾驶舱要改什么【推断】：** 不改账本的单机定位。补两件：
- 别的电脑、云端会话写的东西一律进 git（占位、交接记录、审计报告），账本主机在 `ledger reconcile` 时读进来。G2 契约里已经设计了 `events` 表（带前后哈希）和 `outbox`【读到 `28_G2_跨Agent工作连续性架构契约_CANDIDATE.md` 第 3 节】，要补的是反方向的“收件箱”：从 git 读回来。
- 账本备份可以借 Litestream 的思路，但现在就有 `release` 的指针备份，先不加新工具。

### 卡点 2：身份靠环境变量自报，人和 AI 分不出

| 方案 | 链接 | 怎么做的 | 成熟度 | 判定 |
|---|---|---|---|---|
| 给 agent 单独一个 GitHub 账号 | GitHub 官方文档（docs.github.com 本机打不开） | agent 用第二账号推代码、开 PR；用户账号只用来批 | GitHub 自带功能。“PR 作者不能批自己的 PR”“批准只算有写权限的人”【转述，搜索摘要引的官方文档】；条款允许每人一个免费“机器账号”【转述，我的记忆，没核原文】 | **能直接用，最该做**。仓库已有给 Trae 的第二账号（写权限）【读到 rules_approval_check.py 文件头】 |
| 签名提交（GPG、SSH） | 同上 | 提交带签名，GitHub 显示“已验证” | 【转述】“已验证”只证明“这个账号的钥匙签的”，不证明是人按的 | **不解决这个卡点**：agent 和用户在同一台电脑同一个 Windows 用户下，agent 一样能用那把钥匙【推断】 |
| 换一个 Windows 用户跑 agent | 操作系统自带 | agent 在另一个 Windows 本地账户下运行，读不到用户的凭据管理器和 `gh` 登录态 | 系统自带，成熟 | **能直接用，但成本高**。要在那个账户下重新装工具、配工位；先只记作选项【推断】 |

**这条为什么关键【读到】：** `rules_approval_check.py` 自己写着已知局限：“本机 agent 如果用用户已登录的 `gh` 命令行代发评论，机器分不出是不是本人”。也就是说，规则批准那道门现在挡的是“第二账号自己合并”，挡不住“拿着用户登录态的 agent”。

**驾驶舱要改什么【推断】：**
- 所有 agent（含云端会话）开 PR、推分支一律用第二账号；用户账号只做三件事：点批准、点环境审核、本地说批准句。
- 本机 agent 改用第二账号的令牌（只给这个仓库写权限），用户自己的 `gh` 登录和 Git 凭据不让 agent 用。在同一个 Windows 用户下这只能靠约定，真隔离要“换 Windows 用户”那条。
- 云端会话现在是以用户账号开 PR 的【读到】，这个平台能不能改成以第二账号开，**没核实**，要查平台设置。
- 驾驶舱自己的“这是不是 agent”判断，从“看环境变量”改成“看 GitHub 上是哪个账号做的”，凡是要用户本人的动作，最后都落到 GitHub 上的用户账号动作上核。

### 卡点 3：挡 AI 的门在 Claude 自己的安全检查里，换别家 agent 就没了

| 方案 | 链接 | 怎么做的 | 成熟度 | 判定 |
|---|---|---|---|---|
| 规则集：合并前要 PR、要检查通过、要 N 个批准 | 官方文档“Available rules for rulesets” | main 上设规则，没满足点不了合并 | 【转述】批准数 0～10；可要求“最后推送人以外的人批准” | **能直接用**，前提是卡点 2 先做：作者是第二账号，用户账号的批准才算“别人” |
| 环境审核（Environment required reviewers） | 官方文档“Managing environments for deployment” | 工作流里某个任务挂一个环境，跑到这里停下，等指定的人点 Approve | 【转述】免费账号只在公开仓库能用（本仓库是公开的）；最多 6 个审核人；有“防止自己批自己触发的运行”的勾选项 | **已经在用**：`rules-gate.yml` 第 89 行有 `environment: rules-approval`【读到】。卡点 2 做完后把“防止自批”勾上，才是真门 |
| CODEOWNERS | 官方文档“About code owners” | 给路径指定负责人，配合规则集要求负责人批 | 【转述】要配合分支保护或规则集才强制 | **能直接用**：把规则批准范围那 12 类路径写进 CODEOWNERS 指向用户账号，和 `rules-gate` 互为备份。仓库现在没有 CODEOWNERS 文件【读到】 |
| 合并队列（merge queue） | 官方文档 | 排队合并，合并前在最新 main 上再测一遍 | 【转述】只对“组织名下的公开仓库”或企业版私有仓库开放；本仓库在个人账号下 | **现在用不了**。要用得把仓库转到一个免费组织下，暂不建议为它搬家 |

| pre-commit 钩子 | — | 提交前本地检查 | 【转述】`--no-verify` 一下就跳过 | **不解决**，只能当提醒 |

**驾驶舱要改什么【推断】：** 门往 GitHub 上搬。原则是“凡是 AI 不能自己做的事，都要在 GitHub 上留下一个只有用户账号能做的动作”：
- 规则文件：已有 `rules-gate`，补 CODEOWNERS，补“防止自批”。
- 变更单批准、推完成这类只在本地账本里的动作：搬不上 GitHub 的部分，仍靠本地联锁（8.1 的看板按钮），这一块换 agent 也还在，因为它是驾驶舱自己的代码，不是 Claude 的检查。
- Claude 自带的安全检查当第二道，不当唯一一道。

### 卡点 4：占位租期会过期，没有大家都看得见的实时锁

| 方案 | 链接 | 怎么做的 | 成熟度 | 判定 |
|---|---|---|---|---|
| mcp_agent_mail 的“文件预留” | https://github.com/Dicklesworthstone/mcp_agent_mail | agent 预留一批路径，带有效期，可续可强放；可装提交前检查挡冲突 | 2.2k 星【读到】；**原文：这个 Python 版已不再维护，新装请用 Rust 版**；原文自称“自愿的预留”；要常开一个 HTTP 服务（端口 8765）；安装程序会把已装的 `bd` 换掉【读到】 | **不适用，只借设计**。要常开服务正撞卡点 1；“自愿”说明它也不是硬锁；它管的事和现在的占位一样 |

**结论【推断】：** 卡点 4 的真问题不是“没有锁”，是“锁会自己松”。4 小时到期以后，PR 还开着、人还在干，锁就算没了。

**驾驶舱要改什么：**
- 规则改成“PR 开着，占位就算活着”：`gate` 检查（`reviews/tools/pr_overlap_check.py`）判占位时，对应 PR 没关就不算过期。小代码改动。
- 推送时自动续期（`claim renew` 已有，串进推送前步骤即可，不是新代码）。
- 不上实时锁服务器。

### 卡点 5：agent 之间不能直接交接

| 方案 | 链接 | 怎么做的 | 判定 |
|---|---|---|---|
| mcp_agent_mail 的“邮件” | 同上 | agent 之间发消息，消息是 Markdown 文件存在一个 git 仓库里，SQLite 做索引【读到】 | **借设计**：“消息存成 git 里的文件”这一点正好；但要常开服务、只走 MCP、Python 版已停维护，不装 |

## 第二部分：交接包、交接契约怎么重新用起来

### 1. 三样旧东西各解决了什么、为什么退、哪里好

| | handoff.v1（交接包） | handoff.v2（交接契约） | PM_SESSION |

**吸收的原则【推断】：** 这三样退的原因都是“状态写在两个地方”。所以新的交接记录**只记引用和事实，不记状态**：记“草稿哈希是多少、变更单号是多少、PR 号是多少、审计结论是什么、下一步该谁说哪句话”，不记“已批准”“已完成”。批准和完成只认账本和 GitHub 上用户账号的动作。

### 2. 今晚这条链每一跳带了什么（以 D-372 为例）

| 跳 | 从 → 到 | 带的东西 | 今晚靠什么带过去 | 机器能不能读 |
|---|---|---|---|---|
| ① 起草 | 云端起草 → 审计 | 冻结草稿、草稿哈希（如 bbf051f8…）、可改路径清单及其哈希、基准提交号 | 线程消息【转述，记忆】 | 不能 |
| ② 预核 | 审计 → 本地主力 | 预核结论、要改的地方 | 线程消息＋`audits/` 下的文件 | 半能（文件能读，没人去读） |
| ③ 建单 | 本地主力 → 审计 | 变更单号 CHG-SCPT-2026-657、建单后的正文 | 本地账本＋线程消息 | 只在本机 |
| ④ 逐字比对 | 审计 → 用户 | “比对通过”、用户要在本地说的那句话（“批准 CHG-SCPT-2026-657，同意改 .github 下的 sw008-ci.yml，上限 25 改 40 分钟”） | 线程消息 | 不能 |
| ⑤ 批准 | 用户 → 本地账本 | 用户原话 | 本地主力会话 | 只在本机 |
| ⑥ 开 PR | 云端 → GitHub | 占位 `claims/d372-ci-timeout`、PR #795、PR 正文里的 `领卡占位:` 和可改范围 | GitHub【读到占位记录】 | **能** |
| ⑦ 审计合并 | 审计 → GitHub | 审计报告、CI 结论、合并提交 | GitHub＋`reviews/` | **能** |
| ⑧ 收口 | 用户 → 本地账本 | “推到完成”那句话 | 本地主力会话 | 只在本机 |

**看出来的问题【推断】：** ⑥⑦ 已经走 GitHub，换哪家 agent 都一样。①～④ 全靠这个平台的线程消息，换一家 agent、换一个平台，哈希、单号和“该说哪句话”就断了。要补的就是这四跳。

### 3. 做法：每张实施卡一条交接链，存在 git 里

**放在哪：** 就放在这张卡的占位分支 `claims/<卡号>` 上。每交一次棒，在这条分支上追加一个提交，提交说明是一段 JSON。理由：
- 占位分支已经是“提交说明里放 JSON”的格式【读到】，读写办法现成；
- GitHub 上谁都看得见，云端、本机、哪家 agent 都只要会 `git push`；
- 只追加，旧记录改不了（要改只能强推，强推按硬规矩禁止，GitHub 规则集也能禁）；
- 卡号和实施卡号相同（卡的整理方案甲第一步已定），所以从实施卡能直接找到它的交接链。

**每一笔记什么（拼起来的格式，不是新发明）：**

| 字段 | 来自 | 例子 |
|---|---|---|
| `from`、`to` | v2 的 from_owner、to_owner | `claude-fc1e6b` → `audit` |
| `kind` | 新，取值固定几种 | 起草、预核、建单、比对、待用户说、开PR、交卷、合并 |
| `git_head`、`paths`、`paths_hash` | v2 | 提交号、可改路径、路径清单哈希 |
| `refs` | 新，只放引用 | 草稿哈希、变更单号、PR 号、审计报告路径 |
| `result` | v1 的交卷字段（交卷那一笔用） | 改了哪些文件、验证（lint/测试/其他/没跑）、风险、下一步、先读什么 |
| `verdict` | 新，审计用 | 通过 / 不通过 / 要改哪几处 |
| `user_says` | 新 | 用户要在本地说的那句完整的话；**这里只是提示，不是批准** |
| `next` | v1 的 next_actions | 下一个人该做什么 |

**不记：** “已批准”“已完成”这类状态，用户原话本身（原话只认本地会话和 GitHub 上用户账号的评论）。

### 4. 哪些是串联已有的，哪些要新写

| 东西 | 已有／新写 |
|---|---|
| 订卡、续期、列占位：`claim open/renew/list` | 已有 |
| PR 正文的 `领卡占位:` 和可改范围、`gate` 检查 | 已有 |
| 审计脚本 `audit_pr.py`、审计报告写到 `reviews/` | 已有 |
| v1 交卷字段的校验逻辑（字段齐不齐、文件在不在范围内） | 已有，在 `ai_handoff_service.py` 里，拿出来复用，不复活 v1 的文件存储 |
| `claim note <卡号> --kind … --to …`：在占位分支上追加一笔 | **新写，小** |
| `claim log <卡号>`：按顺序读出整条链，告诉你“现在轮到谁、该做什么” | **新写，小** |
| “PR 开着占位就算活着” | **新写，小**，改 `pr_overlap_check.py` |
| 账本主机 `ledger reconcile` 时把交接链读进账本事件表 | **新写，中**，放后面做 |
| 交卷到收口（自动流程 D）：开头读 `claim log`，结尾写一笔“交卷” | 串联，不是新行为 |

### 5. 和实施卡、占位、交卷到收口的关系

- **实施卡**说“这件事要做什么、验收标准是什么”；**占位**说“现在谁在做、改哪些文件”；**交接链**说“做到哪一棒了、下一棒该谁、该带什么”。三样用同一个卡号。
- 交卷到收口那条自动流程，就是沿着这条链往下走；每个必停点（等用户说话）在链上就是一笔 `user_says`，流程停在那，用户说完、账本里有了，流程再往下。

### 6. 账本只在一台电脑上时，能做到什么、做不到什么

**能做到【推断】：**
- 云端、别的电脑、换了哪家 agent，都能读到“这张卡到哪一棒了、草稿哈希多少、单号多少、下一步谁说什么”。
- 新开一个对话不用翻聊天记录，`claim log <卡号>` 一条命令接上。
- 交接过程有证据可查，旧记录改不了。

**做不到：**
- 不能在云端批准、推完成、切换。这些仍然只在账本主机上、由用户本人做。
- 不能代替 handoff.v2 在本机交钥匙（租约、令牌还在账本里）。交接链只管跨机器那一段。
- 账本主机关机时，链上记的东西进不了账本，开机 `reconcile` 后才入账。
- 身份问题（卡点 2）没解决前，链上写的 `from` 也是自报的，只能当记录，不能当凭据。
