## 1. 目标

**几个 agent 员工在驾驶舱管着的情况下，把一个真实 PLC 原型项目从立项做到交付；过程可查、结果可靠、可验证、可回退，批准的事都经过用户本人。**

## 2. 定位

- 驾驶舱是“规范工具或者枷锁”，让 AI 做的事“可追踪，可验证”。起因：AI 写 PLC 程序没有固定规范，把修订做成新建，删程序、删文档、删虚拟环境；工业现场出问题会伤人、毁设备。
- 驾驶舱是“我和未来数字员工一起协作工作的基石”，做得重是有意的。
- 两条并行的线：**项目线**“是我的业务线”；**工具线**“是我的野心，未来一人公司，agent员工”。
- 使用者：用户一人（电气工程师，兼管项目）和多个 agent。

## 3. 范围

**做**：“后续所有 PLC 原型项目都受驾驶舱管理”。原型程序基于西门子 LSP，做语法验证、逻辑验证、断言。一个原型对应一个客户。

**不做**：原型移植到实际硬件（“实际移植我来做，ai只做原型”）；硬件测试（“由人类工程师负责”）；画电气图纸（“图纸我画”）；交付打包（“暂时不做”）；批准口令（“这个不做”，“不会过度防护”）。

## 4. 生命周期

“一个项目开发是有生命周期的，不要忘了。”阶段沿用用户 10-22 定的六段，前加立项、后加归档：

**立项 → 需求 → 设计 → 编程 → 仿真 → 现场 → 收尾 → 归档**

下面每条需求都标了所属阶段。现场段归用户。驾驶舱必须能回答“这个项目走到哪一段、这一段还缺什么”。

## 5. 项目线需求

| 编号 | 阶段 | 需求 | 验收标准 | 现状 |
|---|---|---|---|---|
| P1 | 需求 | 工艺流程分析 | 项目里有工艺流程文档，过需求段的门时被查到 | 有产品经理角色包和模板；不查内容 |
| P2 | 需求起，贯穿 | 需求文档，含“需求变动的每次记录，防止扯皮”。凭据来自邮件、会议记录、口头、微信 | 每条变动有：谁提、哪天、凭据文件、改硬件还是软件；后续每个改动都能查回它 | 有零件，没对准 |
| P3 | 设计起，贯穿 | 技术架构文档能更新、有记录 | 每次改动自动留一行版次和原因 | 只有文件 |
| P4 | 设计起，贯穿 | 接口文档：FB、FC 接口变动；OPC、Modbus 交互数据变动 | 接口和程序对不上时检查报失败；每次变动留记录 | 核对有，变动记录没有；OPC、Modbus 只有模板 |
| P5 | 编程 | 按模板初始化新程序 | 一条命令生成目录、程序骨架、文档 | 已有 |
| P6 | 编程起，贯穿 | 版本变更记录：FB、FC、文档各自的变化 | 由驾驶舱按变更单自动填，AI 不手写 | 有文件，靠手写 |
| P7 | 设计 | HMI 原型，可交互 HTML（或 PPT） | 原型和 PLC 变量对不上时检查报失败 | 大半有：对不上只警告 |
| P8 | 编程、仿真 | 西门子 LSP 语法、逻辑、断言验证 | 在用户电脑上一条命令出结果；老写法（TIA 实测不通过的三种）报失败 | 已有；那三种不报 |
| P9 | 需求 | 图纸由用户放进项目对应文件夹，“ai检查是否缺失” | 文件夹空着时检查报缺 | 没有 |
| P10 | 收尾 | 版本变更记录按客户模板导出（时间戳加改动内容） | 一条命令导出；任一行能查回需求变更和凭据 | 没有 |
| P11 | 全程 | 项目计划：“一个里程碑包含几个wbs原子任务，里程碑对应的所有wbs任务完成后里程碑完成，要有回写功能。能沉淀到驾驶舱最好，保证后续项目都能做” | 每个项目一张“里程碑加任务”表；任务状态从账本读，里程碑状态自动算并回写；新建项目自带 | 有里程碑表（六段、手填、只查日期）；005 的程序早有了，表里“编程”仍是“未开始”，检查还报通过。卡上没有“属于哪一段” |

用户交给客户的清单（供 P10 和阶段检查对照）：电气图纸、元件清单、PLC 源程序、HMI 程序、接口文档、驱动器和传感器参数说明及参数、整机使用手册、版本变更记录。

## 6. 工具线需求

| 编号 | 需求 | 验收标准 | 现状 |
|---|---|---|---|
| T1 | 多工位、多 agent、多电脑同时干活不打架 | 两个 agent、两台电脑同做一个项目，不丢改动、不出两本账 | 工位、订卡占位、PR 撞车检查已有；账本主机联锁、跨电脑工作票未做；没有实战过 |
| T2 | 不依赖某一家 agent：“未来会有deepseek，gemini，codex，或者别的” | 换一家 agent 做同一张卡，同样被管住 | 规则通用；部分拦截只对 Claude 生效 |
| T3 | 驾驶舱自身的迭代也由 agent 做，同样受管 | 同 T1、T2 | 已是这样 |
| T4 | 自动流程：“驾驶舱那个散落的工具，功能能组合一起就组合”，像搬运机构，“正常自动运行，不需要单独点动，只有运维或者改动程序测试的时候才点动” | 常做的事一条命令或一个按钮走完，只在该用户点头处停 | 已有三处合并（一步收口、插急活、先预览再执行），其余散着；候选见里程碑与 WBS 第 7 节 |
| T5 | “把产品经理角色包做好” | 角色包覆盖工艺流程分析、需求变更记录、生命周期、项目计划表、交付清单 | 现有 60 行，只讲接需求、出计划、派活、验收的流程；这五块一个字都没有 |

## 7. 对 agent 的可靠性要求

“过程可查，结果可靠，可验证，可回退。”

| 编号 | 要求 | 落到驾驶舱上 | 现状 |
|---|---|---|---|
| R1 | 过程可查 | 每次改动查得到谁干的、凭哪条需求、谁批的 | 改动到变更单有；需求到变更单没有 |
| R2 | 结果可靠 | “完成”要挂真证据，不能没做说做了 | 弱：后面阶段的文档可以先写成“已完成” |
| R3 | 可验证 | 机器能判的由机器判 | 有，见 P8 |
| R4 | 可回退 | 改错、删错能一条命令退回，退回本身留记录 | 发版能回退；删项目进回收区能恢复；**某一次合并的一键退回没有** |

## 8. 谁说了算

| 事 | 规则 | 依据 |
|---|---|---|
| 原型程序改动、需求改动 | 用户确认，有记录 | “原型程序改动，需求要找我确认，要有记录” |
| 交付 | 用户检查 | “交东西当然是我检查” |
| 改文档、改测试 | agent 互审后合并，事后告知用户；**前提是能回退（R4）** | “可是事后告诉我，必须可回退” |
| 用户怎么批 | 看板上的审批按钮，留下谁在何时点了同意；不设口令 | “在驾驶舱做个审批按钮” |

审批按钮现状：看板已有 11 个决定按钮；缺变更单的“批准”和“推到完成”，这两样现在要用户在本地对话里说一句完整的话。
