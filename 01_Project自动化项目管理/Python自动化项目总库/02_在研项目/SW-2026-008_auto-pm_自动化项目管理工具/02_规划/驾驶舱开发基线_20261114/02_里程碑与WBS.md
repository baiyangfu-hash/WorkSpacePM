## 0. 怎么读、怎么回写

- **一行是一个原子任务。变更单不按任务开，也不按里程碑开**，按“同一类、能一起审、能一起退”分组（用户 22:56Z 问“一个原子任务一个变更单是否太频繁”，协调者裁定）：一个里程碑里代码一组、规则批准一组、PLC 项目一组，通常 2 到 4 张，小改走快线。每个里程碑下面有一张“变更单分组”表。不并成一个里程碑一张的理由：规则批准的单只有你能批、不能和代码单并；一张单太大，出了问题只能整张退。你若坚持一个里程碑一张再改。
- **你的点头统一记在里程碑验收那一次**：一条带时间和证据的验收记录，不为每个任务单开变更单。
- **变更单、实施卡、PR 三者的关系（审计 11-13 读码核实，全文见 `audits/变更单_任务卡_PR关系_读码核实_20261113.md`）**：用户 22:59Z 说“一个原子任务领一张任务卡可以”，23:06Z 确认他指的就是 codex 当初做的实施卡（“我说错名字了”）。本文对你统一只说“实施卡”。层次是：里程碑 → 几张变更单（见各里程碑的分组表）→ 每张单下的原子任务各一张实施卡 → 每张卡的改动走 PR。拿电气打比方：变更单是你签过字的改造通知单，实施卡是挂在柜门上的“某某正在作业”的牌子，PR 是改完的图纸和程序连同检查记录。

  | 东西 | 是什么 | 谁来做 | 多少 |
  |---|---|---|---|
  | 变更单 | 你批准的授权：允许改什么、改到哪为止 | 你批准、你推完成（8.1 做好后在看板点按钮） | 一个里程碑几张，按分组表 |
  | 实施卡 | 谁在干哪一件的牌子，是进仓库的一个文件，上面写它挂在哪张变更单下 | agent 领，领的时候在实施卡上打占用标记 | 一个原子任务一张；一张变更单可以挂多张 |
  | PR | 改动本身和机器检查、独立审计 | agent 提，审计通过后合并 | 一张卡通常一个；一个 PR 只对一张变更单 |

  落地做法（给 agent 看）：用实施卡 `CARD-<项目号>-NNN`，一个号管三处，即卡文件名、占位 `claims/<卡号>`、PR 描述的 `领卡占位: <卡号>`。不用账本里的卡（Mission）当原子任务，因为那条路一张卡自动占一张变更单；账本卡只留给本机要租约、要工位隔离的派工。只读命令 `implementation-card by-change --change <单号> --project-dir <项目目录>` 能列出一张单下的全部卡。变更单必须和它管的文件属于同一个注册项目，所以 005 的东西和驾驶舱的东西不能放一张单。
- **任务状态怎么判**：只认机器能查的事实，不认卡上手写的状态，摘了牌子不等于完成。没有占位＝未开始；占位有效或 PR 开着＝在干；引用该卡号的 PR 已并进 main＝已合并未验证；再加部署或验证证据＝已完成。前三级只靠 GitHub 就能算，云端和本机算出来一样。
- **分组的代价**：一张变更单的文件清单要在批准前一次列全，组越大中途补单的机会越多；一张单要等组里最后一个任务合并才能推完成，开着的时间更长。
- **栏目**： 线：全＝全流程，标＝标准线，快＝快线（定义见 8.2）。载荷＝是否进发布载荷。规则＝是否在规则批准范围（只有用户能批）。
- **任务状态**四种：未开始、在干、已合并未验证、已完成。沿用现有口径：合并了但没部署、没验证的不算完成。
- **里程碑状态是算出来的**：下属任务全部“已完成”，里程碑自动变成“待用户验收”；用户按该里程碑的验收清单亲手做一遍，通过后才是“已达成”。
- **回写**：任务状态由审计在合并、部署、验证时改这张表的“状态”栏并附证据。状态栏可以改，但每次改都在回写记录里追加一行并带证据，旧记录不改写。8.8 做好后改由驾驶舱按对照去算，不再手改。

> 这里有一处我没有照你的原话写，请你定：你说“里程碑对应的所有任务完成后里程碑完成”。我加了一步“待用户验收”。理由是任务全完成只说明活干了，不说明目的达到了；如果任务一完里程碑就自动完成，等于让干活的 agent 自己宣布达标，这正是你要防的“没做说做了”。你不同意的话，把这一步去掉就是你的原话。
