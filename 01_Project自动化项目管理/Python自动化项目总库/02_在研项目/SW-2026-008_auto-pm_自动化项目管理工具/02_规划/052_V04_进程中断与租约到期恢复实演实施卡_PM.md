## 1. 背景与已核实事实（2026-10-05，基线 `4e165cf4`，均为命令或源码核验）

1. **WBS 原文**：V04“杀执行进程、主控重启各实演；到期不冒记成功；取消/续跑有合法证据与幂等事件”；AC08“重启、到期、真实换 Agent 可恢复：同 Work 续跑、旧 owner 拒绝、恢复自身终态”。其中“真实换 Agent”由 V03 负责；“已启动进程的回收证明”由 V04-R1 负责，**不在本卡**。
2. **现有机制（均已有单元测试，用假时钟与手造对象）**：前台执行 Saga（`LocalExecutionOrchestrator.execute`）独占子进程句柄，先持久化启动声明，再握手，落启动证据，周期续租并等待；非零退出被记为 FAILED（失败码 `NONZERO_EXIT`），模型文字不能把失败变成功。到期结算（`ContinuityExecutionService.settle_expired_run`，命令 `continuity run settle-expired`）只能把已过期的 Run 前向结算为 CANCELLED，且必须同时具备：独立的恢复 CHG、带运行态 capability 的 Decision（动作含 `SETTLE_EXPIRED_RUN`，目标 Run 在名单内，已批准文件覆盖 canonical `continuity.db`）、独立的恢复 Work 与处于 RUNNING 的恢复 Run；目标与恢复不得共享 Work、Decision、CHG。数十个单元测试把这些规则与各种漂移、回滚、重放、并发都覆盖了，用假时钟拨动 61 秒让租约“过期”。
3. **本卡的增量只能是真实进程与真实时间**：用真实子进程当主控与执行器，由操作系统杀掉它们，用真实时钟等租约过期，经真实 `continuity` 命令结算；不重复单元测试已经证明的内容。
4. **主控重启后没有受支持的续做入口**：重启后的新进程不能重新调用 `execute`，因为 `prepare_microtask` 只接受 READY 的 Run（演练里新主控进程报错退出、没有回执）；对账只有服务层的 `ExecutionSupervisorService.recover_started_session`，它没有命令行或 `pm` 入口，进程是否存活要由调用方自己提供判断。这条登记为 `TD-SW008-074`，**不在本卡处置**；本卡只证明“重启后不会盲目再启动第二个执行器”，以及对账在服务层按完整身份工作。
5. **演练发现的真实缺陷一（本卡修复）**：`resolve_started_run`（E06 的对账入口）把 Run 的 `executor_id` 与派发回执的 `executor_id` 比较；但真实派发创建的 Run 记的是“适配器:执行者”（即回执的 `owner_id`，例如 `codex:agent-a`），回执的 `executor_id` 是裸的 `agent-a`。所以**在真实派发路径上，原 session 永远认不出来**，`recover_started_session` 总是报“运行身份不可恢复”。原单元测试用手造对象让两边都等于 `agent-a`，所以一直没发现；V04 的真实进程演练在 r02 里立刻暴露。修复是一行：比较对象改为回执的 `owner_id`；同时把单元测试改成真实形态并加一个反例。同类问题可能还藏在其他手造身份数据的单元测试里，登记为 `TD-SW008-075`。
6. **演练发现的真实缺陷二（本卡修复，写路径与严格只读路径两处）**：存储在每次事务和每次只读前都做一次路径校验（`_validated_db_path`），其中对 `-wal`、`-shm`、`-journal` 三个边车文件检查“解析后仍在工作空间内”和“是唯一链接的普通文件”；严格只读快照（`_stable_read_snapshot`）还要对三个边车逐个读内容取指纹。多个进程同时使用库时，这两处都会误拒绝：
   ① **写路径**（观测到的事实）：第 1 期的并发入箱测试（4 个进程同时 `inbox add`）在 V04 演练的九组回归里失败过一次，报“DB/sidecar 必须是唯一链接的普通文件: continuity.db-shm”（原始输出归档于 `.auto-pm/reports/m2-v04/gates_rehearsal/judge_dry/g2_candidate/rest.txt`，独立审计已核对）；我另外凭记忆记过一次“空闲机器上重复 12 次又失败 1 次”，**没有逐轮日志，不作证据**；之后在空闲机器上做了有逐轮日志的重复（`.auto-pm/reports/m2-v04/e04_repeat/`）：修复前字节 24 次全部通过，候选 24 次全部通过，所以这个缺陷**只在负载下偶发、空闲时很少复现**，该测试区分不了修复前后。**我的推断**（失败那一刻没有直接观测文件状态）：SQLite 在别的进程使用库时会反复创建、删除这些边车，校验恰好遇到半建或待删除的状态。独立审计用故障注入证明：原代码在第一次边车异常时就拒绝、不会重试。
   ② **严格只读路径**（观测到的事实，本版新增）：用加固后的变异检查（它先确认被点名的测试在未变异字节上是绿的）时，`r02` 的基线没有通过；单独重复 20 次（`.auto-pm/reports/m2-v04/r02_repeat/`），第 17 次失败，控制器进程的错误是 `PermissionError: [Errno 13] Permission denied`，发生在严格只读快照对 `continuity.db-shm` 取指纹时（`_file_inventory`），随后 `record_start_evidence` 失败、没有产生 `RUN_STARTED`。机制用一个小实验确认过：在 Windows 上，只要另一个连接开着事务（写事务或读事务），别的句柄读 `-shm` 就报 `PermissionError`，事务结束即恢复。这正是本卡上一版列为“不在本卡”的 `TD-SW008-077`；它会让 V04 自己的真实进程测试随机失败（按本卡 §9 失败就停），也会让多个 Agent 与 `pm` 命令并发使用时偶发失败，所以并入本卡。早先有两次演练里“r01 失败一次”，我当时归因为被强行结束的演练进程残留，没有保留当时的输出，**现在无法判断它们是否也是这个原因**。

## 2. 单一目标（用户故事与完成定义）

作为用户，我希望进程中断、租约到期与并发访问在真实进程与真实时间下被证明是可恢复且诚实的：

1. 执行进程被杀：Run 被如实记为 FAILED（失败码 `NONZERO_EXIT`），租约释放，没有 VERIFYING 或成功冒记，口令不出现在任何事件里；
2. 主控进程被杀：Run 留在 RUNNING，租约不再被续；新进程按**完整身份**（PID、session、启动时间、进程存活）才认原 session，任何一项不符或进程已死都拒绝；重启的主控不会启动第二个执行器（启动声明始终只有一条，启动证据不变）；
3. 到期不冒记成功：真实等到租约过期后，Run 仍是 RUNNING，没有任何转移事件，`pm resume` 给出租约过期冲突且没有“下一合法动作”，旧 owner 的续租被拒；
