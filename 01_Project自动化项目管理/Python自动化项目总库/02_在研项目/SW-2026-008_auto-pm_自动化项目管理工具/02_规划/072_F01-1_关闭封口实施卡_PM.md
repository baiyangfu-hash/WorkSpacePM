## 1. 背景与已核实事实（2026-10-08，基线 `3bc740a4`）

1. **审计发现（我已对照源码核实）**：Astra 里程碑审计 F-01 指出，驾驶舱桥的同步入口 `confirmStart` 是所有写入口里**唯一没有关闭检查**的一个（`pm_cockpit_bridge.py` 第 358 行），关闭后保留桥对象的调用方仍能把有效待审批 Mission 写成进行中；另外窗口的 QML 销毁回调只调用 `stopSnapshotRefresh`（只停刷新），不置关闭标志，所以只调用销毁回调后 `createPlanningDraft`、`startExecution` 仍然放行。实际触及面限于保留桥对象、嵌入调用或显式接口调用：普通关闭的窗口不能再点击，QML 本身也不调用 `confirmStart`（`test_boss_cockpit_view.py` 第 205 行断言了这一点）。这个缺口是我写 V05-B3 时漏掉的相邻入口。GPT R4-05 另指出 TD-SW008-091 的证明偏弱：写入比较只比行数，窗口销毁分支没有真实销毁窗口。
2. **设计采纳（对 GPT 的修复设计 `astra-milestone-audit-20261008/proposals/F01_F02_REPAIR_PLAN.md` §3 的取舍）**：
   - 采纳：不可逆的 `beginShutdown`（置关闭标志并停刷新，不等待、不删对象、可重复调用）；`shutdown` 先调用它；所有写入口在封口后拒绝；独立窗口在关闭请求与销毁时封口；嵌入宿主用 `closesBridgeOnDestruction=false` 只暂停；完整内容比较与真实窗口实演。
   - **未采纳（留作后续）**：线程亲和检查、暂停前结果的“代际丢弃”、以及“暂停状态也拒绝 createPlanningDraft、startExecution、confirmStart”。理由：最后一项会改变嵌入宿主已有的行为，需要先有真实嵌入场景再定合同；本卡让这三个入口在“暂停”时保持原行为，只在“封口”时拒绝（这不是缺口：暂停是可逆的，封口不可逆）。GPT 设计里的这三项登记在 TD-SW008-098 的后续说明里，不在本卡。
3. **拒绝合同**：封口后各入口拒绝并返回同一句话“驾驶舱正在关闭。”；拒绝路径不调用服务、不排队任务、不改任何存储内容。`confirmStart` 的拒绝形状与其他同步入口一致：`{"success": false, "message": "驾驶舱正在关闭。"}`。
4. **探测中确认的一个夹具事实**：`confirmStart` 要在“已规划并已授权”的 Mission 上才会真正写入（我先用 `approve_scope` 路径的 Mission 试过，它没有内部授权，`confirmStart` 会因此自己拒绝，那样的“拒绝”证明不了封口）。所以新测试用门面自己测试里的 Mission 构造（`MISSION-PM-001`，先 `plan` 再 `confirmStart`），并配一个正例证明开着的驾驶舱 `confirmStart` 确实改变存储内容。
5. **我在全新基线副本上的演练**（2026-10-08，非受治理执行，受治理执行里完整重跑，不采纳这些输出；输出在 `.auto-pm/reports/m2-f011/gates_rehearsal/`）：
   ① `ruff check` 与 `mypy --strict` 对三个 Python 文件零问题、`git diff --check` 通过；
   ② G1：26 passed、1 failed（既存，与基线相同：26 passed、1 failed）；
   ③ G9：两个测试文件整份 43 passed、0 failed、0 skipped；

   ⑤ G6：除这四个文件外 `templates`、`auto_pm`、`tests` 树与基线逐字节相同；

## 2. 单一目标与完成定义

让驾驶舱在关闭后不再有任何写入口放行：一个不可逆的封口，所有写入口共用，独立窗口在关闭与销毁时封口；并用完整数据库内容比较和真实窗口实演证明。两个产品文件、两个既有测试文件的修改，其余产品、模板、台账、WBS 均零改动。

8 个新增测试节点：

| 测试 | 证明 |
|---|---|
| `test_confirm_start_really_writes_when_the_cockpit_is_open` | 正例：开着的驾驶舱 `confirmStart` 真的改变数据库内容（否则下面的拒绝什么也证明不了） |
| `test_a_closing_cockpit_refuses_confirm_start_and_changes_nothing[shutdown]`、`[begin-shutdown]` | 经 `shutdown` 或 `beginShutdown` 封口后，`confirmStart` 拒绝，数据库每个表的每一行都与封口前完全相同 |
| `test_begin_shutdown_seals_every_entry_at_once_without_waiting` | `beginShutdown` 重复调用幂等、不到 1 秒；九个入口（createPlanningDraft、confirmStart、startExecution、approveScopeAndStart、confirmAcceptance、retryClosure、requestSnapshot、requestEvidence、startSnapshotRefresh）全部拒绝并说明“正在关闭”；没有任务排队；数据库内容不变；封口后有界等待 `shutdown` 仍可用 |
| `test_a_paused_cockpit_is_not_sealed_and_can_start_again` | 暂停（`stopSnapshotRefresh`）不是封口：可再启动，同步确认照旧；封口后不可再启动 |
| `test_closing_the_real_window_seals_the_bridge_before_the_window_is_destroyed` | 真实创建 QML 窗口并发出真实关闭请求：窗口对象仍存在时桥已封口，写入口拒绝 |
| `test_destroying_the_real_window_seals_an_owning_bridge_and_only_pauses_an_embedded_one[standalone-window]`、`[embedded-view]` | 真实销毁窗口：独立窗口封口；嵌入视图（`closesBridgeOnDestruction=false`）只暂停，桥仍可再启动 |

另有 1 处既有断言更新：`test_boss_cockpit_view.py` 里对旧销毁字符串的静态断言，改为断言新的绑定（真实行为由上面的窗口测试证明，静态字符串不再充当证明）。

6 个变异（对象是桥与 QML 的新代码，每个由点名测试的真实断言失败杀死）：
   - M01-confirm-start-has-no-closing-check：a sealed cockpit refuses the legacy synchronous confirmStart
   - M02-begin-shutdown-does-not-seal：beginShutdown sets the closing flag
   - M03-shutdown-does-not-seal：shutdown seals the cockpit before it waits
   - M04-closing-the-window-does-not-seal：the standalone window seals the bridge on its close request
   - M05-destroying-the-window-only-pauses：the standalone window seals the bridge when it is destroyed
   - M06-an-embedded-view-seals-the-host-bridge：an embedded view that unloads only pauses the bridge
