## 4. 变更原因

**变更背景**：现有 `pm resume <project_id>` 的 `project_id` 为必填参数；GUI/CLI 的 `ai_context.json` 仅在用户主动选择或查询项目后写入。新会话因此依赖用户反复声明当前项目、驾驶舱研发母体、稳定部署槽位及 SYS 治理项目。该行为既没有把工作区实际目录与 PM_SESSION 中的关系收敛为机器可判定的事实，也会在普通项目中诱发“默认驾驶舱”的误绑定。

**变更必要性**：上下文恢复应是驾驶舱的基础能力，但不能把驾驶舱设为整个工作区的全局默认。系统需要从调用目录和项目证据确定工作项目，再在存在显式映射时附带治理控制面；多候选或无证据时必须失败关闭，要求选择，而不是猜测。

**参考依据**：`auto_pm/ui/cli/pm.py`；`auto_pm/application/core/pm_resume_service.py`；`auto_pm/application/core/project_fact_service.py`；`auto_pm/ui/qml/bridges/ai_context_bridge.py`；`PM_SESSION_SW-2026-008.md`；`PM_SESSION_SYS-2026-001.md`；RESUME-955B254E2BDE4A16。

## 5. 变更内容

### 5.1 变更前

| 项目 | 当前状态 |
|------|----------|
| 上下文入口 | `pm resume` 需要调用方提供项目编号；项目选择写入的 `ai_context.json` 是辅助状态，不是可验证的会话引导契约。 |
| 治理关系 | 恢复服务可为指定项目寻找 SYS 控制 PM_SESSION，但调用方必须先已知主体项目；研发母体、部署容器和控制面关系未以统一结构输出。 |
| 普通项目行为 | 没有一张明确的决策表保证普通 Python/PLC/未登记项目不会被隐式绑定到 SW-2026-008 或 SYS-2026-001。 |
| 风险 | 同一工作区多项目并行时，容易把上一次选择或人类口头说明误当作当前会话事实。 |

### 5.2 变更后

| 项目 | 目标状态 |
|------|----------|
| 上下文契约 | 新增版本化、只读的“会话上下文卡”输出：工作区根、工作项目、项目类型、证据路径与哈希、可选治理控制面、可选研发母体/部署槽位。 |
| 发现优先级 | 显式 `--project-id` 最高；其次为调用目录祖先中的项目锚点；最后才允许使用经指纹验证的 UI 最近选择。不得以全局默认项目补全。 |
| 治理关系 | 仅当项目声明或 PM_SESSION 中存在可验证映射时附带控制面；SW-2026-008 显示“研发母体”与其稳定部署容器为两个不同角色。 |
| 不确定性 | 工作区根、多个候选、映射冲突或最近选择失效时输出候选和证据，返回非零，不写 `ai_context.json`，要求显式选择。 |
| 普通项目 | 普通 Python/PLC 项目只返回自身上下文；未登记项目返回“unmanaged”，不虚构 PM_SESSION、治理项目或驾驶舱关系。 |
