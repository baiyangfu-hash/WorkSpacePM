# Day 01：Git 救命防线与工控概念类比

> 🎯 **今日目标**：看懂 Git 保存的工程版本与当前文件差异；区分提交和部署。
> ⏱️ **预计耗时**：15 分钟。
> 🛠️ **前置准备**：由 Agent 确认要查看的实际工作树目录；主工作区不一定是本次任务所在目录。
>
> **2026-10-09 勘误**：提交只是保存版本，不是往 PLC 下载程序，也不保证文件永不丢失。多工作树、GitHub 与日常速查见[独立指南](../Git与GitHub_日常维护够用指南.md)。本页练习只查看，不修改现场。

## 💡 一、工控视角看 Git：告别“散装备份压缩包”

在传统非标电气工程中，大家最熟悉的备份方式是打带日期的压缩包：
- `DJ-2026-005_20260801_初版.zip`
- `DJ-2026-005_20260810_现场改完伺服参数.zip`
- `DJ-2026-005_20260815_最终版_不要动.zip`
- `DJ-2026-005_20260818_真最终版_带气缸报警.zip`

这种做法有三大致命硬伤：**占用磁盘巨大、无法对比两次修改具体动了哪一行、多个人修改时代码无法合并**。

Git 就是软件工程世界的**“专业 PLC 程序版本记录与快照管理机”**：

```text
PLC 工控实体概念                     Git 版本控制核心概念
──────────────────────────          ─────────────────────────────────
电脑上正在编辑的一份工程目录          Working Tree (实际文件，可含未提交修改)
工程文件的逐行比对                    git diff (未暂存差异)
选好本次要归档的改动清单              Staging Area (暂存区，本身不编译、不检查)
保存一次带编号的工程版本              Commit (提交快照，不等于部署或下载)
工程版本修订记录                      git log --oneline (提交历史)
把已验证版本安装或切换为实际运行版本  部署 (本项目需另行授权与运行验证)
```

## ⚙️ 二、日常维护 4 步走标准工作流

修改前先确认目录、任务范围与其他 Agent 的占用情况。下面第 ③ 步交由 Agent 在授权范围内操作；本页不提供批量暂存或撤销步骤：

```text
① 查看现场状态          ② 比对改动细节          ③ 固化安全快照          ④ 查看历史台账
┌───────────────┐     ┌───────────────┐     ┌───────────────┐     ┌───────────────┐
│  git status   │ ──> │   git diff    │ ──> │ Agent 按范围提交 │ ──> │  git log -n 5 │
└───────────────┘     └───────────────┘     └───────────────┘     └───────────────┘
```

1. **`git status`**：显示当前工作树的暂存、未暂存与未跟踪文件，不代表其他工作树的状态；
2. **`git diff`**：默认比较已跟踪文件的未暂存差异；暂存差异用 `git diff --cached` 查看。两者都不显示未跟踪文件的正文；
3. **按范围提交**：Agent 核对文件归属、检查结果和批准范围后，精确选择文件提交；不能把整个共享目录的改动一起收走。提交记录不包含被忽略的运行数据库，也不替代备份；
4. **`git log --oneline -n 5`**：显示当前提交线最近的提交摘要，不能据此判断已经推送、合并或部署。

## 🧪 三、5 分钟动手实操实验

### 步骤 1：查看已确认目录的实际状态
```powershell
git -c core.fsmonitor=false --no-optional-locks status --short --branch
```
*如何读*：显示当前分支或分离 HEAD，以及该目录的文件状态。出现改动不等于出错，可能是其他 Agent 的工作；先核对归属，不为追求“干净”而撤销。

### 步骤 2：查看最近 3 次带哈希的提交快照
```powershell
git log --oneline -n 3
```
*如何读*：每行是一个短 SHA 与提交摘要；版本名、提交 SHA 和正在运行的制品身份要分别核对，不期待固定的示例版本。

## 🛡️ 四、改崩恢复法与今日自测打卡

### 🚑 改错后先保留现场
把实际目录、文件名、错误现象和想保留的修改告诉 Agent，由它先比对，再提出针对单个文件或指定版本的恢复方法。涉及覆盖、删除或共享历史的动作，确认范围后再执行。

旧版的整目录 `git restore .` 会丢弃已跟踪文件的未暂存修改；`git restore --staged .` 会改变整个当前目录范围的暂存选择。它们都不是“恢复出厂”，不适合作为多人工作区的一键自救步骤。[Git restore 官方说明](https://git-scm.com/docs/git-restore)

### 📝 今日自测思考题
1. 保存一次提交，是否说明正在运行的驾驶舱已经更新？
2. 主工作区显示干净，能否证明 Claude 的另一个工作树也没有修改？
3. 发现陌生文件改动时，为什么应先核对归属，而不是整目录恢复？
