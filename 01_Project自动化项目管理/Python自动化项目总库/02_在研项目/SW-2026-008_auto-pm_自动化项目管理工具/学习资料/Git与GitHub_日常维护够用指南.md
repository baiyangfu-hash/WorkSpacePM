# Git 与 GitHub：日常维护够用指南

适合：用 Agent 维护工程、希望看懂版本与交付状态的电气工程师。阅读约 15～20 分钟。本文不要求你学习复杂的合并、变基或挑拣提交操作。

**先记住：文件改好了、保存了版本、传到 GitHub、合并了、部署了，是不同的进度。**你负责确认需求和成果；具体写操作由 Agent 在授权范围内完成。

## 1. 先认清这几个名字

| 名字 | 用工程资料类比 | 需要知道的边界 |
|---|---|---|
| Git | 本机的工程版本档案系统 | 可以离线记录和比较版本 |
| GitHub | 远端工程档案与协作网站 | 只看到已上传的内容，不会自动同步整个电脑 |
| 仓库（repository） | 一个工程的版本档案 | 保存受跟踪文件的提交历史；不是整台电脑的备份 |
| 分支（branch） | 一条开发路线的名字 | 指向某次提交；名字会保留，但指向可随新提交前进 |
| 提交（commit）与 SHA | 一次存档及其唯一编号 | 保存当次已暂存的内容；编号不能证明质量或验收 |
| 工作目录／工作树 | 实际展开文件、动手修改的工位 | 其中可能还有未提交、未跟踪和被忽略的文件 |
| 暂存区（index） | 为下一次存档选好的材料 | 可以只选本次任务的改动，避免夹带别人的工作 |

[GitHub 官方 Git 简介](https://docs.github.com/en/get-started/using-git/about-git)可以留作查阅，不必先通读。看到 `HEAD`，暂且理解为“这个工作树当前检出的提交位置”；它也可能直接指向提交，而没有附着分支。

## 2. 为什么会有多个工作树和隔离候选？

多个 Agent 同时在一个目录改文件，容易互相覆盖。Git 的 worktree 功能允许同一仓库展开几个独立目录：各自有文件、暂存区和当前检出位置，共享提交历史与多数仓库信息。就像几个调试工位，共用工程档案。见 [Git worktree 官方说明](https://git-scm.com/docs/git-worktree)。

**“隔离候选”是项目对待检查成果的称呼，不是 Git 自带的特殊类型，也不表示已经验收。**它通常位于单独工作树，必须说清目录、提交和待检查范围。

```text
本机同一个仓库（共享 Git 历史）
├─ 主工作区：一份实际文件，不保证是 main 或最新版
├─ 候选工作树 A：Agent 修改、检查某个任务
└─ 候选工作树 B：另一个任务的文件与暂存区
          │ 提交，再按授权推送
          ▼
GitHub 分支 → PR 审阅／CI 检查 → 合并到指定分支
                                      │ 构建、批准、部署
                                      ▼
                            部署目录 → 实际运行进程
```

这是关系示意，不表示每次小改动都必须重新建工作树。**主工作区、主分支、最新候选、正在运行的版本，不能互相代替。**运行版本需要查部署与进程身份，不能仅看源码目录里的 SHA。

工作树只隔开文件操作；如果程序连接同一个数据库、端口或外部服务，仍可能互相影响。主目录的 `git status` 也只报告该工作树，不能证明其他工位都干净。

## 3. “已完成”到底完成到哪一步？

| Agent 的说法 | 实际含义 | 尚不能据此认定 |
|---|---|---|
| 已修改 | 文件内容变了 | 已检查、已存档 |
| 已提交 | 选定内容进入本机 Git 历史 | 已上传、已部署 |
| 已推送（push） | 指定分支或标签的提交传到远端 | 全部目录和所有候选都上传了 |
| 已开 PR | 提出把改动合入目标分支的请求 | 已批准或已经合并 |
| CI 通过 | 某个版本通过了所配置的自动检查 | 未运行的检查也通过、业务已经验收 |
| 已合并（merge） | 改动进入指定目标分支 | 当前程序已经更新 |
| 已部署 | 将选定制品放到运行位置并执行部署步骤 | 运行身份、功能和用户验收自然通过 |

PR 用来集中看差异、讨论和检查结果，目标分支也要核对。见 [GitHub PR 说明](https://docs.github.com/en/pull-requests/reference/pull-requests)。

本机未推送的提交，GitHub 看不到；未提交的编辑更不会自动上传。推送传输提交及其所需对象，不打包所有工作树；被忽略且未跟踪的数据库、日志、环境等也不会随之上传。已经被跟踪的文件则不能靠后来加入忽略规则自动排除。

“领先几十个提交”只是历史差异的数量，不代表新增了几十项合格功能。SHA 识别的是一个提交及其记录的受跟踪文件版本，当前目录额外的编辑和文件仍要另外检查。

## 4. 一个小例子：让 Agent 改界面说明文字

你提出：“这句提示不好懂，改成电气工程师能理解的话。”

Agent 先确认实际工作目录、基线和本次文件范围，并核实是否与别人的任务重叠。在合适的已有工作树或获准的隔离目录修改，检查文字、显示与受影响功能，把差异给你看。

确认满足要求后，Agent 按权限选择本次改动进入暂存区并提交，报告提交 SHA。若只到这一步，GitHub 与正在使用的程序都可能没变。需要远端协作时再推送、审阅和合并；需要让运行版本更新时，再走构建与部署安排。

你不必逐条操纵 Git，但可以要求 Agent 一次说清五件事：

1. 在哪个实际目录工作，有没有碰到其他人的改动？
2. 从哪个确定版本开始，准备交到哪里？
3. 本次改了哪些文件，与批准范围是否一致？
4. 检查了什么，还有什么没验证？
5. 提交、推送、合并、部署分别到哪一步，下一步是否需要我决定？

具体审批沿用当前项目规则；本篇学习材料不授予任何写操作权限。

## 5. 恢复和清理：先让 Agent 查清对象

不要把 `restore` 或 `reset` 当“恢复出厂”。不同参数会影响文件、暂存区或提交位置，可能丢弃尚未存档的修改；回退源码也不会自动恢复数据库或已运行程序。遇到问题先保留现场，让 Agent 说明要恢复什么、保留什么，再决定。见 [Git restore 官方说明](https://git-scm.com/docs/git-restore)。

多个工作树共享历史，仍要分别存放检出的文件；环境、缓存和打包产物也会占空间。不要按目录老旧或任务标签就删除。应先确认无活动任务、改动与交付证据已保留，再按工作树管理方式退出。`prune` 清理的是失效管理记录，不会替你删除仍有效的工作树或完成成果归档。

日常维护不用手改治理数据库、lease 或 JSON，也不必先学复杂历史重写。让 Agent 给出具体恢复／清理方案即可。

## 6. 一页只读速查

以下为 **PowerShell 示例**。先把每条中的 `<实际工作树路径>` 换成目标目录的绝对路径，保留单引号；未替换时不要照抄执行。每次只查一个明确工位。

| 想看什么 | 命令 |
|---|---|
| 当前分支、已修改和未跟踪文件 | `git -c core.fsmonitor=false --no-optional-locks -C '<实际工作树路径>' status --short --branch --untracked-files=normal` |
| 已跟踪文件尚未暂存的改动 | `git -C '<实际工作树路径>' diff --no-ext-diff --no-textconv --` |
| 已选入下一次提交的改动 | `git -C '<实际工作树路径>' diff --cached --no-ext-diff --no-textconv --` |
| 最近五次提交 | `git -C '<实际工作树路径>' log -5 --oneline` |
| 当前提交的完整 SHA | `git -C '<实际工作树路径>' rev-parse HEAD` |
| 本仓库登记的所有工作树 | `git -C '<实际工作树路径>' worktree list` |
| 配置了哪些远端地址 | `git -C '<实际工作树路径>' remote -v` |

这些命令只用于查看，不会推送、合并或部署。`diff` 不展示未跟踪文件的内容；状态简表中的 `??` 表示未跟踪，其他改动标记的两列分别对应暂存区和工作目录。没有普通改动输出，也不证明被忽略文件、数据库或部署状态没有变化。

本地显示的远端跟踪状态可能不是 GitHub 此刻的最新状态；不要仅凭它判断已经同步。远端地址也不证明网络与登录权限正常。

读完后能回答“成果在哪、版本是什么、检查过什么、离运行还差几步”，就足够开始日常维护。
