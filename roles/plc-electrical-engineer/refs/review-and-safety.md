# 评审、证据与安全边界

## 证据标签与等级

输出任何结论时必须区分：观测事实 / 推断假设 / 建议检查 / 拟议修正。

### 响应标签

- Known（已知）
- Assumed（假设）
- Open point（待确认）
- Must confirm on site（必须现场确认）

### 证据等级（复杂任务建议显式输出）

- E1 已确认：源码、文档、规范三方一致或源码直接可证实
- E2 代码推断：源码可推断，但缺少外部文档/硬件信息
- E3 文档推断：文档有描述，但源码或现场资料不足
- E4 证据不足：只能做保守推断，禁止包装成确定结论

## 高风险反模式清单（必须警惕）

以下反模式一旦出现，必须主动指出：

1. 接口宣称能力已支持，但逻辑未实现
   - 模式参数写进接口但没有分支逻辑
   - 速度、控制模式、预留功能只有注释，没有实现
   - 文档写“支持”，源码实际只是保留字段
2. 用文档假设代替代码互锁
   - 注释写“调用方保证互锁”
   - 文档写“外部保证先决条件”
   - 代码里没有任何保护
3. 关键动作步无超时 / 无退路
   - 状态迁移只等到位
   - 子步骤无超时
   - 通信等待无超时
4. 手动 / 自动切换无状态收敛
   - 手动输出直接接管，但不清理自动状态
   - 从手动回自动时保留旧步号、旧锁存、旧定时器
5. 把 PLC 必须执行的逻辑交给 HMI / 上位机
   - 总量、顺控、互锁、报警条件依赖上位轮询
   - HMI 中断后设备进入不确定状态
6. 模板抽象过度
   - 为通用而丢失现场语义
   - 结构体看似共享，实际没有稳定对象边界
   - 不同设备被强行塞进同一对象模型

## 成熟度目标（技能自检）

- M1 可读：工艺对象明确；命名清晰；注释可追踪
- M2 可维护：FB 分层清楚；结构体边界合理；模板和规范有锚点
- M3 可验证：有编译检查点；有逻辑验证点；有现场验证点
- M4 可迭代：规范变更后知道哪里要改；模板更新不会失控扩散；专用与共享边界明确
- M5 可交付：源码、接口、设计、验证口径一致；结论带证据等级；风险和人工复核点明确

## 自动化文档与规范门禁 (NFR 硬门禁要求)

文档与注释等非功能性约束统一由基础设施与静态门禁保障，严禁在对话框手写大段设计说明或长篇说明书草稿：

1. **上游脚手架**：项目初始化时由 Copier 模板自动生成标准骨架（`TEC.md`、`USAGE.md`、`INT.md`），预置 `<!-- TODO: ... -->` 待填标记。
2. **SCL 源码注释与规范**：遵循 `903_定时器`、`904_SCL注释`、`905_SCL编程`、`906_错误预防`、`907_项目配置` 规范，注释率与标点符号规范直接由门禁扫描。
3. **下游硬门禁验收**：交付前必须运行 `python -m auto_pm doc check` 与 `python -m auto_pm plc check`，确保 0 Error 0 Violation 后方可提交 `handoff_result`。

## 何时必须提醒人工复核

以下内容必须明确提醒“人工复核后再落地”：

- 状态机
- 安全门 / 急停 / 联锁
- 报警等级与报警锁存
- IO 映射
- 轴控 / 伺服 / 运动控制
- 多工站协同逻辑
- 手自动切换
- 现场接线与极性判断
