# 驾驶舱角色与边界

> 版本：V1.0（2026-10-09）　性质：设计依据与说明
> **本文不改变任何现行规则，不替代 `AGENTS.md`，也不修改 `.trae`、`.cursor`、`.agent` 下的任何文件。** 规则文本的修改由后续的 N1b 卡另行办理，办理之前现行规则照旧有效。
> 与现行文字的关系：`AGENTS.md` 的“子代理物理隔离法则”用的是“PM 调度领域子代理”的口吻，本文对驾驶舱的划分与它的口吻不同；本文只说明用户已确认的方向，不裁决两者的冲突，该冲突由 N1b 呈报用户。
> 内容来源：只来自用户已确认的文字，见文末“来源”。凡用户没有确认的推断，本文不写。

## 1. 目的

用户在任何 IDE、用任何模型干活，项目都不乱：接手者能马上知道现状，每个任务边界清楚，结果能被验收。

## 2. 主路径

用户选择 IDE、Agent 和模型；驾驶舱管理任务边界、项目状态、证据和验收记录。自动启动模型只是可选便利，不是主路径。驾驶舱不替用户选模型。

## 3. 三个角色

| 角色 | 负责 | 不负责 |
|---|---|---|
| 用户 | 提需求、决定取舍、批准范围、选择工具和模型、最终业务验收。用户是唯一决策者 | 找文件、拼治理记录、查死链、整理证据这类常规执行劳动；现场的物理事实和操作仍由用户确认 |
| 用户选定的 IDE、Agent 和模型（任意） | 读取任务、分析、在批准范围内干活、交回证据和没验证的部分 | 自己扩大范围、自己宣布完成、自己造出批准 |
| 驾驶舱 | 给任务、收结果、验收与记录、把状态和看板给用户看 | 干活、选工具、替用户选模型；机器检查通过不等于用户已验收 |
| 可选的自动执行模块 | 在单独批准下启动一种受支持的执行方式 | 它关闭或不可用时，外部 Agent 的主路径照样能完成日常任务 |

## 4. 驾驶舱只做三件事

1. **给任务**：任务卡写清目标、范围（能改哪些文件）、验收标准、禁止事项。需求分析也是一种任务：模型在用户的 IDE 里写，驾驶舱规定格式、存档、跟踪变更。
2. **收结果**：要求 Agent 交回改了什么、证据是什么、什么没验证。
3. **验收与记录**：门禁判卷，更新台账，更新看板。

## 5. 只在三个出口检查，不全程操控

- 开工前：有没有用户批准的任务、范围、边界。
- 提交时：Git 钩子检查是否越界。
- 收尾时：门禁判卷，通过才算完成。

## 6. 和工具的对接方式

只通过仓库里的文件和命令，不依赖任何工具自己的技能机制。新对话的第一步统一为：运行状态简报命令，读输出，再动手。

汇报固定分四块：**需要用户决定的 / 正在进行的 / 已完成的 / 出问题的**，不用卡号、门禁号等内部语言。

状态简报至少包含：项目和目录、源码与部署身份、采集时间、当前任务和需求版本、批准范围、执行身份和租约状态、检查点、冲突、未验证项、必要材料、下一步合法动作。通用简报不暴露租约密钥。

## 7. 任务性质变了怎么办

以“原来的批准是否仍然覆盖”来判断，不因为动作从写代码变成写文档就机械地拆卡。

| 情况 | 处理 |
|---|---|
| 原范围内必要的测试、文档、满足原验收的修复 | 原任务继续，留下过程记录 |
| 同目标同范围下换 IDE、模型或会话 | 原任务交接，按规则处理执行身份、新 Run 和租约 |
| 新增成果、改变验收、扩大文件范围 | 暂停受影响的部分，关联变更或后继任务，重新批准 |
| 新增下载、发布、删除、权限等风险 | 单独明确授权 |
| 顺手修邻近问题或额外重构 | 独立登记，不塞进旧任务 |

需求变更是新版本：记录改了什么、影响哪些任务，不静默覆盖已批准的内容。

## 8. 红线

> 以下是用户已确认的原文，保持原样：
>
> 驾驶舱不是 agent/IDE，不主导它们；不规定用户用哪个工具或模型；不静默扩大范围；自动调用模型（现 Codex 执行器）只是**可选便利**，不是主路径；没有运行过的检查不得报“通过”。

## 9. 看板

看板用驾驶舱自己的 GUI。项目库总览显示每个项目的状态；点进单个项目，任务按**执行中 / 挂起 / 规划中 / 废弃 / 归档**分栏，另有**待验收**和**已完成未归档**两个区域；能看到后续的任务计划、排期、预计成果。

## 10. 需求分析流程

用户给出原始需求（一段对话或一个 md）→ 用户选定的 Agent 分析 → 驾驶舱校验并预览分析报告 → 用户确认具体版本 → 固化成《需求分析》文档 → 关联到任务。文档可以变更，变更产生新版本。

版本管理从三类记录起步：**需求版本**（项目、稳定编号、版本、原始输入的引用与指纹、目标和不做什么、验收、待确认项、前一版本、修改理由）、**批准记录**（批准人、时间、具体版本、决定）、**影响关联**（任务绑定的需求版本、变更的影响和继续、暂停或重新批准的决定）。
