## 2. 一次迭代如何流动

`User 需求 → PM 角色只读 Grooming → CHG/Decision → Work 授权 → Run + lease → 全栈或 PLC 执行 → Checkpoint/handoff.v2 → 领域门禁 → PM 验收 → Work/CHG 关闭`

职责和真源：

- User 决定目标与批准开工；AI 承担调研、实现和验证。
- PM 是当前主 Agent 扮演的治理角色，不是 `pm-workflow` 技能。
- CHG/Decision 是授权真源；Work/Run/Checkpoint/lease 是执行状态真源；Git 是代码真源。
- PM_SESSION 已退役（用户 2026-10-10 裁决），不再生成或刷新，只作历史证据；handoff.v1 同为历史证据，换 Agent 只使用 handoff.v2。
- `pm-workflow` 已退役隔离，不使用、不读取、不注册。

## 3. 每次开始的固定动作

在工作区根目录执行：

```powershell
$ws = "C:\Users\fubai\Documents\My_Workspace"
& "$ws\.venv\Scripts\python.exe" "$ws\main.py" --version
& "$ws\.venv\Scripts\python.exe" "$ws\main.py" pm resume <PID> --json
```

只有以下条件同时满足，才可修改代码：Resume 无冲突；User 已批准；Decision 匹配 CHG；Work 已授权；Run、owner、owned paths 与 lease 有效；现有 dirty paths 已声明。否则只能 Grooming。

## 6. 换 Agent 或新建对话

- 一个独立需求或一个 CHG 建议使用一个新对话；同一 Work 的连续修复无需反复新建。
- 新对话不靠复制长聊天恢复，第一步始终是 `main.py pm resume <PID> --json`。
- 若已有 Run，接手方必须接受 checkpoint-bound handoff.v2 后再写；不能沿用旧 Agent 的 lease token。
- 若 Resume 返回 Work/Run 为空，新 Agent 只能调研，不能根据“上次做到哪了”的口头描述直接改代码。

## 7. 工作区整理边界

- 日常迭代不要求全仓 `git status` 为空；要求本 Work 的 owned paths、dirty paths 和提交边界可证明。
- 禁止 `git add .`、全仓格式化、reset/clean/stash 他人改动，或为绿灯修复无关历史债。
- 长期债务按独立 CHG 排队：旧 release ACL、历史 CHG 格式、全库 Ruff/Mypy、旧 PM_SESSION/台账投影。
- Obsidian 规范变更永远单独立 CHG-SPEC，审批、实现、注册表/索引同步均与产品代码变更分离。

## 9. 受治理实施卡的标准动作

适用于已获 User 批准、要落成提交的实施卡。全部命令在工作区根用 `.venv\Scripts\python.exe main.py` 执行；参数以 `main.py <命令组> --help` 为准。任一步返回非零即停止，不靠重跑变绿。

| 步骤 | 命令 | 要点 |
|---|---|---|
| 1 预检 | `implementation-card precheck --card-file <卡文件>` | 卡的路径表、指纹表与状态词必须通过 |
| 2 变更单 | `change create`，再 `change transition` 逐级到 implementing | 创建后依次 submitted、under_review、approved、implementing |
| 3 决策 | `decision create --change-id <CHG> --file <路径>`（每个 owned path 一个 `--file`） | 条件写进 `--condition`；范围不得超出卡 |
| 4 工作 | `continuity work create`，再 `continuity work authorize --decision-id <DEC>` | Work 的 scope 与 Decision 一致 |
| 5 运行 | `continuity run start`（带 `--owned`、`--worktree`、`--lease-token`、`--lease-seconds`），再 `continuity run transition --to RUNNING` | 在隔离工作树里改动；owner 与租约有效才可写 |
| 6 续租 | `continuity lease` | 长门禁期间定时续租，先确认第一次续租成功 |
| 7 检查点 | `continuity checkpoint create` | 绑定判卷结果与将提交的字节，必须在提交之前创建 |
| 8 门禁 | `doc check`（文档）、`plc check <PID>`（PLC）、`python check <PID>`（Python），再加卡规定的测试组 | 以退出码为准，不接受口头解释 |
| 9 提交 | 正常 `git commit`（pre-commit 与 commit-msg 钩子），不用 `--no-verify` | 提交说明带 CHG 编号 |
| 10 终态 | `continuity run transition`、`continuity work transition`，再把 CHG 推进到 completed | 验收与收口由 User 或其书面委托完成 |
| 11 对账 | `ledger reconcile <PID>` | 台账缺失、孤儿、不一致都必须为 0 |

换 Agent 时用 `continuity handoff` 创建并接受 handoff.v2，不沿用旧 Agent 的租约令牌。

## 10. 插急活（一个项目开着好几张卡）

适用于 TD-071 卡 1～4 合并部署之后；规则真源是根 `AGENTS.md` 的 WS-002。一个项目最多开 8 张卡，同一时刻只有一张“在干”；“切哪张、拿回哪张”只听 User 的，命令都要带 `--approval-evidence-ref`（User 原话位置）。

| 场景 | 命令 | 要点 |
|---|---|---|
| 看四栏 | `pm missions --pid <PID>` | 只读；在干 / 等你 / 搁着 / 已关，搁着的卡带断点摘要，超 7 天 `stale=true` |
| User 说先做 B | `pm switch --pid <PID> --to <B> --reason … --summary … --as <身份> --approval-evidence-ref …` | 一步完成“搁着手上的 → 拿起 B”；第二步失败时第一张稳稳停在“搁着”，原命令重跑只补没做完的那步 |
| B 还没开工 | 同上，然后 `pm confirm-start --mission-id <B>` | switch 只做第一步，并给出开工命令 |
| 拿回原来那张 | `pm unpark --mission-id <A> --as <身份> --approval-evidence-ref …` | 先核对工作树没被动过，再发新钥匙进本机钱包；看 `sync_note`、`overlap_note`，同步 `main` 后再干 |
| agent 自己要停 | `pm park --mission-id <A> --reason … --summary …`（不带凭据） | 只能放进“等你”，然后停下告诉 User |
| 新卡撞车或满 8 张 | `pm approve … --admission-release-ref <User 原话位置>` | 不带就拒并说明撞了哪张卡、哪些文件 |

`pm orient` 会显示“挂起: 支持 | 插队: 不支持”：正在干的卡不能被直接抢走，要切换只能先搁着。11-08 在 DJ-2026-009 上的实地演练步骤见 `01_Project自动化项目管理/Python自动化项目总库/02_在研项目/SW-2026-008_auto-pm_自动化项目管理工具/02_规划/TD-071_插急活实地演练脚本_DJ-2026-009_PM.md`。
