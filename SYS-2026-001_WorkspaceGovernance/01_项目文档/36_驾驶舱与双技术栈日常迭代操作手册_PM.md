## 2. 一次迭代如何流动

`User 需求 → PM 角色只读 Grooming → CHG/Decision → Work 授权 → Run + lease → 全栈或 PLC 执行 → Checkpoint/handoff.v2 → 领域门禁 → PM 验收 → Work/CHG 关闭`

职责和真源：

- User 决定目标与批准开工；AI 承担调研、实现和验证。
- PM 是当前主 Agent 扮演的治理角色，不是 `pm-workflow` 技能。
- CHG/Decision 是授权真源；Work/Run/Checkpoint/lease 是执行状态真源；Git 是代码真源。
- PM_SESSION 只是人工可读项目摘要，不能授权执行；handoff.v1 只是历史证据。
- `pm-workflow` 已退役隔离，不使用、不读取、不注册。

## 3. 每次开始的固定动作

在工作区根目录执行：

```powershell
$ws = "C:\Users\fubai\Documents\My_Workspace"
& "$ws\.venv\Scripts\python.exe" "$ws\main.py" --version
& "$ws\.venv\Scripts\python.exe" "$ws\main.py" pm resume <PID> --json
```

只有以下条件同时满足，才可修改代码：Resume 无冲突；User 已批准；Decision 匹配 CHG；Work 已授权；Run、owner、owned paths 与 lease 有效；现有 dirty paths 已声明。否则只能 Grooming。

## 6. 换 Agent 或新建对话

- 一个独立需求或一个 CHG 建议使用一个新对话；同一 Work 的连续修复无需反复新建。
- 新对话不靠复制长聊天恢复，第一步始终是 `main.py pm resume <PID> --json`。
- 若已有 Run，接手方必须接受 checkpoint-bound handoff.v2 后再写；不能沿用旧 Agent 的 lease token。
- 若 Resume 返回 Work/Run 为空，新 Agent 只能调研，不能根据“上次做到哪了”的口头描述直接改代码。

## 7. 工作区整理边界

- 日常迭代不要求全仓 `git status` 为空；要求本 Work 的 owned paths、dirty paths 和提交边界可证明。
- 禁止 `git add .`、全仓格式化、reset/clean/stash 他人改动，或为绿灯修复无关历史债。
- 长期债务按独立 CHG 排队：旧 release ACL、历史 CHG 格式、全库 Ruff/Mypy、旧 PM_SESSION/台账投影。
- Obsidian 规范变更永远单独立 CHG-SPEC，审批、实现、注册表/索引同步均与产品代码变更分离。
