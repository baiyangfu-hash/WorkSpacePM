## 1. 决策摘要

结论：**可行，但只能采用“受控 Dogfooding”，不能让正在修改的驾驶舱自行批准和发布自己。**

`pm-workflow + auto-pm 驾驶舱 + fullstack-engineer + plc-electrical-engineer` 能构成闭环，但四者不是平级编码角色：

| 角色 | 责任 | 禁止事项 |
|---|---|---|
| 用户 / CCB | 批准需求、取舍和最终验收 | 不承担代码调研与测试体力工作 |
| PM 技能 | 澄清、WBS、变更单、交接、PM_SESSION、台账收口 | 不直接实现驾驶舱业务代码，不自批变更 |
| 稳定版驾驶舱 | 提供项目状态、门禁、证据和回退控制面 | 不以候选版本的自检结果作为唯一放行依据 |
| 全栈技能 | 实现 Python/QML/CLI/测试，是驾驶舱代码主执行者 | 不代替 PM 改写最终台账和审批状态 |
| PLC 技能 | 作为 PLC 域客户和验收者，维护域测试样例与标杆验证 | 不直接成为驾驶舱 Python/QML 的共同 owner |
| `DJ-2026-005` | 验证 PLC 检查、模板、变量表、HMI 原型等真实能力 | 不承担驾驶舱产品账和发布账 |

当前成熟度处于“稳定控制面辅助的可重复自托管”：运行位已迁移，handoff 具备交接、Saga 保护和只读队列观察，候选 worktree 可由稳定版外部复核；仍保留人工 PM/CCB 审批，不追求无人审批的全自动发布。

## 3. 目标运行模型

### 3.1 三平面隔离

1. **稳定控制面**：使用已提交、已验证的驾驶舱版本执行建单、门禁和最终复核；运行时只读，不在其目录中开发。
2. **候选开发面**：每个驾驶舱变更在独立 Git worktree、`codex/` 分支和独立虚拟环境中实现与自测。
3. **证据平面**：每次运行用唯一 `run_id` 把基线 SHA、候选 SHA、命令、退出码和报告写入 `.auto-pm/reports/dogfood/<run_id>/`。

### 3.2 标准闭环

1. 用户批准范围后，稳定版驾驶舱创建 `CHG-SCPT` 与结构化交接请求。
2. PM 技能生成 `skill_context`，指定基线文档、目标、禁止项和验收命令。
3. 全栈技能在候选开发面实现驾驶舱代码并完成候选自检。
4. 稳定版驾驶舱从外部重新检查候选开发面，避免候选版本自证。
5. 涉及 PLC 域能力时，PLC 技能以 `DJ-2026-005` 或隔离夹具执行领域验收。
6. PM 技能核对证据后执行一次性收口；用户完成最终验收。
7. 失败时保留证据并回到稳定版，候选分支不得污染主工作树。

## 4. 强制护栏

- **双钥匙放行**：候选自检通过 + 稳定版外部复核通过，缺一不可。
- **禁止自批**：候选驾驶舱不能修改自己的批准状态或把自己的 handoff 标记为最终闭环。
- **干净树门禁**：创建候选 worktree 前，基线必须无未解释变更；运行态 JSON、数据库和缓存不得进入提交。
- **单一代码真源**：驾驶舱代码只在 `00_Infrastructure/auto_pm` 维护；旧母体代码进入只读回退态。
- **分层文档真源**：产品规划、变更和发布记录归 `SW-2026-008`；工作空间治理决策归 `SYS-2026-001`；不把历史变更档案复制到基础设施位。
- **原子收口**：先验证、再写 PM_SESSION/变更台账/反馈，最后消费 handoff；任一步失败都必须可重试且不能产生重复记录。
- **标杆防污染**：`DJ-2026-005` 未全绿前只能作为诊断标杆，不能直接反向提纯模板。
- **保留人工 CCB**：涉及规范库、项目结构、发布、删除或回退策略的变更必须由用户批准。

## 8. 回退方案

### 8.1 回退触发条件

- 候选版本导致稳定入口不可用、账目部分写入、门禁误放行或跨项目误修改。
- 同一 handoff 重试产生重复 CHG、重复 PM_SESSION 记录或错误 consumed 状态。
- PLC 标杆出现相对稳定基线的行为回归。
- 无法解释的工作树扩散或运行态文件进入提交。

### 8.2 回退动作

1. 停止候选执行，不修改稳定控制面。
2. 固化当前 `run_id` 证据、差异和失败日志。
3. 回到最近通过双钥匙门禁的提交；已合入的问题用新的回退提交纠正，不重写历史。
4. 保留旧母体代码回退入口，直到 M6 获批。
5. 修复后从新的候选 worktree 重跑全闭环，不复用不可信运行态状态。
