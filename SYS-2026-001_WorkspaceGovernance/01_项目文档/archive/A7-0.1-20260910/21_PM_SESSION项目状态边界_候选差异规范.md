# PM_SESSION 项目状态边界（候选差异方案）

**状态**：候选，未修改 PM-004、PM-010 或 Obsidian 法典。
**变更单**：CHG-SPEC-2026-011；**上位候选**：文档 20。

## 1. 待解决的矛盾

PM-004 要求 PM_SESSION 持有完整过程段落；PM-010 又要求它是最多 150 行的当前快照。两者不能同时承担 Work/Run 的细粒度执行日志，因此执行事实将迁出到连续性对象，PM_SESSION 保持项目状态投影。

## 2. 拟定边界

| 项目 | PM_SESSION 保留 | 迁出或仅引用 |
|---|---|---|
| 项目身份、目标、范围、风险摘要 | 是 | — |
| 当前批准 CHG、活跃 Work 摘要、下一合法动作 | 是，以 ID 和链接摘要表示 | 原始事件与回执 |
| 逐步执行日志、Agent 原始上下文、lease 心跳 | 否 | Work/Run/Handoff 记录 |
| 证据散列、Git/运行槽位摘要 | 是，有限摘要 | 完整 evidence/read_set |
| 历史决策 | 只列不可变决策 ID | 决策与变更记录真源 |

PM_SESSION 必须有 `schema_version`、`project_id`、`updated_at`、当前状态与规范化引用；超出快照容量的内容只保留链接和摘要。任何“由文本内包含某项目 ID 推导控制面”的规则禁止进入最终规范。

## 3. 对 PM-004 / PM-010 的后续修订策略

PM-004 改为定义项目状态字段、PM 写入权限及向 Work/Run 的引用规则；PM-010 改为定义 ≤150 行的可读快照、必填元数据和迁移兼容性。两份规范共同引用连续性协议，不互相复制对象定义。版本号、编号和正式文本均待 CHG-SPEC 发布审批时按注册表分配。

## 4. 验收与止损

Dogfood 要证明：同一项目可从 PM_SESSION 恢复摘要、从 Work/Run 恢复细节；SYS 主体不会错误指向 SW 控制面；旧 PM_SESSION 可只读解析；超过容量时写入被拒绝或产生明确引用。未通过前不得修改 PM-004、PM-010、`spec_registry.json` 或索引。
