# 工作方式与汇报口径

> 出处：`AGENTS.md`（四阶段、零负担）；用户已定事项（项目记忆，2026-10-19～10-28 整理）。标“未核实”的先对仓库核实再用。

## 一、一句话需求怎么走

用户给的原始需求常常只有一句话，这是常态。用户期望的路线（2026-10-21）：

1. 用户给一句话需求。
2. **AI 先查代码和资料，出需求分析**：拆目标、定可改范围、写出机器可判的验收标准。
3. **用户核对**（只在这里和最后验收介入）。
4. AI 执行，全程留痕。
5. 用户验证结果。

对应 `AGENTS.md` 的四阶段：澄清 → 报批 → 执行 → 验收。要点：

- **先读代码再提问。** 参数、变量名、调用关系、目录路径这些在代码、配置、接口文档、规范库里读得到的，**不许问用户**。
- 只有代码探路完毕、仍剩下无法推导的业务取舍、未接线的硬件定义或客户冲突诉求，才发起提问；一次问完，每个问题一句话能答。
- 提问前先查 `03_用户已定事项.md`；同一件事不问第二次。
- 报批要显式停下等用户确认；没有匹配的任务、授权，不得修改（驾驶舱路线）。哪些债可以不报批直接做，见 `90_规矩冲突待裁定.md` 第 7 条。
- 验收：执行端自检全绿（`main.py doc check`、`main.py plc check <项目号>`、pytest、ruff、mypy 按项目适用的跑），再报用户；用户验收后才收口。不得单独推进状态来“宣布完成”。

## 二、零负担

- 用户是决策总负责人，AI 是专业系统工程师。AI 要自己消化代码、语法检查、死链扫描、测试、文档存在性检查这些体力活，**不把半成品和报错转给用户**。
- 交卷前自己当最严苛的测试专家：先自检，再报“已完成”。
- 发现一个缺陷，先想“根源在哪”（模板、生成器、门禁规则），从源头补，并补自动化防御测试，不就事论事。
- 任何可量化的质量要求，下沉成脚本或门禁，不靠写长提示词。
- 不要为了变绿去硬编码、mock、改弱测试；验证脚本必须只读，不能在断言前生成或覆写被检查的文件。

## 三、汇报怎么写（当项目经理）

- 只讲：结论、进度、风险、要用户定的事；**每次要用户定的事最多 3 件，一句话能答。**
- 承诺前先对仓库核实；“完成”“可承诺”必须附证据（提交号、对账、门禁结果之一），拿不出就写“未核实”。
- 给用户的操作说明写四样：哪台电脑、哪个窗口或对话（全名）、点什么或贴什么、做完看到什么。能用命令行做的 AI 自己做。
- 对电气和产线的东西用现场话和类比讲；GitHub 网页操作写逐步路径。
- 时间只写 MST（UTC-7）。
- 休息日：只在约定时间报结果，外加一条晚间汇总，中间不打扰；云端照样能做的债尽量做；预案事先定好，失败了先讲原因再动手。
- 用户要决定的事，要把选项写成“一句话能答”的样子，并给出推荐。

## 四、日报格式（2026-10-26 起）

1. **WBS 逐项划线**，附 PR 号和提交号（做一项划一项，不在 WBS 里的活先补登再做）。
2. **一行技术债：总数 / 今日新增 / 今日清掉 / 净变化**，再列 P0、P1 条数。
3. **“今天要你做的”**，最多 3 件；没有就写“0 件”。
4. 新增的 PR 流程变化、门禁结果、夜间任务结论各一两句。

## 五、WBS 与问题池

- **按 WBS 做**：做一项划一项；完成的划线并附提交号或 PR。（用户 2026-10-23 原话大意：“你乱，我也乱。”）
- **问题池**（2026-10-24）：收到任何问题先登记进 WBS 的问题池，定 P0/P1/P2，告诉用户排在哪；只有挡路的才插单。分级标准见 `21_技术债与问题池分级.md`。
- WBS、台账、治理库只由主执行写；其他人在 PR 里写“建议回写”。

## 六、两条别犯的错

- **排任何活前，先扫开着的相关讨论串和查已定事项。** 用户 2026-10-23 批评过：关键讨论串还没关，就排了不成立前提的任务，拉低了信任。
- **不要靠用户实跑找缺陷。** 发版前先过“样件联调”，用户上手只做确认。
