# 第二 GitHub 账号怎么用

> 用途：Trae 里的 AI 通过 GitHub 连接器推分支、开 PR、写评论时，用的是**专门给它注册的第二个账号**，不是用户本人的账号。本篇讲这个账号能做什么、不能做什么、怎么确认没用错账号、用错了怎么办。
> 出处：Trae 全面接手路线图第八节（共享文件夹，协调者 2026-10-29 定）；`reviews/tools/safety_zone_check.py`（仓库里可核）；`90_规矩冲突待裁定.md` 第 5 条。**账号注册、授权、规则集怎么设，由用户和协调者在共享文件夹里处理；账号登录名和授权细节按 `90` 第 5 条不写进公开仓库**。写不准的标“未核实”。
> 本篇写于账号注册之前：第六节列出的几项要等账号真的建好、授权好以后才能核。

## 一、为什么要有第二个账号

连接器授权的是哪个 GitHub 账号，AI 动手时就是哪个账号。如果 Trae 里授权的是用户本人的账号，Trae 的任何会话都能以用户本人的名义写评论、点合并，包括“安全签字”。机器分不出那条评论是用户亲手写的还是 AI 代写的（`safety_zone_check.py` 开头的说明里就写着这个已知漏洞）。

电气上的类比：不能把主管的安全门旁路钥匙挂在操作工腰上，所以给操作工另配一把**只能开机、开不了旁路**的钥匙。第二个账号就是这把钥匙。

## 二、这个账号能做什么、不能做什么

| 事 | 能不能 | 说明 |
|---|---|---|
| 推自己前缀的分支（`trae/…`） | 能 | 分支名规矩见 `AGENTS.md` WS-001 |
| 开 PR（先开草稿）、在自己的 PR 上回应审计意见 | 能 | PR 描述照 `.github/pull_request_template.md` 填 |
| 审计会话把审计结论贴到被审 PR 的评论里 | 能 | 审计怎么做见 `AGENTS.md` AUD-001；审计的会话不能是写这个 PR 的会话 |
| 在 GitHub 的 Actions 页手动触发检查（例如改受保护清单的 PR 要手动跑一次 `sw008-ci`） | 能 | 需要 Write 权限；Trae 能不能点这个页面：**未核实** |
| 在评论里写“安全签字 …” | **不写** | 即使写了，`safety-zone` 也只认用户本人登录名加数字 ID 的评论，其他账号一律“不是指定签字人，不算”。写了不会过，还会让人误会 |
| 点合并 | **等用户定** | 现在没定：只有用户点，还是单独的“合并会话”点（`90` 第 5 条）。没定之前，Trae 只做到 PR 备好、审计过、CI 绿，然后告诉用户可以合 |
| 改仓库设置、规则集、分支保护 | 做不到 | 账号只有 Write 权限，不是管理员；不要想办法绕 |
| 删分支、删文件 | **不做** | 要用户回“收”（`02` 第一节） |
| 改 `AGENTS.md`、`.trae/`、规范库文字 | **不做** | 要用户原话（`02` 第一节） |

## 三、开 PR 前先确认用的是哪个账号

每个 Trae 会话**开第一个 PR 之后**，打开 PR 页面看**作者**那一栏：

1. 作者是第二个账号：正常，往下走。
2. 作者是用户本人的账号：**停**。不开第二个 PR，不写评论，不点合并，把 PR 链接和“作者是用户本人账号”原样报告给用户，等用户把 Trae 里的授权换回第二个账号。已经发出去的 PR 和评论不自己删（删除要用户回“收”）。
3. 看不出作者是谁：当作第 2 种处理，报告。

注意区分：提交里的“作者”是 `git config` 里的名字，不代表 GitHub 上是谁发的；以 PR 页面显示的为准。

## 四、验证这个账号确实代签不了（账号建好后做一次）

1. 用第二个账号开一个**测试 PR**（只改一个无关紧要的文档文件，PR 描述里写明“测试 PR，不合并”）。
2. 在这个 PR 上用第二个账号写一行评论：`安全签字 <PR 头提交号前 12 位>`。
3. 看 `safety-zone`（`.github/workflows/safety-gate.yml` 产生的检查）的详情：应该出现“不是指定签字人，不算”，并且**不因这条评论而通过**。注意：只有碰到安全区或写了“安全回路: 是”的 PR，`safety-zone` 才要求签字；测试 PR 要照 `02` 第二节的做法让它落在要签字的范围里，否则这个检查本来就不要签字，看不出区别（怎么构造这样的测试 PR：**未核实**，先和协调者商量）。
4. 结果贴给用户：PR 链接、`safety-zone` 的原文提示。看到“算”或检查绿灯，立刻报告，这是严重问题。
5. 测试 PR 关闭，不合并；分支留到用户回“收”再删。

## 五、出事了怎么办

| 现象 | 做法 |
|---|---|
| 连接器提示授权过期、推送被拒 | 原样报告用户；**不用用户本人账号顶替**，不去网页上手工操作用户的登录状态，不把令牌写进任何地方（`02` 第三节） |
| PR 作者是用户本人账号 | 见第三节第 2 点 |
| 第二个账号的权限被网页提示“需要审核/不够” | 报告；不换别的账号 |
| 有人（或 AI）在 PR 里用第二个账号写了“安全签字” | 照常报告用户；这条评论不会被认，也不会让 `safety-zone` 通过 |
| 想让第二个账号去合并安全区的 PR | **不做**。安全区的 PR AI 自己不合，留给用户（`02` 第二节） |
| 想让第二个账号去合并改 `.trae/`、`AGENTS.md`、规范库的 PR | **不做**。这几类改动要先有用户原话（`02` 第一节），没有原话不合；合并由谁点见 `90` 第 5 条，没定之前等用户 |

## 六、未核实（账号建好、授权好以后补）

- 第二个账号的建立日期、授权到期或重新授权的日期：**未核实**。账号建好后只在本篇写日期，不写任何凭据、邮箱或登录名。
- Trae 的 GitHub 连接器是否支持换账号、只授权一个仓库、撤掉用户本人的授权：**未核实**，路线图第八节原文也写“试时现场验”。
- 仓库规则集里管理员、Trae 账号是否都不在绕过名单，是否要求指定人审核（`CODEOWNERS`）：**未核实**，仓库里目前没有 `.github/CODEOWNERS`。
- 第四节的测试 PR 怎么构造才能让 `safety-zone` 真的要求签字：**未核实**。
