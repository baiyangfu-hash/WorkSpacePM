# GitHub 打不开时的完整做法

> 用途：`26_出事了怎么办_一页纸.md` 第二节只有半页，讲“照常本机提交、有网再推”。本篇把它补全：怎么判断是不是真的打不开、断网期间哪些事还能做、PR 怎么排队、没推出去的提交怎么备份、恢复后怎么补开。
> 出处：用户 10-22 已定“断网照常本机提交”（`03` 第 24 行）；命令和行为都对着仓库里的脚本核过，核不到的标“未核实”。本篇**不新增规矩**，凡是“建议”的地方都写明了，用户没有定过。
> 总原则不变：拿不准就停下报告；不换远程地址、不把令牌写进任何文件、不用 `--no-verify`（`02` 第三节）。

## 一、先判断是不是真的打不开

三种现象要分开，处理不一样：

| 现象 | 怎么确认 | 意思 |
|---|---|---|
| 浏览器打不开 github.com，但 git 能推能拉 | 在仓库里敲 `git ls-remote origin main`，能打印出一个提交号和 `refs/heads/main` | git 是通的，网页不通。照常推拉，PR 评论和 Actions 页暂时看不了 |
| git 推拉报错，网页也打不开 | 同一条命令挂住不动，或报连接失败 | 真的打不开。走本篇第二节以下 |
| 只有 Trae 的 GitHub 连接器报错 | `git ls-remote origin main` 正常 | 是连接器授权或服务的问题，不是网络。原样报告，**不要**改用别的账号或令牌顶替（`27` 第五节） |

`git ls-remote` 只读，不改任何东西。命令挂住时按 Ctrl+C 结束；超过一两分钟没反应就当作不通，不要连敲十几遍。

## 二、断网期间，哪些事能做，哪些不能

| 事 | 能不能 | 说明 |
|---|---|---|
| 在本机写代码、写文档、提交 | **能** | 提交检查（`commit-msg`、`pre-commit`）不联网，拦的内容和有网一样（见 `26` 第二节） |
| 本地检查：`main.py doc check`、`main.py plc check <项目号>`、pytest、`ruff`/`mypy` | 能 | 都在本机跑 |
| 越界检查本地试跑：`python reviews/tools/pr_scope_check.py --base <基线提交> --head <分支头提交>` | 能 | 脚本里没有任何联网调用（已核）；用来提前发现“可改范围”漏了文件 |
| 自己审计别人的 PR：`python reviews/tools/audit_pr.py <PR号> --offline` | **有条件** | 要求本机已经有 `refs/audit/pr-<号>` 和 `origin/main`（以前审过、取过才有）；没有就报错，不能凭空审。CI 结论查不到，脚本会标 UNVERIFIED，要在报告里写“CI 结论未核实” |
| 开 PR、看 CI、看评论、合并、触发 Actions | **不能** | 都要联网。不要为了“显得做完了”在本地假装合并 |
| 拉别人刚合并的改动 | 不能 | 本机的 `origin/main` 是上一次 `fetch` 的样子，**会越来越旧** |
| 控制根同步提示（`[控制根同步]`） | 只能参考 | 它**从不联网**，比的是本机已有的 `origin/main`（脚本头注释写明只读、不 fetch）。断网时它说“没落后”，只代表“相对上次 fetch 没落后” |

## 三、PR 怎么排队

断网期间能完成的是“PR 的原料”：一个自检全绿的分支。每做完一个分支，在**工位里的 `.agents/` 目录**建一份排队记录（这个目录里的过程文件不入库，`.gitignore` 已覆盖；`AGENTS.md` DEV-TMP-001 第 4 条规定过程文件只放这里。具体用哪个文件名：**建议** `.agents/pr_queue.md`，没人定过），每个分支写一段：

```
## <分支名>
- 基线：<敲 git rev-parse origin/main 得到的提交号>（断网时的“旧 main”）
- 拟定 PR 标题：<一句话>
- 可改范围（每行一个完整路径，锁定文件逐字写完整路径）：
  - <路径 1>
  - <路径 2>
- 安全回路：是 或 否
- 本机已跑的检查和退出码：<命令 → 退出码>
- 变更单：<CHG 号或“待取”；取号方式见 26 第六节>
- 备注：<要等的东西、风险>
```

规矩只有三条：

1. **一个分支一张卡**，分支前缀照 `AGENTS.md` WS-001，不把几件事混进一个分支。
2. **排队记录里没有的东西，恢复后不凭记忆补**。排队记录是恢复后写 PR 描述的原料，写不全就是“未核实”。
3. 排队的 PR 一多（**建议**超过 5 个）就叫用户：基线越旧，恢复后冲突越多，用户可能想先停下新活。数字是建议，没人定过。

## 四、没推出去的提交，怎么备份（防电脑出事）

提交只在本机时，这台电脑坏了就全丢。有 `git bundle` 可以把“没推出去的提交”打成一个文件，拷到另一块硬盘或 U 盘。这一节的命令我在一个临时仓库里实跑过（建包、校验、从包里取回分支，都成功），但没有在 Trae 环境里跑过：**未核实**。

1. 先把要备份的改动提交到本机分支（**没提交的改动不会进包**；提交时检查照常拦）。
2. 打包（把 `<分支>` 换成你的分支名）：
   `git bundle create <备份文件>.bundle origin/main..<分支>`
   这样包里只有这条分支比本机 `origin/main` 多出来的提交，文件很小。
3. 校验：`git bundle verify <备份文件>.bundle`，看到 `okay` 才算备份成功。
4. 把 `.bundle` 文件拷到**仓库以外**的地方（另一块硬盘、U 盘）。**不要放进工作区**，也不要提交进仓库。
5. 要从包里取回：在一个能看到同一个 `origin/main` 的仓库里敲
   `git fetch <备份文件>.bundle <分支>:<分支>`
   取回的是普通分支，之后照常推。

这只是**保险**，不能代替推送：PR 和 CI 仍然要等网络恢复。

## 五、网络恢复后，怎么补

1. `git fetch origin main`（先对齐，再继续；别在落后的基线上接着改，见 `26` 第二节第 6 条）。
2. 对每个排队分支，先看 `main` 有没有动到它的可改范围：
   `git diff --stat <排队记录里的基线>..origin/main -- <可改范围里的路径>`
   - 没有输出：没动，直接推、开 PR。
   - 有输出：先把 `origin/main` 合进自己的分支（`git merge origin/main`，只动自己的分支）。有冲突就**停**，原样报告冲突文件，不自己硬解。（合并还是变基，没人定过，本篇**建议**用合并，因为不改写已有提交；**未核实**用户是否另有偏好。）
3. 变更单号可能撞了：排队期间别人可能已经合并了新的变更单。按 `26` 第六节取号的第 ② 步再查一遍开着的 PR，撞了就改号。
4. 开 PR，描述照模板填；“证据”里写明“断网期间本机完成，排队 N 天”，并附本机检查的退出码。
5. 对着新头再看一次 CI。CI 是在最新头上跑的，本机断网时跑过的检查不能当 CI 结论用。
6. 需要独立审计的 PR，按 `AGENTS.md` AUD-001 找另一个会话，用 `audit_pr.py <PR号>`（联网版）重新审，不用断网时的离线结果顶替。
7. 补完后在排队记录里把该分支标“已开 PR”，等 PR 合并再清理记录，不提前删。

## 六、什么时候叫用户

- 连不上超过半天（`26` 第二节第 6 条，协调者定的试行口径）。
- 排队的 PR 超过 5 个，或某个分支冲突解不开。
- 需要决定“要不要换一种方式联网”。**不要自己试代理、镜像或换远程地址**：用户没有定过这类做法，换了地址可能把代码推到不该去的地方。
- 需要有人在网页上点合并、点批准，而自己做不到时。

## 七、未核实

- 不同网络环境下 GitHub 不通的具体表现（只网页不通、只 git 不通、时通时断），本篇的判断表是按 git 和网页各自的通路写的，**没有在真实被限制的网络里试过**。
- Trae CN 里终端的 git 是否走系统代理、连接器是否另有通路：未核实。
- 备份文件放哪（要保证随时拿得到的位置）和多久备一次，没有人定：本篇只写命令，不写地点。
- `.agents/pr_queue.md` 这个文件名是**建议**，不是现行规矩。
- 合并还是变基（第五节第 2 步）没有被用户定过。
