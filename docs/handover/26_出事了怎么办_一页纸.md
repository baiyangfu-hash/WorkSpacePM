# 出事了怎么办（一页纸）

> 用途：Trae 接力、协调者不在线时，遇到下面五种情况，照这一页先稳住、再恢复、再找用户。**本页不新增规矩**，每条都指向已有手册或代码；查不到出处的标“未核实”。
> 总原则：拿不准就停下报告；“不做的事”以 `02_必须用户亲口同意的事.md` 第三节全文为准；“好了”要附证据，没有就写“未核实”。

## 一、卡住了（命令不动了、租约过期、Run 还写着“在运行”）

1. **先只读看**：`pm orient <项目编号> --json`（旧发布版没有这条命令，报 `No such command 'orient'` 就改用 `pm resume`，不是故障）。
2. **命令输出建议 `--fix`、`doc sync` 一类修复命令：不运行**，原文报告，停下等用户（`25` 第三节）。
3. **租约过期、续租被拒**：已过期的不自己换身份绕过，原样报告；以后手敲长命令一律用 `continuity lease run-with-renewal` 包起来（`22` 第七节）。
4. **主控或电脑重启后 Run 还是 RUNNING**：在跑执行代理的那台电脑、控制根里敲 `pm recover --run-id <Run>`（只读）。ALIVE 等着；UNKNOWN 什么都不改、同一用户再敲一次、仍 UNKNOWN 就报告；DEAD / PID_REUSED 先报告用户，持有租约的人才可加 `--apply --lease-wallet`（`22` 第八节，结论只对本机本用户、不在容器里的执行代理有效）。
5. **不要做**：不开新 Run、不清理工位里的半成品、不结束任何进程。
6. **叫用户**：UNKNOWN 持续、DEAD 要 `--apply`、租约已过期要回收。

## 二、GitHub 打不开（推不上、拉不下、网页开不了）

1. **照常在本机提交**，有网再推；断网不影响本机提交（用户 10-22 已定，`03` 第 24 行）。
2. 提交检查（`.git/hooks` 里的 `commit-msg`、`pre-commit`）不联网，断网和有网拦的是同样的东西（`0100_PLC自动化/00_通用规范/无AI离线手册.md` 第 5 节在断网沙箱里实测过）：
   - 提交里有生产代码（`.scl`/`.st`/`.py` 等）时，说明里必须**恰好写一个** CHG 号，没有或多于一个都拦（`git_hook_enforcer.py` 的 `commit-msg`）。“用 BC 号也放行”只是修复卡 A 的计划，**现在还不是现状**。
   - PLC 项目的文档与代码一致性检查只对 PLC 项目的提交生效。
   - 纯文档提交不要求 CHG 号。
   - 被拦时：**AI 不得 `--no-verify`**（只有用户本人在 `manual/` 分支可以，`02` 第三节），原样报告拦在哪条、提示原文，停下。
3. 控制根同步提示出现“未核实”：离线时不影响入箱与批准，开工前联网后再看一次（`control_root_sync.py` 的提示原文）。
4. 只用仓库已有的远程，不换地址，不把令牌写进任何文件（`02` 第三节）。
5. 云端 Trae 的克隆是单分支克隆、没有 `origin/main`：先 `git fetch origin main`，再 `git switch --detach FETCH_HEAD`（`90` 第 9 条）。
6. **叫用户**：超过半天仍连不上；需要判断“要不要等”时。网络恢复后先 `git fetch origin main` 对一次再继续，别在落后的基线上接着改。

## 三、CI 红了

1. **先看红的是不是你这个 PR 的**：点开失败的那项看日志，再看 `main` 上同一项是不是也红。红在 `main` 的，别人已有修复就把那个修复端口进来，没有就报告，别自己放宽检查（`22` 第六节）。
   - “偶发”不是根因；只在检查还没跑到测试就死了（拉取、安装、机器丢失）时**只重跑一次**，第二次再红就是真的。
2. **按 FIX-001 修**：先写根因，再全库查同类，清单写进 PR；修完在本地把同一条检查跑绿再推。
3. **常见几种**（出处 `01` 第二节、`25` 第三节）：
   - `gate` 报越界：“可改范围”漏了文件，补全路径（锁定文件要逐字写完整路径），不要放宽目录前缀。
   - `safety-zone` 要签字：只认用户本人在评论里写“安全签字 <提交号至少 12 位>”，AI 不代写。
   - `sw008-ci` 没跑：纯文档 PR 或改“受保护清单”的 PR 要在 GitHub 的 Actions 页手动触发一次。
   - 判卷脚本（`reviews/tools`）红：先本地跑 `python -m pytest reviews/tools -q -p no:cacheprovider -o addopts=`（`25` 第二节）。
4. **不要做**：不跳过、禁用或隔离测试求绿；不推空提交、不关了重开 PR 来“踢”CI（`22` 第六节）；其余见 `02` 第三节全文。
5. **叫用户**：同一条检查你修了两轮仍红；红的是判卷脚本的判定本身（改判定要先问用户，`02` 第 16 行）。

## 四、控制根落后 `main`

1. **症状**：`pm inbox add`、`pm approve`、`pm resume`、`pm orient`、`pm verify` 这几条命令会在屏幕上打印 `[控制根同步]` 提示，写着“控制根落后 origin/main N 个提交”。
2. **只允许的恢复**：在控制根执行 `git fetch origin main`，再 `git merge --ff-only origin/main`（只快进，不改你的文件；`control_root_sync.py` 提示原文）。
3. **快进不了**（本地有 main 里没有的提交，或有重复提交、未提交文件）：**停**。不 `reset`、不删、不重复推 PR，把提示原文给用户。控制根里未跟踪或未提交的东西只备份、入库、加忽略，**绝不删**（`02` 第三节）。
4. **`run start` 现在并不会拦**（只打印提示，对应的 P1 还没修）：看到提示就必须先停下同步，**不得开 Run**。台账、WBS、发布指针只由主执行写，工位里的 agent 不写（`AGENTS.md` WS-001 第 6 条）。
5. **叫用户**：快进不了；控制根里有不认识的未提交文件。

## 五、工位满了（`.auto-pm/worktrees` 下目录数到上限）

1. **症状**：`worktree open` 报“已有 N 个目录，上限 8（WS-001）”；发版前 `doctor --pre-release` 超过 7 个会失败（`agent_worktree_service.py` 常量 `MAX_STATIONS=8`、`RELEASE_FREE_PLACES=1`）。
2. **先看**：`main.py worktree list`（只读）。看每个目录有没有未提交、未推送、是否已并进 `main`、是否闲置超过 3 天。
3. **自己收自己的**：自己名册内、分支已并进 `main` 的工位，用 `worktree close <自己的agent名>` 收（#486 已合；有未提交改动或没推送提交的，工具本来就不动）。
4. **批量删除必须用户亲口回“收”**：`worktree sweep` 默认只列清单，加 `--apply` 才删，而且必须先把清单给用户、等到用户回“收”；别的 agent 的工位、保留名单里的目录（`m3-pr-chg470`、`gui-trial`、`trae`）不碰。删目录或远程分支同理（`02` 第一节第 11 行）。用户没回，就停在“满了”这件事上，别绕过。
5. **标成“残缺目录”的**：只报告，不清。在工位里敲 `git add -A` 之前先跑 `git rev-parse --show-toplevel`，看到的必须是自己的工位，不是控制根（`01` 第六节）。
6. **叫用户**：需要删除时（给清单等“收”）；`list` 里出现你不认识的目录。
