# 技术债与问题池分级

> 出处：`plans/技术债清理计划_20261025.md`（共享文件夹，**不在仓库里，待搬**）；`AGENTS.md` FIX-001；用户已定事项。**数字是快照，会过期**，以 `SW-2026-008` 项目下 `04_监控/02_整改项/` 里的活动技术债台账为准；台账只由主执行写。

## 一、分级标准

| 级别 | 标准 | 处理 |
|---|---|---|
| P0 | 挡发版，或挡真实项目，或**同一问题第二次出现** | 马上插队修，当天开 PR |
| P1 | 影响日常使用或门禁，但不挡 | 本周内清，每天 2～3 条 |
| P2 / P3 | 不影响当下 | 排队；空闲的云端额度顺带清；不设清零日期，目标只降不升 |

**规矩：同一问题出现第二次，直接升 P0。** 配合 FIX-001：修一条必须附同类排查，防止它再冒出来第二次。

## 二、怎么清

1. **先对账**：台账里的状态常常落后于实际（修了没改状态）。第一步只改状态、不写代码，通常能直接减一批。对账由主执行写台账，云端只提“建议回写”。
2. 每天清 2～3 条小债；一条一个小 PR；走审计和 CI。
3. 每个 PR 附同类排查清单：根因是什么、全库同类写法怎么查的、逐条修了还是不修（写理由）。
4. 真正的杠杆是**少新增**：审计发现问题先看同类，一次修一类；新增不降下来，曲线不会往下走。
5. 认领先登记：在认领清单里写债号和预计改的文件，再动手；两边预计改的文件有交集，后登记的换债。认领清单现在在共享文件夹 `plans/驾驶舱技术债认领_*.md`（待搬）。
6. 不做、要问用户的类型：含 PLC 的债、安全区、改 `AGENTS.md`/`.trae/`、需要用户裁决或删除的债（治理记录类）、大设计或大重构。

## 三、修复卡的硬要求（FIX-001）

- 修缺陷先写根因，再把全库同类写法一次查全，清单写进卡里或 PR 里。
- 只修挡路的一处不许报“已修好”；技术债关单要证明根因已经除掉。
- 修好后要补**反例测试**，并做“变异验证”：把修好的地方改回旧写法，新测试必须变红。
