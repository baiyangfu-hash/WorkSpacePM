# 门禁、发版与长任务

> 出处：用户已定事项和项目记忆（2026-10-19～10-28 整理）；`SW-2026-008` 下 `scripts/long_gate.py` 及其测试。**细节以仓库里的脚本为准**，本文只讲规矩和为什么。标“未核实”的先核。

## 一、两层门禁

- **日常快门禁**：GitHub 上的检查（`gate`、`safety-zone`、`reviews-tools` 是 main 必过检查；`sw008-ci`、`plc-ci` 等按路径过滤，纯文档或只改工具的 PR 要手动触发，见 `01_角色分工与流水线.md`）。
- **重门禁**：九组全量回归（G1～G9），只在**发版前**跑；用户 2026-10-19 定“重门禁只在发版跑，日常用 GitHub 快门禁”。

## 二、判卷规矩（机器无情判卷）

- 退出码非零就打回重做，不听口头解释。
- **每组通过数、跳过数必须先实跑再填，不凭印象填。** 修复产生新提交，要整轮重跑（约 3 小时）。
- 下一张卡测试数变化的，一律实跑再写。
- “改判卷口径”（例如按测试名对不对，而不是数数）已登记，**是改判定，要用户点头**（出处：协调者 2026-10-28 定，待用户确认）；在此之前沿用数数判法。
- 门禁的 `known` 基线比对：只拦**新增**的失败，已知老失败不拦；基线不在 main 上要写说明。

## 三、长门禁怎么跑（不被中断）

- 起法：`scripts/long_gate.py` 的 `launch / run / status / stop`。Windows 上用一次性计划任务（电池下也跑、12 小时上限）；续租和防休眠是进程内线程；**跑完的组（过或不过）不重跑，只重跑没跑完的组**；配置字节或工作树指纹变了拒绝续跑；续租失败或剩余不到 10 分钟是最终硬停止。
- 后台**隐藏运行**，不弹窗口（弹窗被关掉会杀任务）。门禁期间不要开虚拟机（同机抢资源，计时类测试会误报）。
- 用户不想守窗口、贴命令、被吵醒：**门禁 AI 自己跑、夜里跑**；计划一变立刻告诉用户。
- 笔记本重载任务（全量测试、长门禁）：**17:00～21:00 MST 禁跑**，要防休眠，不和用户在场的操作同时跑；开跑前挂一个到时检查的提醒。云端清债不受这条限制。
- 合盖会睡眠、注销会停；起任务前确认电源和登录状态。

## 四、样件联调

- 用假任务当样件，在临时目录从入箱一路跑到 `close_accepted`、变更单完成、对账 0/0/0。命令：在 `SW-2026-008` 目录运行 `python scripts/sample_drill.py`（约 2 分钟）；CI 有对应工作流。
- 教训：**样件目录结构要贴近现场**，否则漏缺陷；新项目迁入前先拿它的目录复制做样件跑一遍。
- 用户上手前先过样件联调；用户只做确认，不负责找缺陷。

## 五、发版与切换

- 发版版本号形如 `1.3.3-<提交前7位>`；切换后本机跑的就是新版本。
- **切换发布只认用户亲口说**（在主执行会话里打的字，可以带条件预授权）。
- 切换后跑 `main.py ledger reconcile <项目号>`，目标是 0/0/0（三项都为 0）。
- 回退要先切版本再 `restore-backup`；带“单向”变更的发版，切换前先 `main.py continuity backup` 并 `verify-backup`。
- 启动器（`00_Infrastructure/auto_pm/launcher/launch.py`）的改动算部署，要用户授权一张部署卡，攒几条一起做，不为单条改动单独部署。

## 六、遇到失败怎么办

- 先看是不是这个 PR 的：同一个检查在 main 上也红，就不是它的；该端口别人的修复就端口进来。
- “偶发”不是根因；只在检查还没跑到测试就死了（拉取、安装、机器丢失）时重跑一次，第二次再红就是真的。
- 不许跳过、禁用或隔离测试求绿；不许推空提交或关了再开 PR 去“踢”CI。

## 七、手工跑长命令，别让租约过期（2026-10-30，依据 #354/#359/本卡）

- 默认租约 30 分钟（代码常量 `DEFAULT_LEASE_SECONDS`=1800 秒，有测试钉住本句与常量一致）。在 Run 里手敲一条要跑十几分钟的命令（全量 pytest、`pm verify`），没人续租就会过期，过期后自己续不了，只能靠主执行回收。
- **长命令一律用包装**：`main.py continuity lease run-with-renewal --run-id <Run> --owner <你> --lease-wallet -- <命令…>`（`--` 后面是要跑的命令，退出码原样返回；命令最长跑 `--timeout-seconds`，默认 4 小时，超时被终止并以 124 退出）。包装只做一件事：每三分之一租约时长续一次租，命令结束就停；第一次续租失败就不启动命令；命令拿不到租约口令。续租反复失败、租约快过期时包装会放弃续租并**终止命令**，以 125 退出（先查租约再决定是否重跑），不会让命令在没有租约的情况下一直跑下去。
- `pm verify` 已内置续租：验证中途续租被拒（例如到了 3 小时上限）时，结果里多一个 `lease_keepalive_warning`，不阻断验证，看到它先查租约。
- 包装**只续租、不延长**总上限：每个 Run 最多持有 3 小时（#354）。要更久只能用户本人 `lease extend-hold`；用户批准派发的长门禁由 `long_gate` 用批准记录自动延长一次（合计 13 小时）。
- `lease renew` 必须带 `--idempotency-key`：同一次续租重试用同一个 key，下一次续租换新 key（例如 `<run-id>-renew-v<当前版本>`）。
- 在 `VERIFYING` 状态续租需要 #359（放宽拦截，用户点头后才合并）；合并前，verify 开始前先续满一次 `--lease-seconds 3600`。

## 八、主控重启（或电脑重启）后，Run 还写着“在运行”怎么办（TD-074，2026-11-01）

**现在是什么情况**：驾驶舱主控好比总控柜，执行代理好比车间里的执行机。总控柜断电重启时，执行机可能还在转，也可能已经被一起带走。账本不会自己知道，Run 会一直写着 `RUNNING`。

**先判断，别猜**（只读，不改账本，不结束任何进程）：

1. 在跑执行代理的那台电脑上，窗口选控制根的终端，敲：`python main.py pm recover --run-id <Run 编号>`（Run 编号在 `pm orient` 的输出里；`pm orient` 看到 Run 是 RUNNING 时会直接把这条命令打出来）。知道派发时的操作编号也可以改用 `--operation-id`。
2. 命令先写“现在的情况”，再写“下一步”，时刻都按 MST 显示。账上这个 Run 不在 RUNNING 状态（例如还没开始跑）时，命令会直说“不用对账”并告诉你敲 `pm orient` 看当前 Run。四种结论各自怎么办：

| 结论 | 意思 | 你该做什么 |
|------|------|------------|
| ALIVE | 执行进程还在转 | 什么都不用敲，等它结束。要中途停它，问用户；驾驶舱不替你结束进程 |
| UNKNOWN | 这台电脑读不出进程状态 | 什么都不要改；确认你在跑执行代理的那台电脑上、用同一个用户再敲一次；仍是 UNKNOWN 就原样报告用户 |
| DEAD | 记录的进程已经不在了 | **先确认你就在跑执行代理的那台电脑上**（在别的电脑上敲，进程号不存在，也会得到 DEAD，那是误判）。**执行代理如果跑在容器（Docker/WSL 等）里，或用的是另一个系统用户，这台电脑也看不到它的进程，同样会误判成 DEAD：这种情况这个结论不可信，不要 `--apply`。**然后先别自己开新 Run，也不要清理工位里的半成品（里面可能有它没做完的改动）。把输出报告用户后，持有这个 Run 租约的人敲 `python main.py pm recover --run-id <Run 编号> --apply --lease-wallet`，把它在账上记为失败 |
| PID_REUSED | 进程号现在属于另一个更晚创建的无关进程，原执行进程已经不在 | 同 DEAD；驾驶舱不会去碰那个无关进程 |

**`--apply` 做什么、不做什么**：只在 DEAD / PID_REUSED 且 Run 当前是 RUNNING 时，把 Run 记为失败，失败原因 `EXECUTOR_LOST`（执行进程已不在；它不等于 `TERMINATED`“被我们终止”）。进程活着、判不出（UNKNOWN）、Run 已是别的状态、口令对不上、租约已过期，一律拒绝并说明原因，账本一个字都不改。租约已过期时不要硬改，按 `pm orient` 给的 `RECLAIM_EXPIRED_RUN` 走回收。租约默认只有 15～30 分钟，所以 `--apply` 只在“主控重启后租约还没到期”的窗口里有用，重启久了多半是回收那条路。不清理工位，不开新 Run；记为失败之后开新 Run 需要用户批准，新 Run 开工时用 `--declared-dirty` 声明工位里留下的未提交改动。`--apply` 会写账本，所以和别的写命令一样要过“运行身份”检查（在登记过这个项目的那台电脑上敲）。

**边界（别越）**：`pm recover` 不带 `--apply` 时只是看，不落账；驾驶舱任何时候都不替你结束进程；重新开 Run 要用户批准。结论只对**这台电脑、这个系统用户、不在容器里**的执行代理有效（账本里的进程证据不含主机标识）。失败记录里只有失败原因代码；账本记的进程号和启动时刻本来就在启动记录里，“这台电脑现在看到的创建时刻”和判定结论只在命令输出里。所以 `--apply` 成功后，命令会把这 4 行依据完整打印出来，**请贴进这个 Run 的变更单或报告**，事后才核对得了当时为什么判定进程已不在。

**不能回滚**：一旦用 `--apply` 写入过 `EXECUTOR_LOST`，这个账本就不能再换回不认识它的旧版本（旧版读到不认识的失败原因会报“结构化执行失败原因损坏”，驾驶舱快照打不开）。首个含本功能的发布之前的版本（包括已部署的 1.3.3-163c7a3、1.3.3-8d7d387）都认不出它；发版和切换版本前先查有没有项目记过 `EXECUTOR_LOST`。
