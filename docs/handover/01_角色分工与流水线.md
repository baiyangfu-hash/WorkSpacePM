# 角色分工与流水线

> 出处：`AGENTS.md`（AUD-001、WS-001、FIX-001）；用户已定做法（项目记忆，2026-10-22～10-28 整理）。凡标“用户授权（未找到原话）”的，是按记忆整理，原话以用户为准。

## 一、四个角色

| 角色 | 现在谁做 | 做什么 | 不做什么 |
|---|---|---|---|
| 决策与验收（用户） | 用户本人 | 拍板需求和业务取舍；PLC 业务逻辑认可；安全签字；删除、切换发布、规范库改动、改 `.trae/` 的同意；最终验收 | 不看代码、不敲命令（能让 AI 做的不交给他） |
| 作者 | AI 工程师（一债一个会话） | 读代码、出计划、写代码和测试、开 PR | 不审自己的 PR，不合自己的 PR |
| 独立审计 | **另一个** AI 会话 | 跑 `python reviews/tools/audit_pr.py <PR号>`，照 `reviews/21_audit_checklist.md` 逐项核，写报告，结论贴 PR 评论 | 不推被审的分支，不删任何东西；写的人不能审 |
| 合并 | 云端合并线程 | 审计过 + CI 全绿 + 评审对话全部解决，三条都满足，用 **Merge commit** 合；合后一句话告知 | 不用 Squash 或 Rebase；安全区、`.trae/`、`AGENTS.md`、规范库的 PR 不自己合，等用户 |
| 协调 | 协调者会话 | 排期、盯所有讨论串、问题池分级、日报；只在需要用户动手时叫他 | 不替用户拍板 |

做和审要分开会话。第二审计员和云端作者各有固定线程；审计号按 `reviews/` 里现有最大号往后取，开号前先 `ls reviews/` 查重。

## 二、一个 PR 的流水线

1. **认领**：先在认领清单里登记（债号、预计改的文件），再动手。两边预计改的文件有交集，后登记的换债。清单见共享文件夹 `plans/驾驶舱技术债认领_*.md`（**不在仓库里，待搬**）。
2. **开分支**：`<agent 前缀>/<主题>`，前缀见 `AGENTS.md` WS-001 表（Claude 云端用 `claude/`，Trae 用 `trae/`）。一个分支一件事。
3. **写 PR 描述**：照 `.github/pull_request_template.md` 的字段写：做了什么、可改范围（每行一个完整路径）、安全回路（是/否）、证据、同类排查、关联 TD。AI 写的 PR 末尾要有署名行。
4. **机器关**（必过检查，不过合不进 main）：
   - `gate`（越界检查）：改的每个文件必须在“可改范围”里；锁定文件（`AGENTS.md`、`.github/workflows/*`、`00_Obsidian_Base*`、`00_Infrastructure/auto_pm/*`、`.auto-pm/*`、带 `CHG-`、`DEC-` 的文件、`*_WBS_PM.md`、带“台账”二字的文件、`roles/*`）必须**逐字写出完整路径**，目录前缀不算授权。
   - `safety-zone`（安全区签字）：碰安全区必须有用户账号对当前头提交号的“安全签字”评论。
   - `reviews-tools`：每个 PR 都跑，含严格 UTF-8 乱码扫描。
   - `sw008-ci`：按路径过滤，只在改到项目目录、环境目录或工作流文件时自动跑。**纯文档 PR 没触发时，要手动跑一次（workflow_dispatch）**；改“受保护清单”（`audit_pr.py` 的 `PROTECTED_PATTERNS` 和 `pm verify` 用的受保护清单，两份要一起改）的 PR 必须手动跑一次。
5. **独立审计**：见上；审计报告每段结论末尾单独一行 `放行判定: <头提交前8位> 过|有条件过|不过`（`pr ready` 只认这一行）。判“有条件过”且唯一条件是“CI 全绿”的，合并线程在头提交不变、CI 全绿时直接合，审计员不必再回来改。
6. **合并**：三条满足才合；只用 Merge commit。
7. **回写**：台账、WBS、治理库、发布指针**只由主执行写**（用户笔记本上的那一个会话），云端会话只在 PR 里写“建议回写”。

## 三、做事的硬要求（来自 FIX-001，用户 2026-10-22 批准）

1. 修缺陷先写根因，再把全库同类写法一次查全，清单写进 PR，逐条修或写明不修的理由；只修挡路的一处不许报“已修好”。
2. 样件联调查出的缺陷，本周的活会碰到就先修再用。
3. 说“完成”“可承诺”必须附证据（提交号、对账结果、门禁结果之一）；拿不出写“未核实”。
4. 向用户提问前先查 `03_用户已定事项.md` 和用户给过的图纸手册；同一问题不问第二次。
5. 交给用户的每个操作写四样：哪台电脑、哪个窗口或对话（全名）、点什么或贴什么、做完看到什么。AI 能用命令行做的不交给用户。
6. 云端预做队列常备 3 件，不让云端闲着。

## 四、重载任务的时间窗

- 笔记本上的重载任务（全量测试、长门禁）：**17:00～21:00 MST 禁跑**，要防休眠，不与用户在场操作同时跑；开跑前挂一个到时检查的提醒。
- 云端清技术债不受这个时间窗限制（用户 2026-10-28 15:48 MST 明确：“17:00 不停了”）。
- 门禁判卷：每组通过/跳过数必须先实跑再填，不凭印象填数。

## 五、已知的几个漏洞（别假装它们不存在）

- 本机或云端 agent 如果拿着用户账号的令牌，能代用户在 PR 上写评论，机器分不出是谁写的，所以“安全签字”这道锁有洞（`reviews/` 里的安全签字说明已写明）。补法：第二个 GitHub 账号、只给最小权限的细粒度令牌。
- 批准口令（缺口⑨）的代码在 main，但口令校验文件未提交，现在只做格式检查；用户已把它挂起。
- “agent 说完成了”这句话本身不受机器控制，要靠证据和审计。
