# 功能模块迭代流程标准

## 1. 定位

本文规定功能迭代从事实澄清、授权、执行、验证到发布收尾的统一生命周期。它不绑定 Trae、Cursor、Codex 或任何单一技能；跨 Agent 状态与恢复遵循 PM-056，变更授权遵循 PM-042，物理派发遵循 PM-046。

## 2. 核心原则

1. 代码基优先：Brownfield 必须先读取源码、配置、接口和现有测试。
2. 授权与执行分离：CHG/Decision 决定“可不可以做”，Work/Run 记录“正在怎么做”。
3. 一 Work 一范围：新增发现不得暗中扩项。
4. 一事实一真源：PM_SESSION 仅作项目摘要投影。
5. 真实验证：口头 PASS、模拟结果和旧 release 结果不能代替声明范围内的门禁。
6. 可回退：写入、发布和迁移必须有明确恢复路径。

## 3. 生命周期

| 阶段 | 目标 | 必要输出 | 硬停止条件 |
|---|---|---|---|
| 0 事实澄清 | 建立真实基线 | Context、read set、影响文件、风险与未知项 | 未读代码、subject/control 冲突 |
| 1 规划与授权 | 冻结范围和验收 | CHG/Decision、Work、acceptance、回退方案 | 写入型 Work 未批准 |
| 2 执行 | 在 lease 和 owned paths 内实现 | Run、增量 checkpoint、测试证据 | lease/基线/dirty/scope 冲突 |
| 3 验证 | 证明交付满足验收 | 全量与专项门禁、失败注入、差异审查 | 任一必需门禁非零 |
| 4 发布与收尾 | 受控生效并关闭 | 不可变制品、manifest、切流/回退证据、关闭状态 | 制品不可复现或台账不一致 |

## 4. 阶段 0：事实澄清

### 4.1 Brownfield

先从 Workspace Registry 和局部项目锚点解析 Context，再读取目标源码、配置、接口文档、数据结构、调用关系和测试。可通过 PM-046 的只读 Grooming 派发调研，但必须创建 read-only Work，并回传带路径和证据的结构化结果。

只有代码库无法回答的真实业务取舍、物理硬件事实或互相冲突的目标，才提交用户决策。

### 4.2 Greenfield

先确认产品目标、边界、关键输入和验收。工业项目还需确认 CAD/轴系/动作时序等不可推断事实。缺失时先检索已批准规范和模板，仍无法推导再提问。

## 5. 阶段 1：规划与授权

写入前必须形成：目标与非目标、精确 scope paths、依赖关系、风险、测试矩阵、发布与回退方案。变更内容通过 PM-042 的 CHG/Decision 获得授权，然后创建 Work；Work scope 不得超过批准文件。

Spec、设计或计划产物放在项目约定的文档目录并登记路径，不强制 `.trae/specs` 或任何 IDE 私有目录。

## 6. 阶段 2：执行

每次执行创建独立 Run，绑定 executor、adapter、Git HEAD、worktree、owned paths 和 dirty 声明。执行者只修改授权且 owned 的文件；发现新范围时创建关系 Work 并停止越界写入。

Checkpoint 在有可恢复增量时追加，至少包含摘要、Git 基线、dirty paths 和验证 evidence。跨 Agent 续跑必须使用 PM-046 Handoff，并由接收方原子取得 lease。

## 7. 阶段 3：验证

验证强度与风险匹配，至少覆盖：

- 新增或修改逻辑的自动化测试；
- 相关静态检查、类型检查和文档门禁；
- 真实入口或真实运行环境的冒烟；
- 关键失败路径和 fail-closed 行为；
- dirty tree、Git diff 和 scope 越界检查。

GUI、PLC 或外部设备无法在本机完成的部分必须明确标为 `not_verified`，并说明由谁、在何环境完成；不得伪造通过。

## 8. 阶段 4：发布与收尾

发布从已提交母体构建不可变制品，先做 inactive 验证，再切换 active；previous 必须可回退。运行入口采用项目声明的 release launcher，例如：

```text
<workspace-python> <workspace-root>/main.py --workspace <workspace-root> <command>
```

禁止把本机绝对解释器路径、editable install 或 `python -m auto_pm` 写成规范要求。

完成后关闭 Run 和 Work，更新 CHG/Decision 实施与验证记录、变更台账和必要项目摘要。PM_SESSION 不记录执行队列、lease token 或 next action。

## 9. 角色与平台适配

| 角色 | 职责 |
|---|---|
| 用户/架构师 | 业务与高风险变更最终决策 |
| PM 职责 | 范围、授权、依赖、风险和验收闭环 |
| 执行者 | 在 Work/Run/lease 边界内实现并自检 |
| 验收者 | 独立核对 evidence、制品和运行结果 |
| Adapter | 平台输入输出转换，不持有核心状态 |

角色是职责，不等于某个技能名。任何技能或 IDE 均不得独占 PM owner 或规范生命周期管理权。

## 10. 最小交付清单

- [ ] Context 无冲突，read set 可追溯
- [ ] CHG/Decision 已批准，Work scope 未越界
- [ ] Run、lease、dirty、Git/worktree 可核验
- [ ] Checkpoint/Handoff 足以恢复
- [ ] 必需测试和门禁 Exit 0
- [ ] active/previous 与 manifest 可验证
- [ ] Work/Run/CHG/台账状态闭环
- [ ] 未修改未授权规范或其他 owner 文件
