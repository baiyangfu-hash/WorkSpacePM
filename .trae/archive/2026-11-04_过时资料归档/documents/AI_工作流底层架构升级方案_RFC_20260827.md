# AI 工作流底层架构升级方案：子代理物理隔离机制 (RFC/交接文档)

## 1. 变革动因与背景 (Why)
在当前的“一人团队”工作流中，所有的规划（PM）、编码（PLC/全栈）和排错都在同一个主对话（主 Agent）中顺次进行。
随着项目复杂度的提升，暴露出了致命的底层缺陷：
- **上下文污染 (Context Bleed)**：长对话积累了大量的废弃需求、试错过程和情绪拉扯。这导致 AI 的“注意力机制 (Attention)”被严重稀释，产生用 Python 思维写 PLC、或者无视 `STD-820` 规范的幻觉。
- **职责越界**：主 Agent 既当裁判又当运动员，违反了高内聚低耦合的工程原则。

**结论**：必须从“Prompt 软约束”升级为“系统级物理隔离（硬约束）”。

---

## 2. 核心架构优势 (Advantages)
实施“子代理物理隔离”后，工作流将获得以下决定性优势：

1. **算力 100% 聚焦 (极致纯净的上下文)**
   每次进入 `developing`（开发）阶段，系统会开辟一个全新的独立线程。子代理**完全看不见**之前的拉扯过程，它的脑子里只有唯一的输入（精确的 JSON 需求）和唯一的法则（如 `LSP-905`），从而输出工业级的确定性代码。
2. **强制契约化交付 (Zero-Burden 落地)**
   通过定义标准 JSON 交接包，强迫 PM Agent 必须把模糊的需求转化为精确的输入。如果 PM 没写清楚，子代理就会报错，从而倒逼上游提高需求质量（这也是真实软件工程的核心）。
3. **真正的异步并行与自闭环**
   主 Agent 下发任务后可以被释放，子代理在“黑盒”中自行调用 Linter、跑测试，直到全绿才将最终结果通过 `send_message` 汇报，彻底解放你的精力。

## 3. 跨 Agent 移交契约：数据结构细节 (The Handoff Contract)
为了实现物理隔离，PM 技能与执行技能之间必须依靠 JSON 契约进行通讯。
PM 必须生成以下标准的 `skill_context` 并将其喂给子代理：

```json
{
  "handoff_metadata": {
    "source_agent": "pm-workflow",
    "target_skill": "plc-electrical-engineer",
    "timestamp": "YYYY-MM-DD HH:MM:SS"
  },
  "project_context": {
    "project_id": "DJ-2026-009",
    "project_path": "C:\\Users\\fubai\\Documents\\My_Workspace\\0100_PLC自动化\\DJ-2026-009_汇川换型改造"
  },
  "execution_payload": {
    "baseline_documents": [
      "02_PLC程序/PLC_ST/00_程序方案/详细设计说明书_DSN.md",
      "02_PLC程序/PLC_ST/00_程序方案/接口文档_INT.md"
    ],
    "goal": "基于 DTO 架构完成 FB_Handshake_8Step 与 FB_Comm_Adapter 的 ST 源码编写",
    "strict_constraints": [
      "禁止任何硬线物理寻址 (%IX/%QX)",
      "必须遵守 STD-820 8步握手规范",
      "必须使用 CASE 语句并包含 ELSE 防死锁逻辑 (LSP-906)"
    ]
  }
}
```
**细节说明**：
- `baseline_documents` 强制子代理自己去读文件，而不是靠 PM 转述，确保信息 0 损耗。
- `strict_constraints` 是每次任务的红线，子代理必须在输出前自我对照校验。

## 4. 实施清单与规则落账 (Implementation Details)
需要由你（或引导 GPT）将以下规则正式写入工作区的真源文件：

### 4.1 写入 `AGENTS.md` (全局法典)
**新增章节：【子代理物理隔离法则】**
- **明确边界**：当前主会话仅限用于业务路由、需求澄清、架构设计（阶段0~2）及交付验收。
- **剥离执行权**：当状态机切入 `developing`（编码执行）时，主 Agent **褫夺编码权**。
- **强制工具调用**：必须强制使用 `invoke_subagent` 拉起专职 Agent 并在后台运行。

### 4.2 写入 `.trae/skills/pm-workflow/refs/cockpit_context.md` (PM 路由规则)
**修改流转逻辑**：
- 在状态从 `planning` 切换至 `developing` 的触发器中，加入“必须生成 `skill_context` 结构化 JSON”的强制前置条件。
- 规定 PM 必须调用唤醒命令，并在子代理运行期间进入“等待回传”状态。

### 4.3 写入 `.trae/skills/plc-electrical-engineer/SKILL.md` (执行端自治规则)
**增加子线程自闭环协议**：
- **拒绝索要上下文**：子代理严禁向 User 提问，必须自行利用 `view_file` 读取 JSON 契约中指向的文档。
- **强制内部测试**：代码写完后，强制自行调用代码检查工具（如 Linter）跑通测试。
- **统一汇报接口**：结果一律通过 `send_message` 工具反馈给 PM Agent，严禁将中间报错抛给外部 User。
