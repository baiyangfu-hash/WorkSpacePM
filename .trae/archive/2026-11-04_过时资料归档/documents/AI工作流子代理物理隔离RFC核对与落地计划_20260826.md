# AI 工作流「子代理物理隔离」RFC 核对与落地计划

## 1. 摘要 (Summary)

用户提交的 `AI_工作流底层架构升级方案_RFC.md` 提出「子代理物理隔离」机制，要求将规则写入 `AGENTS.md`、`cockpit_context.md`、`plc-electrical-engineer/SKILL.md` 三处。

经核对，RFC 的**理念正确**（剥离执行权、契约化交接、执行端自闭环），但**细节与工作区真源存在 3 处硬冲突 + 2 处覆盖缺口**：

| 类型 | RFC 原文 | 工作区真源 | 处置 |
|---|---|---|---|
| 工具名失真 | `invoke_subagent` / `send_message` / `view_file` | 无此工具；真实为 IDE 子代理机制（Task/subagent）+ `handoff_result` 写入 `.auto-pm/handoffs/<request_id>.json` | 通用化修正 |
| 状态机虚构 | `planning → developing` | 无此状态机；真实为四阶段门禁 + PMBOK 5 大过程组 + G1-G4 | 通用化修正 |
| JSON 契约冲突 | 新契约 `execution_payload/baseline_documents/strict_constraints` | 已有 `skill_context` → `handoff_result` | 扩展现有契约 |
| 覆盖缺口 | 只写 PLC 执行端 | 工作流含全栈 | 补齐 fullstack |
| 概念混用 | 示例用 `DTO 架构 + FB_Handshake_8Step` | DTO 属 Python 域；实际 FB 为 `FB_3001_ExternalInteraction` | 修正示例 |

**落地方向（已与用户确认）**：修正为实际机制 + 扩展现有契约 + PLC/全栈同时覆盖 + 通用化（不绑定单一 AI IDE 的工具名）。

## 2. 现状分析 (Current State Analysis)

现有跨技能协同机制已成型，RFC 应「扩展」而非「替换」：

- **单一真源**：`.trae/skills/shared/refs/skill_coordination.md` 定义三技能边界：`pm-workflow` 是唯一落账 owner，`plc-electrical-engineer`/`fullstack-engineer` 是纯执行者，接收 `skill_context`、回传 `handoff_result`。
- **输入契约 `skill_context`**：定义在 `.trae/skills/pm-workflow/refs/cockpit_context.md` §3，字段为 `source/request_id/project_id/stack/change_number/change_domain/change_nature/mode/pm_summary`。
- **输出契约 `handoff_result`**：定义在 `.trae/skills/pm-workflow/refs/handoff_schema.md` §1。
- **执行门禁**：PLC 端 `auto-pm plc check`；全栈端 `ruff + mypy + pytest`。
- **阶段术语**：四阶段（澄清→报批→执行→验收）+ PMBOK 5 大过程组（启动/规划/执行管控/变更管理/收尾验收，见 `00_Obsidian_Base全局规范文件仓库/01_项目管理域/` 目录结构）+ G1-G4 门禁。

RFC 的「物理隔离」本质是「阶段 2【执行】」的派发与回收纪律，应嵌入现有四阶段 + PMBOK 框架，而非另立 `planning/developing` 状态机。

## 3. 术语修正对照表（通用化，不绑定 IDE）

| RFC 原文 | 修正为（通用化表述） | 落点 |
|---|---|---|
| `invoke_subagent` | 启动独立执行子代理/执行技能（各 IDE 按自身 Task/subagent 机制调用） | 不硬编码工具名 |
| `send_message` | 通过 `handoff_result` 写入 `.auto-pm/handoffs/<request_id>.json` 回传 | 现有机制 |

| `developing` | 阶段 2【执行】/ PMBOK 执行过程组 | 现有四阶段 |
| 新 JSON 契约 | 扩展 `skill_context`（新增 `baseline_documents`/`goal`/`strict_constraints`，保留原字段） | 向后兼容 |

## 4. 拟变更文件与具体内容 (Proposed Changes)

### 4.1 `AGENTS.md`（全局法典）

**位置**：在「强制协同铁律」章节之后新增一节「子代理物理隔离法则」。

**新增内容**：

```markdown
## 子代理物理隔离法则（执行权剥离）

1. **明确边界**：主会话（主 Agent）仅限业务路由、需求澄清、架构设计（PMBOK 启动/规划过程组）与交付验收（收尾过程组）。
2. **剥离执行权**：四阶段门禁进入【阶段 2 执行】时，主 Agent 褫夺编码权，仅做派发与验收，不亲自写代码。
3. **强制契约化交接**：派发前必须生成结构化 `skill_context`（含 baseline_documents、goal、strict_constraints）；执行端以 `handoff_result` 回执，严禁口头转述需求。
```

**为何**：把 RFC 的「物理隔离」落到现有四阶段门禁框架，明确执行权剥离的触发点是「阶段 2」。

### 4.2 `.trae/skills/pm-workflow/refs/cockpit_context.md` §3（扩展 skill_context）

**位置**：§3 `skill_context 传递结构` 的 JSON 示例与说明。

**改动**：在保留现有 9 个字段基础上，新增 3 个字段，并补充说明。

**新增后 JSON**：

```json
{
  "source": "pm-workflow",
  "request_id": "AI-20260821-001",
  "project_id": "DJ-2026-009",
  "stack": "plc",
  "change_number": "CHG-PLC-2026-001",
  "change_domain": "PLC",
  "change_nature": "DEF",
  "mode": "变更/缺陷/发布",
  "pm_summary": "上下文已通过 cockpit AI 辅助恢复，跳过项目识别。",
  "baseline_documents": [
    "02_PLC程序/PLC_ST/00_程序方案/详细设计说明书_DSN.md",
    "02_PLC程序/PLC_ST/00_程序方案/接口文档_INT.md"
  ],
  "goal": "基于 STD-820 完成 FB_3001_ExternalInteraction 的 8 步握手 ST 源码编写",
  "strict_constraints": [
    "禁止任何硬线物理寻址 (%IX/%QX)",
    "必须遵守 STD-820 8步握手规范",
    "必须使用 CASE 语句并包含 ELSE 防死锁逻辑 (LSP-906)"
  ]
}
```

**新增说明**：
- `baseline_documents`：强制执行端自行读取文档，信息 0 损耗，PM 不得转述。
- `goal`：本次执行的唯一目标。
- `strict_constraints`：任务红线，执行端输出前必须自我对照校验。

**为何**：满足用户「扩展现有契约」决策，向后兼容，不另起炉灶。

### 4.3 `.trae/skills/plc-electrical-engineer/SKILL.md`（执行端自闭环协议）

**新增内容**：

## 5. 假设与决策 (Assumptions & Decisions)

1. **通用化原则**：文档来自其他 AI IDE，规则措辞不硬编码任何单一 IDE 工具名（`invoke_subagent`/`send_message`/`view_file`），改用「执行子代理/执行技能」「读取文件」「handoff_result 回执」等中性表述。
2. **契约扩展而非替换**：`skill_context` 原 9 字段全部保留，仅新增 3 字段；`handoff_schema.md` 与 `shared/refs/skill_coordination.md` 本次不改动（其已引用 skill_context 且无需结构变化，避免无关重构）。
3. **状态机归并**：不引入 `planning/developing` 新状态机，直接嵌入现有四阶段门禁 + PMBOK 5 大过程组。
4. **示例纠偏**：RFC §3 示例的 `DTO 架构 + FB_Handshake_8Step` 属概念混用，落地示例改用 `STD-820 + FB_3001_ExternalInteraction`（符合 LSP-905 命名与真实项目）。
5. **范围收敛**：仅改上述 4 个文件，不触碰 Obsidian 规范真源、`spec_registry.json`、`auto-pm` 源码。
