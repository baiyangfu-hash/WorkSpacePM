## 2. P0 级改进建议（严重，必须修复）

### P0-001: 修复 auto-pm site 模块 GBK 编码崩溃

- **问题描述**: 直接运行 `python -m auto_pm` 会因 site 模块初始化失败而崩溃，报错 `UnicodeDecodeError: 'gbk' codec can't decode byte 0xaa in position 48`。该错误发生在 Python 解释器加载 site 模块阶段（`site.addpackage` 处理 .pth 文件时），早于任何 auto-pm 代码执行。设置 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`、`python -X utf8` 均无效。当前仅能通过 `python -S` + 手动注入 site-packages 路径绕过。
- **来源**: 参考项目双重审查报告 §1.2 执行环境说明
- **改进建议**:
  1. 排查 `.venv\Lib\site-packages\` 下所有 `.pth` 文件，定位含 0xaa 字节的源头文件
  2. 在 auto-pm 启动脚本中强制设置 `PYTHONUTF8=1` 并在 site 加载前生效（或改用 `python -X utf8` 启动包装器）
  3. 在 pyproject.toml 的 `[project.scripts]` 入口点添加 UTF-8 强制初始化逻辑
  4. 补充启动诊断命令 `auto-pm doctor` 检测环境编码问题
- **建议纳入版本**: V2.5（系统设置/打包）

### P0-002: plc check 增加"文档实质化"检查

- **问题描述**: `auto-pm plc check DJ-2026-000` 报告 13 项全部 PASS，但 PRD/REQ.md 全文 47 行均为"待填写"占位符，frontmatter 标注 `lifecycle: draft`。检查器仅验证"文件是否存在"，不验证"内容实质化"，导致检查结果误导用户认为文档已就绪。SysLib 的 REQ.md 同样存在此问题。
- **来源**: 参考项目双重审查报告 §2.2（DJ-2026-000 REQ 空模板仍判 PASS）+ §3.2.1（SysLib 同问题）
- **改进建议**:
  1. 在 plc check 检查器中新增"文档实质化"检查项，扫描"待填写"/"待定义"/"待补充"等占位符比例
  2. 占位符比例超过 30% 时发出 WARN，超过 70% 时发出 FAIL
  3. 检查 frontmatter 的 `lifecycle` 字段，`draft` 状态的项目在 `plc check` 中提示"文档仍在草稿阶段"
  4. 必填字段（如 REQ §3.1 项目来源、§4.1 核心功能）若仍为占位符则直接 FAIL
- **建议纳入版本**: V2.4（模板/插件/报告）
